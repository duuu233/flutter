# Wi-Fi 版相框接入（二）：功能差异矩阵 · 详情页 · 搜索动线

> 文档类型：Analysis（决策依据，不是当前实现事实）
> 日期：2026-09-19
> 承接：[`WIFI_FRAME_BLUFI_ANALYSIS.md`](WIFI_FRAME_BLUFI_ANALYSIS.md)（2026-09-18，BluFi 配网可行性）
> 依据材料：`docs/相框v2.0.0/XT相框通讯协议_V1.3.1(1).pdf` + 三份产品规格说明书；
> 本仓当前实现：`lib/src/device/ble/frame_protocol.dart`、`features/devices/presentation/device_details_page.dart`、
> `features/cast/`、`state.dart` 的 `refreshDevices`
> 适用：相册 App 与相册小程序（两端结论一致，差异在 §5）

## 0. 三句话结论

1. **架构先变，功能才谈得上**：Wi-Fi 版里 **App 不跟设备说话**。设备只跟服务器走 MQTT，
   App 只跟后端走 REST——现在端上那套「连上蓝牙→发指令→等 ACK」整条不复用。
2. **详情页必须新做一份**：现有那一页 13 个元素，逐个对下来**只有 4 个语义没变**，
   其余要么数据源换了、要么语义变了、要么根本不存在（连接/断开、连接间隔）。
3. **搜索可以合并，但合并的只是"配网"那一段**：已配网的 Wi-Fi 设备**根本不在 BLE 广播里**，
   它和现在的蓝牙相框一样从**后端设备列表**来。所以「同时搜到蓝牙和 Wi-Fi 设备」这句话，
   只在**添加设备**那一屏成立。

## 1. 架构差异（这一条决定其余所有）

| | 蓝牙版（现在） | Wi-Fi 版 |
| --- | --- | --- |
| 谁跟设备说话 | **App**（BLE GATT，FF00/FF01/FF02 + 自研帧协议） | **服务器**（MQTT v3.1.1 QoS1，`/device/report/{clientid}` ↔ `/inkjoyap/{clientid}`） |
| App 的角色 | 指令发起方 + 图片编码方 | **只跟后端说话**；设备那头由服务端代劳 |
| 图片怎么到屏上 | App 本地抖动编码（`image_codec.dart`）→ BLE 0x20/0x21/0x22 分片传 | 服务端把 `.bin` 放在 host/port/path，MQTT 下发 `play`/`strategy_bin`，**设备自己去下载** |
| 设备在不在 | BLE 连接态 | MQTT 心跳（`heart`，含 `wifi_rssi`/`battery`/`tf`…） |
| 实时数据 | 连上才有（0x01/0x03/0x04） | 心跳里常有，**不连也有** |

**对 App 的直接含义**（两条，落地前必须跟后端对齐）：

- ✅ **App 不需要 MQTT 客户端**。协议白纸黑字：手机与设备之间「**目前只有配网阶段**」有通信（BluFi）。
- ⚠️ **Wi-Fi 版的每一个动作都要后端给一个接口**（下发 `play` / `strategy` / `wifimode` /
  `wifi_sleep` / `clean_tf` / `ota`…）。**这套接口目前一个都没有**——这是整件事的关键路径，
  比端上 UI 大得多。

## 2. 功能差异矩阵

「现在」= 相册 App/小程序今天对蓝牙相框做的事；「Wi-Fi 版」= 协议 V1.3.1 + 规格书给的能力。

| 能力 | 现在（蓝牙） | Wi-Fi 版 | 差异结论 |
| --- | --- | --- | --- |
| **投屏 / 传图** | 端上编码 + BLE 分片传（0x20–0x23），进度、失败重试全在端上 | `play` 下发**单图 URL**，设备自己下载 | ⚠️ **整条换掉**。端上那套编码/分片/进度不再适用；「谁生成 `.bin`」文档没写（昨天那份 §5.1 的头号风险） |
| **指定当前显示图** | 0x24 SET_CUR_IMG（按槽位索引） | 无直接对应（只有 `play` 单图 / `strategy` 策略） | 🔶 语义变了：从"选第 N 槽"变成"服务端推哪张" |
| **轮播** | 0x02/0x10：`PLAY_MODE`（顺序/随机/手动）+ `INTERVAL`（秒） | `strategy`：顺序/随机 + **固定时间点**或**间隔分钟** + `updatedays` + **轮播后是否休眠**；另有 `strategy_bin`（设备本地按策略挑图）、`strategy_stop` | ⚠️ **Wi-Fi 版能力更强**，现有轮播设置页的两个字段装不下 |
| **删图** | 0x12：12 字节**槽位掩码**（精确删某几张） | `clean_tf`：`ALL` / `LOCAL` / `OTHER` **整类清空** | ⚠️ **粒度变粗**：现有「一键清空」能映射，「删某一张」映射不了 |
| **最大照片数 / 已用槽位** | 0x01 的 `imgMask`/`imgCount`/`capacity` | 心跳的 `tf`/`tfsize`/`tfused`（**TF 卡容量，单位 MB**） | ⚠️ **口径换了**：从"槽位数"变成"存储空间"。详情页那一行要重画 |
| **电量** | 0x04（连上才读） | 心跳 `battery`（常驻） | ✅ 语义相同，数据源更好 |
| **固件版本 / 升级** | 0x03 读版本；OTA 走既有升级页 | `ota`（host/port/path）+ **`fpga`（FPGA 升级）** + `ota_status` 上报 | ⚠️ **多一条 FPGA 升级链路**，心跳里也多一个 `fpga_ver`；蓝牙版没有这个概念 |
| **校时** | 0x11 SET_TIME（App 把手机时间发给设备） | **协议里没有校时指令** | ⚠️ 需确认设备怎么对时（NTP？服务端下发？）。⚠️ 别照搬 0x11 |
| **连接 / 断开** | 详情页顶部的主操作 | **不存在这个概念**（设备常驻 MQTT） | ⚠️ 这颗按钮在 Wi-Fi 版详情页要**去掉**，不是置灰 |
| **连接间隔** | 0x05/0x13（BLE 调参） | 不适用 | ⚠️ 消失 |
| **屏幕尺寸 / 分辨率** | 0x01 的 `width`/`height`/`screenType` | 协议不带；规格书静态参数（7.09 = 1200×1600，10.1/13.3 = 1600×1200，均 Spectra6 六色） | 🔶 改由**后端产品档案**给 |
| **工作模式** | 无 | `wifimode`：实时 / 定时 / 休眠 + 唤醒保持时长 + 定时周期 | 🆕 **新增**，要新出 UI |
| **定时休眠** | 无 | `wifi_sleep`：一次性 / 周期，起止时间；**App 存本地时间、下发转 UTC** | 🆕 新增 |
| **TF 卡** | 无 | `play_tf` 播放卡内图、`clean_tf` 清卡、心跳报容量/已用 | 🆕 新增 |
| **内置图** | 无 | `down_int_img`：出厂页 / 设置页 / 无 Wi-Fi / 低电量 / 关机 / 已连接六张（带坐标与 CRC16） | 🆕 新增（偏运营配置，可能不进 C 端） |
| **国家码** | 无 | `country` + 配网时 `wifi_set_country_code`（影响信道与发射功率） | 🆕 新增 |
| **屏幕方向** | App 侧导出角（`device_rotation.dart`：横向取后端 `rotationDegree`、竖向 `verticalRotation`） | 心跳有 `orientation`，但协议原文标注「**当前取不到预留**」 | ⚠️ 设备侧有字段但没数据；导出角这套**还得端上自己算**，不能指望设备 |
| **关机 / 低电** | 端上按电量阈值提示 | 设备主动上报 `shutdown`；低电量有内置提示页 | 🔶 提示时机从端上判断变成设备驱动 |
| **设备归属 / 绑定** | 端上 BLE 绑定 + 后端登记 | `device_config` 由**服务端**下发 `uid`/`deviceId`/`batchKey` | ⚠️ 认领链路要后端给（昨天那份 §5.2） |
| **蓝牙标签（uptag）** | 无 | 协议里有，但那是 XT **基站/标签**家族的东西 | 🚫 相框不用，别实现 |

**一句话**：相同的只有「电量」「删全部」「升级」「设备名/ID」这几项；**投屏、轮播、删图、校时、
连接**五项要么换实现要么换语义；**工作模式、休眠、TF 卡、内置图、国家码**五项是纯新增。

## 3. 设备详情页：为什么必须新做一份

现有 `device_details_page.dart` 的 13 个元素逐个对：

| 现在这一页上的元素 | Wi-Fi 版 | 处理 |
| --- | --- | --- |
| 摘要卡（图 + 名称 + 电量） | 电量来自心跳 | ✅ 留，换数据源 |
| **投屏** | 走「选图 → 后端 → `play`/`strategy_bin`」 | ⚠️ 留按钮，**整条动线换** |
| **连接 / 断开** | 无此概念 | ❌ **删** |
| 轮播设置 | `strategy` 能力更大 | ⚠️ 留入口，**页面重做**（加定时/固定时间点/轮播后休眠） |
| 设备 ID | 心跳 `clientid` / `stamac` | ✅ 留 |
| 屏幕尺寸 | 后端产品档案 | 🔶 留，换数据源 |
| 最大照片数量 | 换成 TF 卡容量/已用 | ⚠️ **换口径重画** |
| 固件升级 | `ota` + **FPGA 版本**两条 | ⚠️ 留，**可能要并列两行** |
| 一键清空 | `clean_tf` | ✅ 语义能对上 |
| 解除绑定 / 删除设备 | 后端 + `device_config` | 🔶 留，后端链路换 |
| 重命名 | 后端 | ✅ 留 |
| —— | **工作模式**（实时/定时/休眠） | 🆕 新增一行 |
| —— | **定时休眠**、**TF 卡**、**国家码**、**时间同步** | 🆕 新增 |

**结论：新做一份 `WifiDeviceDetailsPage`，不要在现有页上加 `if (isWifi)`。**
理由不是"页面长得不一样"，而是**三条硬的**：

1. **数据来源不同**：现在这一页的实时数据是「连上 BLE 之后 0x01/0x03/0x04 读回来的」，
   页面上大量 `--` 占位、粘性版本号、连接态红点等逻辑全是围着"连没连上"转的；
   Wi-Fi 版没有连接态，那套占位/粘性规则一条都不适用。
2. **动作通道不同**：每一颗按钮从"BLE 写帧 + 等 ACK"变成"调后端接口 + 等 MQTT 回执"，
   失败语义、超时、重试全不一样。
3. **加 `if` 的代价**：这一页现在 1000 行、注释里记着十几条踩过的坑（版本号粘性、
   红点与点击同源、分辨率不跟随连接态……）。往里塞第二套数据源，等于让这些坑全部翻倍。

🔶 **可以共用的**：摘要卡、信息行组件、二次确认弹窗（`AppDialog`）、删除/解绑流程的外壳。
建议把这些抽成共用件，两份详情页各自组装。

## 4. 搜索动线：能不能合并（再次确认）

分三层看，结论不一样：

### 4.1 广播层：**可以合并**（结论同昨天，且更有把握）

`DeviceBle.scan()` 本来就**不按 service UUID 过滤**，放行靠「后端产品列表 `broadcastId` 白名单
+ 厂商数据兜底」。Wi-Fi 版在**配网模式**下广播 BLE 名 `IJ_<MAC>`（BluFi），同一轮扫描就能收到。
后端把 Wi-Fi 版产品的 `broadcastId` 配成 `IJ_`，现有 App **一行不改**就能把它列出来。

⚠️ 但端上仍要**认得出**「这一行是 Wi-Fi 版」，且匹配要用 **`IJ_` 前缀**而不是 `contains('IJ')`
（两个字母太短，会把周围名字带 IJ 的蓝牙设备都放进来）。

### 4.2 选中之后：**不能合并**

| | 蓝牙相框 | Wi-Fi 版 |
| --- | --- | --- |
| GATT | FF00 + FF01/FF02 | BluFi（乐鑫默认 `FFFF`/`FF01`/`FF02`，待真机确认） |
| 会话 | 自研帧协议 | BluFi 帧 + JSON 自定义消息 |
| 下一步 | 直接绑定、传图 | 配网（SSID/密码/MQTT 参数）→ 设备上云 → 后端认领 |

⚠️ **分叉必须放在"点之前"**：现在的代码连上去发现没有 FF00 会报
「未找到相框主服务(FF00)…请确认是相框设备」——对 Wi-Fi 版用户这是一句与事实不符的话。

### 4.3 ⚠️ 已绑定设备：**本来就不经过搜索**（这一条昨天没讲透）

两端的设备列表都来自**后端**（App：`/Client/UserProduct/getUserProductList` → `DeviceItem`；
BLE 只在连上时回填电量/内存/版本这些实时字段）。而 Wi-Fi 版设备**配好网之后 BLE 大概率不再广播**
（协议里 BLE 只服务配网阶段，心跳里的 `ble` 开关也说明它可关），所以：

> 「同时搜到蓝牙设备和 Wi-Fi 设备」这句话**只在"添加设备"那一屏成立**；
> 已绑定的两类设备本来就一起躺在后端列表里，不需要"搜"。

这反而是好消息：**设备列表页不用改**，改的是列表项点进去之后进哪一份详情页
（按后端下发的产品 ID / 设备类型分流）。

### 4.4 两套方案，给产品选

| | A：合并搜索 | B：先选产品类型 |
| --- | --- | --- |
| 做法 | 一轮扫描两类设备同列，行上打「Wi-Fi 版 · 需配网」角标，点了按类型分流 | 「添加设备」先问一句是哪种，再进各自的搜索页 |
| 好处 | 用户不用知道自己买的是哪种 | 两条动线互不污染；现有那套被反复调过的搜索逻辑一行不动 |
| 代价 | 空态/失败/重试文案要同时对两类成立；`IJ_` 判别要可靠 | 多一步点击 |
| 风险 | Wi-Fi 版广播结构未知（有没有厂商数据、弱信号表现如何）——现有搜索页为「搜不到设备」调过好几轮，混进一类没摸过的设备有回归风险 | 低 |

**建议：先 B、后 A。** 等真机把 Wi-Fi 版的广播摸清楚（名字、厂商数据、信号表现）再谈合并；
合并所需的端上改动很小（一条前缀规则 + 一个分流），任何时候都能补。

## 5. 小程序侧的额外差异

结论与 App 一致（架构、详情页、搜索三条都成立），但有两点小程序独有：

1. ⚠️ **BluFi 在小程序上没有现成实现**。App 端至少能桥接乐鑫官方 SDK（Android `blufi` 库 /
   iOS EspBlufiSDK），小程序只能用 `wx.writeBLECharacteristicValue` **自己实现 BluFi 帧层**
   （分片、序号、CRC16，若固件要求安全协商还要 DH + AES-128-CFB）。
   🔶 这使得「固件能不能关掉安全协商」这个问题在小程序侧的分量比 App 更重。
2. ⚠️ **小程序 BLE 单包默认 20 字节**（`wx.setBLEMTU` 只在安卓可用），BluFi 分片会更碎、更慢。
   配网只发几百字节，影响可控，但要预留重试。

## 7. 建议落地顺序

1. **先把 §6 的 13/14/16 问掉**——后端接口与设备类型字段不定，端上做什么都是白做；
2. 拿真机 + 官方 EspBlufi 走通一次配网并抓包（昨天那份 §7 第 1 条）；
3. 端上先做**方案 B 的独立入口** + `WifiDeviceDetailsPage` 骨架（只读：心跳字段先摆上）；
4. 动作按后端接口就绪的顺序逐个接（投屏 → 轮播策略 → 工作模式/休眠 → TF 卡）；
5. 最后再谈搜索合并与两份详情页的公共件抽取。

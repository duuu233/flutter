## 0. 结论速览

**骨架是对的**：配网（BluFi + `mqtt_config` → `login`）、绑定只存关系、下行指令 + `*_ack`、
心跳喂设备影子、轮播用 `strategy` 让设备自己拉图——这几条都能在协议里找到依据，可以照着往下做。

**但有 4 处会让「功能看起来做完了、实际不闭环」的硬伤**，全部集中在“内容下行”这条线上：

| 编号 | 问题 | 后果 |
| :--- | :--- | :--- |
| **D（删图）** | 删除链路建立在三个协议没有背书的假设上（见 §2） | 用户点了删除，**相框上那张照片还在**，而且可能一直在 |
| **P1** | 投屏链路**少了「图片转 bin」这一步**；方案写的是「图片已在 OSS，复用现有上传」 | 设备拿到的是原图 JPG 而不是六色 4bpp `.bin`，**投屏必然失败或花屏** |
| **P5** | 方案默认设备随时在线，但没说设备跑在哪种 `wifimode` | **可达性是产品决策**：实时通讯可秒级下发（2.4G 下续航仍有约 5.7 个月），定时通讯默认 4 小时才醒 10 分钟。两种承诺不能混着写（**二稿已修正口径，见 §8.2**） |
| **P7** | `image_refresh` 的语义与回执：协议原文只说「通知设备清空 TF 卡内容」，且 `image_refresh_ack` **没有 `result`、没有 `ack_msgid`** | 平台下发完**无法判断成功与否**，也无法与指令对应；删图、刷新两个功能都悬在这上面 |

另有 **14 处**与协议原文对不上或方案没有归属的细节（§3），以及 **6 条协议 action 方案里完全没提**（§4）。

**最要紧的一句话**：电子纸是双稳态的——**不重新刷屏，屏幕就一直显示那张被删的照片**。
所以“删除”这个动作在这类设备上，**必须伴随一次“用什么替换它”的下发**，
而方案 §6 从头到尾只有“删云端 + 择机 `image_refresh`”，没有替换图，也没有刷屏动作。

## 1. 对照方法

1. 把方案 v1.0 的 13 节逐条拆成「它用了哪条 action / 它假设了什么」；

3. 再用三份规格书的硬指标（刷图时间、续航、电池、支持格式、按键）验一遍**代价**——
   协议允许的事，不等于这台一年一充的电池设备扛得住；
4. 凡是**协议没写**的，一律标成「假设」并进 §7 待确认，不按“应该是这样”当成结论。

## 2. 重点：删除图片这条链路不成立

> ⚠️ **2026-09-20 二稿修正**：平台侧澄清「TF 卡与 App 是两个独立通道，App 投屏的图不在设备存储」。
> 据此，本章 **D2（TF 缓存 + 切图键）与 D3（清 TF 连内置图一起清）对 App 通道不再成立**，
> 详见 §8.1；**D1（不刷屏就不变）、D4（可达性，口径已修正）、D5（删空了显示什么）以及
> `image_refresh` 没有可用回执这一条仍然成立**，而且结论更干净：删 App 通道的图，
> 根本不该碰 `image_refresh` / `clean_tf`——那是 TF 通道的指令。

### 2.1 方案原文（§6 照片删除）

```
① App 删除图 A
② IoT / 服务器删除云端图 A（OSS）+ 更新 path 列表
③ 标记「列表已变」
④ 择机下发 image_refresh（A 可能正在显示 / 用户主动刷新 → 立即下发；否则攒批）
⑤ 设备清空重拉 → 不再含 A
```

这条链路依赖三个假设，**协议原文一个都没有背书**：

| 假设 | 协议怎么写的 |
| :--- | :--- |
| A1：`image_refresh` = 清空 + **重拉** + 刷屏 | §2.15 标题「刷新图片」，说明只有一句「**通知设备清空 TF 卡内容**」。**没有**“重新拉图”“刷新显示”的字样 |
| A2：下发之后设备会执行并回执 | `image_refresh_ack` 只有 `action` / `msgid` / `stamac`——**没有 `data`、没有 `result`、没有 `ack_msgid`**（全协议独一份） |
| A3：需要时可以「立即下发」 | `wifimode` 默认 `mode=2` 定时通讯、`timingtime` 默认 240 分钟；设备不在线时下行去哪了，协议没写 |

### 2.2 硬伤 D1：删了云端，屏幕上那张还在（电子纸双稳态）

电子纸**断电也保持画面**。删掉云端文件、甚至清空 TF 卡，**都不会让屏幕变化**——
屏幕上的像素要变，必须**再刷一次图**，而刷一次要 **12~35 秒**（13.3 寸 12~30s / 10.1 寸 20~35s / 7.09 寸 25~35s）。

所以用户视角的“删除成功”= **换了一张图**，而方案里没有任何一步推新图。
正确的链路必须是「先决定拿什么替换 → `play` 下发替换图 → 屏幕刷新 → 再谈清缓存」。

### 2.3 硬伤 D2：TF 卡里的副本还在，而且实体按键能把它翻出来

- 走 §2.10 `strategy_bin` 时，设备会**把整份 `imgList` 下载到本地**（TF 卡）；
- 7.09 规格书写得很清楚：**「切图键：按一下 立即刷新下一张图（当前仅支持 TF 卡切图）」**。

也就是说：云端删了 A，只要 TF 卡里还有 A 的 bin，用户**按一下机身按键就把 A 翻出来了**。
这不是体验问题，是**隐私问题**（删掉的合影/证件照又出现在客厅相框上）。

### 2.4 硬伤 D3：`image_refresh` 清的是整张 TF 卡，**内置图会一起没**

协议 §2.14 `down_int_img` 下发的六张内置图（`FACTORY` 出厂页 / `SET` 设置页 / `NO_WIFI` 无 Wi-Fi 提示 /
`LOW_BATTORY` 低电量 / `LOW_POWER_OFF` 低电量关机 / `CONNECTED` 连接页）**也存在 TF 卡上**。
§2.13 `clean_tf` 专门分了 `ALL / LOCAL / OTHER` 三个范围，恰恰说明**内置图与用户图是分开的两类**。

而 `image_refresh` 的说明是「清空 TF 卡内容」，**没有范围参数**。于是：

> 用户删一张照片 → 平台下发 `image_refresh` → 设备把 TF 卡清空（含内置图）→
> 这时如果 Wi-Fi 断了，设备**连“无 Wi-Fi 提示页”都没有了**，屏幕上只剩上一张残留画面，
> 低电量提示、关机页同样消失。

**建议**：删图不要用 `image_refresh`，改用 `clean_tf` + 明确范围（`OTHER`）；
若必须用 `image_refresh`，平台**必须在其后补一次 `down_int_img`**，并把这条写进方案。

### 2.5 硬伤 D4：删除的时机，取决于设备什么时候醒

`wifimode`（§2.5）三种模式：`1` 实时通讯、`2` 定时通讯、`3` 休眠。
定时通讯的参数是 `timingtime`（**定时时间，60~1440 分钟，默认 240**）与
`live`（**唤醒后保持时间，60~65535 秒，默认 600**）。

| 模式 | 设备可达窗口 | 删除生效延迟 |
| :--- | :--- | :--- |
| 实时通讯（mode=1） | 常在线 | 秒级（但最耗电，见 §5） |
| 定时通讯（mode=2，默认） | 每 `timingtime` 分钟醒一次，醒 `live` 秒 | **默认平均 2 小时、最坏 4 小时；`timingtime` 拉到 1440 就是最坏 24 小时** |
| 休眠（mode=3） | 不可达 | 直到用户手动唤醒 |

另外 `strategy` 里还有 `idle`（**轮播后是否休眠**，0 休眠 / 1 不休眠）——轮播完就睡的设备，
“立即下发”窗口更窄。方案 §6 的「若 A 可能正在显示 → 立即下发」，在默认配置下**无法立即**。

还有一层：协议只写了 **MQTT v3.1.1 QoS1**，**没写会话是否持久（clean session）**。
设备离线时的下行是被 broker 丢掉、还是堆到下次连上一次性灌进来，直接决定：

- 丢掉 → 平台必须自己做「待办指令队列」，在设备上线（`login` / `heart` / MQTT connect）时补发；
- 堆积 → 设备一醒可能收到十几条历史 `play`/`image_refresh`，**要防重放**（`msgid` 去重 + 过期丢弃）。

**方案里这一段完全没有**，而它是所有“下发类”功能的地基，不止删图。

### 2.6 硬伤 D5：删空了显示什么，没有定义

协议 18 条 action 里**没有“清屏”“显示空白”**。删到列表为空时：

- 走 `strategy`（§2.9 单图拉取）：设备到点去 `path` 拉图，拉到空/404——协议没定义设备怎么处理；
- 走 `strategy_bin`（§2.10）：`imgList` 返回空数组，同上；
- 屏幕：仍然停留在最后一张（双稳态）。

**建议**：列表空时由平台主动下发 `down_int_img` 的 `FACTORY` 或一张“相册为空”的 bin，
把“空态”当成一张正常图去投，别指望设备自己处理。

### 2.7 一次删除的真实代价（规格书口径）

| 指标 | 13.3 寸 | 10.1 寸 | 7.09 寸 |
| :--- | :--- | :--- | :--- |
| 刷图时间 | 12~30s | 20~35s | 25~35s |
| 续航基准 | **一天刷新一次可续航 6 个月**（5000mAh） | 一天一次 3 个月 | 一天一次 6 个月 |
| 深睡 / 浅睡电流 | 62.35μA / 339.75μA | — | — |
| Wi-Fi 连接平均电流 | 2.4G 991μA，**5G 3.29mA** | — | — |
| 单次刷图峰值电流 | 874~897mA | — | — |

整机功耗预算是按**一天刷一次**算出来的。删一张图就「清空 TF + 重下整包 + 刷屏」
= 一次全量下载（Wi-Fi 长时间开着，5G 下平均电流是深睡的 50 倍）+ 一次刷屏。
用户连删 10 张，如果每次都触发一轮，等于**把半年续航按天烧**。

**所以“攒批”不是优化项，是必需项**；而攒批又和 D1 冲突（用户要立刻看到那张照片消失）。
唯一的解法是把两件事分开：**立刻换图（一次 `play`，只刷一屏）+ 择机清缓存（`clean_tf`，不刷屏）**。

### 2.8 建议的删除链路（按用户意图分三种）

先把“删除”拆清楚——现在 App 的「我的上传」列表里那个删除按钮，
在蓝牙版是**删设备槽位**（`frame_protocol.dart` CMD=0x12，12 字节掩码，
`gallery_page.dart` 的 `imgIndex` 就是槽位号）；Wi-Fi 版根本没有槽位，语义必须重新定义。

| 用户意图 | 建议实现 | 用到的 action |
| :--- | :--- | :--- |
| **① 从相框上撤下这张**（最常见） | 后端从该设备的图列表移除 → 若它**正在显示**：立即下发一次 `play`（替换图=下一张，列表空则内置图）→ 屏幕刷新一次；若不在显示：只改列表，等下次轮播自然跳过 | `play`（+ 可选 `strategy` 重下） |
| **② 从我的上传里彻底删除**（含云端文件） | ① 的全部 + 删 OSS 文件 + **择机** `clean_tf(OTHER)` 清设备缓存（可与下一次轮播合并，不单独刷屏） | `play` + `clean_tf` |
| **③ 清空相框** | `strategy_stop` 停轮播 → `clean_tf(ALL 或 OTHER)` → 下发内置图/空态图 → 一次刷屏 | `strategy_stop` + `clean_tf` + `down_int_img`/`play` |

时序（意图 ②，设备定时通讯模式）：

```
App 删除 A
  └─ 后端：图列表移除 A + 标记 A 待清理（OSS 文件先保留到设备确认清完，避免设备正在下载 A 而 404）
      ├─ 设备在线？
      │   ├─ 在  → 立即 play(替换图 B) ── play_ack(result) ──→ 记录“已换图”
      │   └─ 不在 → 进「待办指令队列」，等 login/heart/MQTT connect 触发补发（见 D4）
      └─ 下次设备醒来且非紧急时刻 → clean_tf(OTHER) ── clean_tf_ack(result) ──→ 删 OSS 文件
```

关键点三条：
1. **替换图先于清缓存**——用户看到的“删除成功”由 `play` 兑现，不由清缓存兑现；
2. **OSS 文件延后删**——设备可能正在下载该文件，先删会得到 104「下载文件失败」；
3. **清缓存不单独刷屏**——`clean_tf` 只清存储，避免额外一次 12~35s 刷图。

### 2.9 最小协议增补建议（按性价比排序，都要硬件配合）

| 优先级 | 增补 | 解决什么 |
| :--- | :--- | :--- |
| **P0** | `strategy_ack` / `play_ack` 的 `data` 里带上**当前显示图的 `imgid`** | 现在平台完全不知道设备在显示哪张（方案 §6 自己也承认），只能“猜着刷”。协议 §2.9 已经写了“每次更换图片时可以上报一条消息”，**加个字段即可**，改动最小、收益最大 |
| **P1** | `image_refresh` 补 `result` + `ack_msgid`；或**直接废弃它**，统一用 `clean_tf` | 现在这条指令下发完全无回执，平台无法记录成败 |
| **P2** | 按 `imgid` 删除单图：`clean_img { imgids: [...] }` | 免去“清空 + 重下整包”的功耗代价（§2.7） |
| **P3** | `clean_tf` 的 ack 里回一下清完的 `tfused` | 平台能自证清理生效，不必等下一次心跳 |

P0 拿到之后，方案 §6 的“无法精确判断，故按列表变更→择机刷新”这句话就可以删掉了。

## 3. 其它缺陷与对不上的地方

### P1 ⚠️ 投屏链路少了「图片转 bin」这一整步（严重）

方案 §3 写「① App 选图 → 图片已在 OSS（复用现有上传）… ④ 设备从 OSS 下载 → 显示」。
但协议 §2.8 `play` 的示例是 `"imgurl": "/ufile/hh7man.bin"`，§2.9 的 `path` 也是 `/a/a.bin`（§2.10 返回的 `imgList` 则是一串无扩展名的文件地址）——
**设备吃的是预处理好的 bin，不是原图 JPG**。

本仓现在的做法（蓝牙版）可以直接照搬到服务端，链路是现成的：
`projection_service` → `DitheringApi.requestFrameBin()`（`lib/src/network/dithering_api.dart`）
把**设备分辨率的图片** multipart 传给 seekink 的
`cloud.seekink.cn:8443/prod-api/api/v1/label/imageDitheringBinDownload`，
收回**六色 4bpp 的 .bin**，铁闸校验是「**字节数 = 宽 × 高 ÷ 2**」。

Wi-Fi 版要补的是：

1. **谁转**：App 不再碰图像字节 → 转换必须挪到服务端，且要拿 seekink 的 token（现在是 App 端
   用 `/Client/Basic/getXTYUserToken` 动态取，服务端要自己走一遍）；
2. **按设备转**：分辨率不是一个常数——按可视区域与像素密度反算，**10.1 是横屏 1600×1200，
   7.09 与 13.3 都是竖屏 1200×1600**（13.3 规格书那栏按“长边×短边”写，容易误读，详见 §8.3），
   还要叠加设备记录里的两个旋转角。**同一张原图对不同相框要转出不同的 bin**；
3. **存哪**：转出来的 bin 与原图分开存；`play` 下发的是 bin 的 `host/port/path`；
4. **什么时候转**：上传即转（占存储）还是投屏时转（首次投屏慢一拍），方案要选一个。

规格书里「软件 支持图片格式 JPG、BMP、PNG」这一行（13.3 与 10.1 有，7.09 那份没写）
更可能指的是**TF 卡直读**那条路（`play_tf`），
不能据此认为云端可以直接丢 JPG 给设备——这点 §7 待确认里要跟硬件钉死。

### P2 `play` 的 `host/port/path` 不是一个 OSS URL

协议给的是 `host`（域名或 IP）+ `port`（示例 9000 / 8080 / 443）+ `path`，**没有 scheme、没有签名参数**。
这意味着：

- **私有 OSS 不行**：带 `Signature`/`token` 查询串的地址塞不进这个结构（除非整串塞进 `path`，要硬件确认能不能接受长 query）；
- **协议用的是什么**：状态码表里有「**获取 FTP 服务器失败(102)**」，示例端口又出现 9000（常见于 MinIO）与 443，
  到底是 FTP、HTTP 还是 HTTPS，**必须问硬件**（这条与另一份文档的待确认 30 是同一件事）；
- 若设备只支持明文 HTTP，还要评估图片内容**在公网明文传输**的合规问题（相册是私人照片）。

### P3 绑定只存关系，但协议有 `device_config`（uid/deviceId/batchKey）没人用

方案 §2 写「绑定：IoT 存『用户-设备』关系；解绑：删关系，**不下发设备指令**」。
但协议 §2.7 有一条 `device_config`，下发的正是 `batchkey` / `deviceId` / `uid`。

两种可能，方案必须选一个并写清楚：

- 如果设备拉图时要带 `uid`/`deviceId` 去认人（`strategy` 的 `path` 是“拉该设备的图列表”），
  那么**绑定时必须下发 `device_config`**，否则换绑之后设备还在拉旧用户的图；
- 如果 `path` 里已经带了设备标识（后端按 `stamac` 分配），那 `device_config` 属于基站产品线的遗留字段，
  应在方案里明确“不使用”，免得后面有人照着协议实现一遍。

### P4 解绑不下发指令 → 残留与隐私

接 P3。解绑只删平台关系的话，设备侧会保留：**MQTT 配置**（继续连平台）、
**当前生效的 `strategy`**（继续按时去拉图）、**TF 卡里的全部照片**（按键还能翻）。
结果是：设备被转手/退货后，**上一位用户的照片还在相框里**，而且设备还在往平台发心跳。

**建议**解绑至少三步：`strategy_stop` → `clean_tf(ALL)` → `down_int_img`（恢复出厂页），
并在平台侧把该 `clientid` 的下行置为拒绝。规格书里 RESET 键“恢复出厂设置”是本地动作，
**不能指望用户去按**。

### P5 在线判定：`login` 只上报一次，心跳周期协议没定义

- §2.1 原文：「**APP 扫码设备配网成功后，上报一次数据**」——`login` 是**配网后一次性**的，
  **不是每次重连都发**。方案 §1 步骤⑥「IoT 记录设备上线」若只挂在 `login` 上，重连就漏了；
- **心跳周期协议通篇没有定义**，方案 §12 的「心跳超时判定在线」缺一个数；
- 而且判定必须**按 `wifimode` 分档**：定时通讯模式下设备 4 小时不说话是正常的，
  用一套固定超时会把正常设备判成离线（App 上就是“设备全部离线”的投诉）。

**建议**：在线 = MQTT 连接事件为准（broker 的 connect/disconnect），
心跳只用来更新影子；App 侧显示「**电量 86%（4 小时前）**」这种带时间戳的口径。

### P6 状态码：示例里的 `result: 1` 不在码表里

协议末尾《状态码定义表》只有 **100~118 与 255**（100 收到需 ack、101 FLASH 地址失败、
102 FTP 失败、103 文件大小失败、104 下载失败、105 添加设备列表失败、106 指令添加成功、
107 下载图片或文件成功、109/110/112/113/114/115~118、255 下载成功），
**没有 0，也没有 1**——但全协议所有 `*_ack` 示例写的都是 `"result": 1`。
（BluFi 那侧又是另一套：`0=成功，非0=错误码`，与 MQTT 侧**方向相反**。）

平台不能“非 0 即失败”或“1 即成功”地实现。**方案必须定义成功集合**，建议：
成功 = `{100, 106, 107, 113, 255}`，失败 = `{101,102,103,104,105,109,110,112,114,115,116,117,118}`，
其余未知码一律按失败记录并原样透传给 App（便于现场定位）。

### P7 `wifi_sleep` 的字段在协议里自相矛盾

§2.6 的字段表写的是 `mode` / `live` / `timingtime`（类型标 `int`，描述却是
`yyyy-MM-dd HH:mm` 或 `HH:mm` 的**时间字符串**），
而紧挨着的**示例**写的是 `"action": "wifimode"`（抄错了）+ `beginTime` / `endTime` 两个字段。
方案 §8 只写了「开始/截止时间（UTC）」，等于把这个矛盾留给了实现者。

**必须问硬件**：到底是 `live`/`timingtime` 还是 `beginTime`/`endTime`；类型是字符串还是时间戳。
顺带两处大小写不一致也一并确认：`timingtime` vs 示例的 `timingTime`；
`batchkey` vs 示例的 `batchKey`；以及 `wifimode_ack` 里 `0x03` 被写成“**停机模式**”而下行表写的是“休眠模式”。

### P8 时区与时钟：设备的时间从哪来，协议没说

`wifi_sleep` 明确「App 保存本地时间，下发时统一转 UTC」，
而 `strategy` 的 `updatetimelist`（`["11:00","15:00"]`）、`begintime`/`endtime` **没写时区**。
两者若一个 UTC 一个本地，设备上就是“说好 11 点换图、实际 19 点换”。
而且协议里**没有任何校时指令**（这点与另一份文档 §2 的结论一致），
设备只能靠自己 SNTP；休眠期间没网，RTC 漂移谁来纠正也没写。

**建议**：全部统一成 UTC 下发 + App 侧按设备所在时区展示，并把“设备如何校时”列为硬件确认项。

### P9 `strategy` 与 `strategy_bin` 是两种删除语义，方案没选

| | §2.9 `strategy` | §2.10 `strategy_bin` |
| :--- | :--- | :--- |
| 设备拿到什么 | `path` = **拉图路径**，到点去拉**一张** | `path` = **查所有图片地址**，拿回整份 `imgList` |
| 删一张图的生效方式 | 后端改列表即可，下次拉图自然不含 A | 设备本地已有整包，**必须清缓存或重下列表** |
| 本地缓存 | 少 | 多（整包在 TF 卡） |
| 备注 | — | §2.10 的**字段表里 action 写的还是 `strategy`**，只有示例写 `strategy_bin`，需确认 |

**删除方案的难度完全取决于选哪一种**——方案 §4 只写了 `strategy`，§6 的删除却按“列表变更 + 清 TF”来写，
更像 `strategy_bin` 的世界。这一条必须先定，否则 §6 永远对不齐。

### P10 图源切换缺回路：没有“停止 TF 播放”这条指令

方案 §7 写「切到 TF：下发 `play_tf`；切回 APP：下发 `play`/`strategy`」。协议里：

- `play_tf`（§2.12）**零参数**，回执也只有 `result`；
- **没有 `play_tf_stop`**；`strategy_stop` 按原文只对应“播放策略/播放策略+Bin”，对 TF 播放是否生效未定义；
- `play_tf` 之后设备处于什么状态（播一张就停？轮播卡内图？与正在生效的 `strategy` 谁优先？）**协议没写**。

方案自己也说「IoT 需记录设备当前图源，避免状态错乱」——但**平台记的是自己发过什么，不是设备实际在放什么**。
两者一旦不一致（用户按了机身切图键、或设备重启），没有任何指令能读回来。这条建议：
要么等硬件把状态补进心跳，要么 App 上不要做“图源开关”这种**双向状态控件**，只做“播放 TF 卡内容”这种**单向动作**。

### P11 六条 action 在方案里没有归属

`clean_tf`（§2.13）、`down_int_img`（§2.14）、`country`（§2.16）、`shutdown`（§2.17，上行）、
`device_config`（§2.7）、`strategy_bin`（§2.10）——方案 13 节里一次都没出现。
其中前两条正是删除/异常提示的关键（见 §2.4、§2.6），`shutdown` 是 App 上“设备已关机”的唯一依据，
`country` 与 BluFi 的 `wifi_set_country_code` 是两条不同的通道（配网时一条、运行时一条），也要说清谁在什么时候发。

### P12 固件升级：方案 §9 与协议一致，补两条

`ota`/`fpga` 报文逐字段相同、都由设备自己下载、**只有成功/失败没有进度**——这几句都对
（详见 `WIFI_FRAME_FEATURE_GAP_AND_DETAIL_PAGE.md` §9.2）。要补的是：

1. **成功判据**：`ota_ack` 的 `result` 只代表“下载/执行”这一步，
   真正的成功要看心跳里的 `version` / `fpga_ver` 变没变——平台要落库心跳版本号并给 App 查询接口；
2. **两条固件线各比各的**：后台固件表要加「固件类型（ESP / FPGA）」维度，否则版本比对会串。

### P13 影子的新鲜度要显式暴露给 App

方案 §10 说设备信息“数据来源心跳、无需额外下发”——对，但定时通讯模式下这份数据**可能是 4 小时甚至 24 小时前的**。
App 上的电量、TF 容量、Wi-Fi 信号都要带“更新于 X”，否则用户会拿着 100% 的电量图标问为什么设备不动。
另外 `orientation` 字段协议标注「**当前取不到预留**」，App 不要读它。

### P14 规格书与协议在“支持格式”上口径不同

规格书（13.3、10.1）：**软件 支持图片格式 JPG、BMP、PNG**；协议：`play`/`strategy` 的示例全是 `.bin`。
合理解释是“TF 卡直读支持 JPG/BMP/PNG，云端下发走预处理好的 bin”，但**这只是推断**。
如果硬件确认云端也能直吃 JPG，那 P1 那一大段服务端转码就可以省掉——**这是本次评审里性价比最高的一个问题**，建议优先问。

## 8. 回应平台侧的三点澄清（2026-09-20 二稿）

> 平台侧原话：「TF 卡和 APP 是 2 个通道，要结合规格书看——可以单独接一个 TF 卡去播放卡里的内容，
> 或者 APP 下发 bin 地址让设备去下载；也就是说 **APP 上传投屏的图片不在设备存储**。
> 3 个规格书除了方形尺寸不一样其他都一样。**立即下发无法实现吗？**」

### 8.1 两个通道：接受，并撤回一稿里的两条推断

这个模型与协议自洽，也解释了为什么 `clean_tf` 要分 `LOCAL`(内置) / `OTHER`(其他) 而没有「App 图」这一类：

| 通道 | 内容从哪来 | 设备上怎么存 | 相关 action |
| :--- | :--- | :--- | :--- |
| **TF 通道** | 用户自己插卡拷进去的文件；平台下发的内置图 | **存在 TF 卡上** | `play_tf`、`clean_tf`、`down_int_img`、`image_refresh`、7.09 的切图键 |
| **App 通道** | 平台下发 bin 地址，设备**按需下载**并显示 | **不落盘保留**（只有一张在渲染） | `play`、`strategy`、`strategy_bin`、`strategy_stop` |

**据此撤回一稿的两条**（都是我按"缓存会落在 TF 卡"推的，协议原文并没有这么写）：

- ~~D2：`strategy_bin` 把整包 bin 下到 TF，7.09 切图键能把已删照片翻出来~~
  → **不成立**。`strategy_bin` 下发的是**图片地址列表**，设备存的是列表、按需下载；
  切图键既然「仅支持 TF 卡切图」，就翻不出 App 通道的图。
  **只剩一条边界要跟产品讲清**：用户**自己拷进 TF 卡**的照片，云端删除管不着，只能靠 `clean_tf(OTHER)` 或拔卡。
- ~~D3：删一张图触发 `image_refresh`，会把内置图一起清掉~~
  → 对 App 通道**不该发生**，因为删 App 通道的图压根不需要碰 TF。
  这条转为对方案 §6 的另一种批评（更强）：**它用错了通道**——见 8.1.1。

#### 8.1.1 反过来说，删除链路其实比方案写的**简单得多**

既然 App 投的图不在设备上，删除就只剩两件事：

```
① 服务端把图 A 从该设备的图列表里移除          ← 下次 strategy 拉图自然不含 A，无需任何"清理"指令
② 若 A 正显示在屏幕上 → 下发一次 play(替换图)  ← 唯一需要下发的东西；屏幕刷新 12~35s 后 A 消失
```

**方案 §6 的 `image_refresh` 整步可以删掉**：它属于 TF 通道（协议原文「通知设备清空 TF 卡内容」），
对 App 通道的图既没用、还会顺手清掉内置图（出厂页 / 无 Wi-Fi 提示 / 低电量页）。
删除流程里不该出现它，也不该出现 `clean_tf`。

**一稿里仍然成立、且现在成了全部重点的四条**：

1. **D1 电子纸不刷屏就不变**：删掉云端记录 ≠ 屏幕上那张消失。**删除必须带一次"替换图"的 `play`**，
   这是方案 §6 从头到尾没有的一步，也是用户投诉"删了还在"的唯一原因。
2. **平台不知道设备正在显示哪张**，所以判断不了"要不要推替换图"。方案自己也承认这点。
   → 最小增补仍然是：**`strategy_ack` / `play_ack` 带上当前显示图的 `imgid`**（协议已经写了
   "每次更换图片时可以上报一条消息"，加个字段即可）。拿到它，删除就能做到"精确、且只在必要时刷一次屏"。
3. **`image_refresh_ack` 没有 `result`、没有 `ack_msgid`**（全协议唯一）。这条指令若还要保留给"刷新屏幕"
   功能用，回执得补齐；否则平台下发完无法判断成败。
4. **删空了显示什么没定义**：列表被删空时，`strategy` 拉到空列表设备怎么办协议没写；
   屏幕会停在最后一张。建议平台主动投一张"相册为空"的 bin，或下发 `down_int_img` 的 `FACTORY`。

#### 8.1.2 两通道模型带出的新问题（要请硬件确认）

- **A19**：App 通道的图既然不落盘，**断电/重启后还能不能重绘当前这张**？（电子纸会保持画面，
  但用户按一下切图键、或设备重启后需要重画时，是否必须重新联网下载？没网会发生什么？）
- **A20**：轮播时**每换一张都要联网下载一张 bin**（1200×1600 六色 4bpp ≈ **0.92MB**）。
  在定时通讯/休眠模式下，这意味着每次换图都要唤醒 Wi-Fi。**轮播的最小间隔/每天上限**是多少？
- **A21**：**没插 TF 卡的设备**（三份规格书都写"支持 TF 卡"，但卡未必随机附带），

  App 侧的"清空 TF 卡"按钮要按"有没有卡"（心跳 `tf` 字段）置灰。
- **A22**：`strategy_bin` 的 `imgList` 拿回来后，**设备把列表存在哪**（RAM / FLASH / TF）？

### 8.2 「立即下发无法实现吗？」——**能实现。我一稿这句话说重了，这里给准确口径**

一稿写的是"默认配置下立即下发不成立"，这句话把**默认参数**说成了**能力上限**，不对。准确的是：

| `wifimode` | 设备可达性 | 下发到生效 | 续航（按规格书电气参数反推，5000mAh × 3.85V = 19,250mWh） |
| :--- | :--- | :--- | :--- |
| **1 实时通讯** | 常在线 | **秒级下发** + 12~35s 刷屏 | **2.4GHz：4.59mWh/h → 约 4194h ≈ 175 天 ≈ 5.7 个月**（10.1 为 5.31mWh/h ≈ 5 个月） |
| | | | ⚠️ **5GHz：18.89mWh/h → 约 1019h ≈ 42 天**（10.1 为 8.3mWh/h ≈ 96 天） |
| 2 定时通讯（`timingtime` 60~1440 分钟，默认 240；`live` 默认 600 秒） | 每 `timingtime` 醒一次，醒 `live` 秒 | 平均半个周期，默认约 2 小时，最坏 24 小时 | 最省 |
| 3 休眠 | 不可达 | 到用户唤醒为止 | 深睡 62.35μA ≈ 0.24mWh/h |

**关键的一条反推**：规格书标称的「一天刷新一次可续航 6 个月」，用电气参数对一下就知道它**本来就是
"常连 2.4G Wi-Fi"这个工作点算出来的**——
2.4G 连接平均电流 991μA ≈ 3.82mWh/h，加上每天一次刷图（875mA × 3.85V × 30s ≈ 28mWh，摊到每小时 ≈ 1.17mWh/h），
合计 ≈ 4.99mWh/h，与规格书写的 4.59mWh/h 同量级；而若设备真的整天深睡（0.24mWh/h），续航会是**9 年**而不是 6 个月。

**所以结论反过来**：**实时通讯 + 立即下发，正是规格书标称续航对应的工作方式，不是奢侈选项。**
真正要避开的是**常连 5GHz**（42 天），这一点要写进配网逻辑——BluFi 配网时**优先让设备连 2.4G**。
（⚠️ 规格书没有定义"工作状态"的占空比，以上是反推，请硬件确认一句。→ **A23**）

还要一起定的三件事：

1. **"立即"对用户意味着两段**：下发秒级，但**刷屏 12~35s**。App 上不能做成"点完就变"，
   要有明确的"正在更新（约 30 秒）"状态；
2. **模式是产品决策，不是技术限制**：如果为了续航把设备放进定时通讯，那么"删除/投屏立即生效"
   就要在 App 文案上改成"将在设备下次联网时更新"。**同一套接口，两种承诺，必须先选**；
3. **临时掉线仍要补发**：断电、搬动、路由重启期间的下行，协议只写了 QoS1，**没写 broker 会话是否持久**。
   要么平台做待办指令队列（设备上线时补发 + `msgid` 去重），要么确认 broker 会为离线设备保留消息。→ **A24**

### 8.3 「3 个规格书除了尺寸不一样其他都一样」——功能项是一样，但有四处会影响实现

功能栏确实一致：都是 Spectra6 六色、都支持 TF 卡、都双频 Wi-Fi 6 + BLE 5.0、都 5000mAh、
刷图方式都是「TF 卡刷图 / APP 刷图」。**但下面四处不一样，而且每一处都落在实现上**：

| 项 | 7.09 | 10.1 | 13.3 |
| :--- | :--- | :--- | :--- |
| 可视区域 | 108(H) × 144(V) mm | 203.2(H) × 152.4(V) mm | 202.8 × 270.4 mm |
| 分辨率（规格书原文） | 1200×1600 | 1600×1200 | 1600×1200 |
| 像素密度 | 282 PPI | 200 PPI | 150 DPI |
| **按可视区域 + 密度反算的真实取向** | **竖**（108mm→1200px，144mm→1600px） | **横**（203.2mm→1600px，152.4mm→1200px） | **竖**（202.8mm→1200px，270.4mm→1600px） |
| 刷图时间 | 25~35s | 20~35s | 12~30s |
| 续航（一天一刷） | 6 个月 | **3 个月** | 6 个月 |
| 单次刷图峰值电流(2.4G) | 874.59mA | **1576.95mA** | 874.59mA |
| 切图键 | **有**（立即刷新下一张，仅 TF 卡切图） | 无 | 无 |
| 「软件 支持图片格式 JPG/BMP/PNG」这一行 | 无 | 有 | 有 |

也就是说：**13.3 那份的"分辨率 1600×1200"是按「长边×短边」写的**（用 150DPI 反算：
270.4mm 对应 1600px、202.8mm 对应 1200px），它和 7.09 一样是竖屏；
真正横过来的是 10.1。**这正是"转 bin 不能按机型名硬编码"的理由**——
一稿把 13.3 归到横屏那一组，也是被这一行误导的，这里一并更正。

**好消息是这套逻辑本仓早就有了，可以直接搬到服务端**：App 与小程序都不按机型写死，
而是按**后端设备记录里的每台设备字段**来转：

- 分辨率：`state.dart` 里 `screenWidth` / `screenHeight` ← 后端 `width` / `height`；
- 旋转：**两个不同字段** `verticalRotation`（竖向构图导出角）与 `rotationDegree`（横向构图导出角），
  互不通用（`cast_image_editor.dart` 里有"角度取设备字段、错了必然花屏"的注释）；
- 转换：`lib/src/network/dithering_api.dart` / 小程序 `utils/dithering.js` → seekink
  `imageDitheringBinDownload`，收回六色 4bpp bin，铁闸是**字节数 = 宽 × 高 ÷ 2**。

平台侧自己那句「APP 下发 bin 地址让设备去下载」，也正好确认了一稿 §3 P1 的结论：
**bin 得有人转**。Wi-Fi 版里 App 不碰图像字节，这一步就必须挪到服务端，
并且按**每台设备**的 width / height / 两个旋转角来转，而不是按型号。

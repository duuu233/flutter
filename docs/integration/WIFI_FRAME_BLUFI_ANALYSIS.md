## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 协议第五点（附件一）的蓝牙那条，能不能和我们现在的「搜索」合并？ | **扫描和列表这一层可以合并**，一条扫描、一个列表同时列出现有 BLE 相框和 Wi-Fi 版；**连接之后不能合并**——两者是两套 GATT 服务、两套会话协议、两条完全不同的后续动线，必须在「用户点了哪一行」之后就分叉 |
| Wi-Fi 版配网能不能实现 | 能。BluFi 是乐鑫公开协议，两端都有官方实现可桥接，纯 Dart 实现也做得出来；**前提是先确定固件用的是哪种安全模式**（见 §4.2） |
| 最大的风险在哪 | **不在配网**。在于 Wi-Fi 版把「图片变成设备能显示的 `.bin`」这件事整个搬到了服务端，而我们现在是**端上**做的（`image_codec.dart`），这块四份文档一个字都没写（§5.1） |

## 1. 这批文档讲了什么

### 1.1 三款硬件（三份规格书）

| | 7.09 寸 | 10.1 寸（内胆） | 13.3 寸（模块化） |
| --- | --- | --- | --- |
| 分辨率 | 1200×1600（竖） | 1600×1200（横） | 1600×1200 |
| 屏 | 电子纸 Spectra6，六色（红黄蓝白绿黑） | 同左 | 同左 |
| Wi-Fi | **2.4 & 5 GHz 双频 Wi-Fi 6 (802.11ax)** | 同左 | 同左 |
| 蓝牙 | **BLE 5.0** | 同左 | 同左 |
| TF 卡 | 支持 | 支持 | 支持 |
| 刷图 | 20–35 s，方式：TF 卡刷图 / **APP 刷图** | 同左 | 同左 |
| 电池 | 5000 mAh | 5000 mAh | 5000 mAh |
| 按键 | BUTTON（开关机 / 配网 / 查状态）+ RESET（恢复出厂） | 同左 | 同左 |

🔶 **推断（未经证实）**：「双频 Wi-Fi 6 + BLE 5.0」这组合在乐鑫产品线里指向 **ESP32-C5**，
而协议文档通篇写的是「ESP32 设备」。芯片型号影响的是 BluFi 版本与安全模式的默认值，
需要向硬件方确认（§6）。

**配网相关的硬件行为**（三份规格书一致，这一条对 App 的交互设计很重要）：

- **首次开机或按 RESET 后开机，直接进入配网模式**；
- BUTTON **双击（2 秒内）**手动重进配网模式；配网模式下双击退出；
- 蓝灯闪（亮 3 灭 3）= 配网模式；成功后蓝灯常亮 30 秒熄灭；
- **失败：首次配网指示灯持续 10 分钟（状态和页面持续 20 分钟），二次配网只持续 3 分钟**；
- 橙灯慢闪 30s = 配网失败 / 网络错误；橙灯快闪 15s = 有 AP 无网络或没搜到 AP；
- **绿+蓝交替慢闪 = 密码错误；连续 5 次密码错误直接关闭配网模式**。

### 1.2 通讯协议 V1.3.1 的骨架

两条完全独立的通道：

1. **设备 ↔ 服务器：MQTT v3.1.1，QoS 1**
   - 上行 `/device/report/{clientid}`，下行 `/inkjoyap/{clientid}`；
   - `clientid` = MAC 去分隔符大写（示例 `A61F5AE3A12D`）。
2. **手机 App ↔ 设备：只有配网阶段**，走 **BluFi 自定义消息**（JSON / UTF-8）。
   文档原话：「定义了手机 App 与 ESP32 设备在蓝牙连接阶段（**目前只有配网阶段**）的
   Blufi 自定义消息格式」。

MQTT 指令全集（都带 `action` / `msgid` / `stamac`，`*_ack` 回执带 `result` + `ack_msgid`）：

| 方向 | action | 作用 |
| --- | --- | --- |
| 上 | `login` | 配网成功后上报一次（带 `ver` / `statype`） |
| 上 | `heart` | 心跳：`wifi/ble/tf/tfsize/tfused/orientation/battery/wifi_rssi/wifi_name/ble_rssi/version/country_code/fpga_ver` |
| 下 | `ota` / `fpga` | 给 host/port/path 让设备自己去下载升级包 |
| 下 | `wifimode` | 实时 / 定时 / 休眠三种通讯模式 + 唤醒保持时间 |
| 下 | `wifi_sleep` | 定时休眠（一次性 / 周期，**App 存本地时间、下发转 UTC**） |
| 下 | `device_config` | `batchKey` / `deviceId` / `uid` —— **设备与用户的绑定关系** |
| 下 | `play` | 播放单图：host/port + `imgs[{imgid, imgurl}]` |
| 下 | `strategy` | 播放策略：顺序/随机、固定时间或间隔时间、轮播后是否休眠 |
| 下 | `strategy_bin` | 策略 + 图片清单（设备本地按策略挑图） |
| 下 | `strategy_stop` | 暂停轮播 |
| 下 | `play_tf` / `clean_tf` | 播放 / 清空 TF 卡内容 |
| 下 | `down_int_img` | 下载内置图（出厂页/设置页/无 Wi-Fi/低电量/关机/已连接六张） |
| 下 | `image_refresh` / `country` | 刷新图片 / 国家码变更 |
| 上 | `shutdown` / `uptag` | 关机通知 / **蓝牙标签上报** |

⚠️ **这份协议不是相框专用的**：`statype` 取值是「1 LINUX 基站 / 2 Wi-Fi 基站 /
3 基站+标签一体机 / 4 PC 基站(USB)」，还有 `uptag`（蓝牙标签上报）和「文件发送到蓝牙主机失败」
这类状态码——它是 XT 那套**基站/电子标签**家族协议，相框只是其中一种形态。
落地时要挑着实现，别把标签那半当成相框要做的事。

## 2. 第五点（附件一）到底是什么

文档第 5 节「附件一．设备修改服务器通讯参数」给了**两条**改服务器参数的路子：

**方法一（Wi-Fi AP + 网页）**
设备进配网模式后自建热点 `XT_ESP_` + MAC 后 4 位，密码固定 `1234567890`；
连上以后浏览器开 `192.168.4.1`，网页上改 Server IP / Server Port / User / Password，
点 SET 保存，Sys Reset 里点 RESET 重启。

**方法二（BLE + BluFi）← 用户问的这条**

- **BLE 设备名 `IJ_(MAC地址)`**；
- 通过 **BluFi 协议的自定义数据帧**发 JSON 配置：

```json
{ "msgid": "1756108400173", "action": "mqtt_config",
  "data": { "host": "192.168.1.1", "port": 1883, "usr": "device", "pwd": "1234567890ab" } }
```

- ⚠️ **固件版本门槛**：V0.1.1 及以上才支持；**V0.2.7 起 `broker` 字段改名 `host`**；
- 另有 `wifi_set_country_code`（国家码，影响信道范围与发射功率），回执可能带
  `pending: 1`，文档明说 **`pending` 的优先级高于 `result`**；
- 回执 action 一律是「原 action + `_ack`」，`data.result` 0 成功、非 0 错误码，
  `data.ack_msgid` 回带请求的 `msgid`。

**⚠️ 文档只写了"自定义消息"那一层，没写标准 BluFi 那一层。**
真正的配网（协商密钥 → 下发 SSID → 下发密码 → 令设备连 AP → 读取连接状态）是
BluFi 自己的帧类型，得照乐鑫官方文档实现。文档给的基线是：

- 实现以**乐鑫官方 BluFi demo** 为准（`bluetooth/blufi`）；
- 参考 App 是 **EspBlufi for Android / iOS**；
- BluFi 数据帧（分片）最大支持 **64 KB** 的数据内容。

## 3. 能不能跟我们现在的「搜索」合并

### 3.1 我们现在的搜索是怎么工作的（代码事实）

`DeviceBle.scan()`（`lib/src/device/ble/device_ble.dart`）：

- 用 `flutter_blue_plus`，**不按 service UUID 过滤**（真机广播不一定带 FF00，过滤会漏设备）；
- 放行规则两条，命中任一即列出：
  1. 广播名（`platformName` + `advName`，大写后 **contains**）命中白名单；
  2. 厂商数据像相框（`_looksLikeFrame`：Company_ID `0xFFFF` + 合法 Screen_Type + 电量 ≤ 100）；
- 白名单来自**后端产品列表的 `broadcastId`**（`BoltFoxApi.getProductBroadcastIds`），
  端上兜底常量只有 `EF6-370` / `EF6-589`；
- 选中之后连接时**必须发现 FF00 主服务下的 FF01(写)/FF02(通知)**，否则直接报
  「未找到相框主服务(FF00)或读写特征(FF01/FF02)，请确认是相框设备」。

### 3.2 新设备落在这套规则里是什么样

| 层次 | 现有 BLE 相框 | Wi-Fi 版（BluFi） | 能否合并 |
| --- | --- | --- | --- |
| 扫描 | 一轮 FBP 扫描，无 UUID 过滤 | 同一轮扫描就能收到 | ✅ **本来就在一起** |
| 列表放行 | 名字含 `EF6-370` 等 / 厂商数据像相框 | 名字 `IJ_<MAC>` | ✅ 加一条名字规则即可 |
| 列表展示 | 名称 + 信号 + 电量/屏型（来自厂商数据） | 只有名字和信号（**厂商数据格式未知**） | ⚠️ 同一个列表里两种信息量，见 §3.4 |
| 点击之后 | 连 FF00 → 绑定 → 端上传图 | 连 **BluFi 服务** → 配网 → 设备自己上云 | ❌ **必须分叉** |
| 会话协议 | 自研帧协议（`frame_protocol.dart`） | BluFi 帧 + JSON 自定义消息 | ❌ 两套 |
| 设备归属 | 端上绑定 | 服务端 `device_config` 下发 `uid` | ❌ 两套 |

**结论：搜索这一层合并没有技术障碍，分叉点在「点了哪一行之后」。**

### 3.3 合并要注意的三件事

1. **放行规则最好由后端下发，端上零改动。**
   白名单本来就是产品列表的 `broadcastId`。只要后端把 Wi-Fi 版产品的 `broadcastId`
   配成 `IJ_`，现有 App **一行代码不改**就能把它列出来。
   ⚠️ 但**端上仍然得认得出"这一行是 Wi-Fi 版"**（要走另一条动线），所以还是要有一条
   端上的判别规则，不能纯靠后端。

2. **别用 contains 匹配 `IJ`。**
   现在的匹配是「大写后 contains」，`IJ` 两个字母太短，周围任何名字里带 IJ 的蓝牙设备都会被
   放进来。判别用 **`IJ_` 前缀**（`startsWith`），或者更稳的：**广播里带 BluFi 的
   service UUID**。
   🔶 BluFi 的 GATT 是 service `0xFFFF` / 写 `0xFF01` / 通知 `0xFF02`（**来自乐鑫公开文档，
   不是本批 PDF**，需真机抓包确认）。注意它和我们现在的 FF00 服务**不冲突**：
   特征短码虽然都叫 FF01/FF02，但我们的 `_findCharacteristics` 是先匹配服务 FF00 再找特征的。
   ⚠️ 另注意 `_looksLikeFrame` 认的 `0xFFFF` 是**厂商数据里的 Company ID**，
   与 BluFi 的 service UUID 0xFFFF 是两个字段，不会互相误判。

3. **分叉点放在「连接之前」，不要放在连接之后。**
   连上去再发现没有 FF00，现在的代码会报「请确认是相框设备」——用户看到的是一句
   与事实不符的话。应当在扫描结果上就分流：`IJ_` 前缀（或 BluFi service UUID）→ 走配网页；
   其余 → 走现有绑定流程。列表行上给 Wi-Fi 版打一个「Wi-Fi 版 · 需要配网」的角标，
   否则两种设备长得一样、点下去却是两条路，用户会懵。

### 3.4 另一个更省事的方案（给产品选）

**不合并搜索**：在「添加设备」入口先让用户选产品类型（现有相框 / Wi-Fi 版相框），
再进各自的搜索页。

- 代价：多一步点击；
- 收益：两条动线互不污染——列表文案、空态提示、失败提示、重试策略都能各说各的；
  现有那套被反复调过的搜索逻辑（起扫频率账本、弱信号追溯放行、厂商数据兜底）
  一行都不用动。

考虑到现有搜索页为了「搜不到设备」这件事做过多轮优化，**如果 Wi-Fi 版的广播结构
与现有相框差别较大（尤其是没有我们那套厂商数据），建议先走方案 B（分开），
等真机数据摸清楚再谈合并。**

## 4. BluFi 配网的实现路径

### 4.1 要做的事（按顺序）

1. 扫描到 `IJ_xxxx` → 连接 → 发现 BluFi 服务、开通知、协商 MTU；
2. （可选）**安全协商**：DH 交换密钥，之后数据 AES-128-CFB 加密 + CRC16 校验；
3. 下发 **SSID** 与 **密码**（BluFi 标准帧）；
4. 下发自定义 JSON：`mqtt_config`（host/port/usr/pwd），必要时 `wifi_set_country_code`；
5. 令设备连 AP，读回连接状态（BluFi 标准帧：Wi-Fi 连接状态报告）；
6. 设备连上 → MQTT `login` 上报 → **服务端**把设备绑到用户（`device_config`）；
7. App 侧从后端确认「这台已经归我了」，结束配网。

### 4.2 两条实现路线

| | A：纯 Dart 在 flutter_blue_plus 上实现 BluFi | B：桥接乐鑫原生 SDK |
| --- | --- | --- |
| 做法 | 自己写帧格式、分片、CRC16、AES-128-CFB、DH | Android 引 EspBlufi 的 blufi 库、iOS 引 EspBlufiSDK，各写一层 MethodChannel |
| 工作量 | **关掉安全协商**的话：帧 + 分片 + 自定义 JSON，量不大；要 DH+AES 则明显变重 | 两端各一套桥接 + 两端各自的回调编排 |
| 风险 | DH 2048 位在 Dart 里做 `modPow` 有性能与兼容风险；协议细节踩坑靠自测 | 与官方实现一致，踩坑少；但多两份原生依赖、两端行为要各自验 |
| 复用现有能力 | ✅ 直接复用本仓已经调熟的连接/重连/MTU/权限那一套 | ❌ 原生 SDK 自己管连接，与我们现有 BLE 会话并存要小心（同一台设备两条连接） |
| 维护 | 全在 Dart，一处改两端生效 | 升级 SDK 要动两端原生工程 |

**建议**：先问硬件方一个问题——**固件的 BluFi 是否要求安全协商**（`esp_blufi_security` 是否启用）。

- 若可以**关掉**（或支持不加密模式）：走 **A**，BluFi 退化成「按格式拼帧 + 分片」，
  再叠上文档里那几条 JSON 就完事，且能完全复用我们现有的 BLE 连接层；
- 若**必须加密**：走 **B** 更稳妥，别为了省两个原生依赖去手搓 DH + AES-CFB。

## 5. 风险清单（按严重度排序）

### 5.1 🔴 内容链路整个换了，而且文档没写

我们现在的模型是：**手机**把图片抖动/编码成设备能吃的位图（`lib/src/device/ble/image_codec.dart`），
再经 BLE 传给相框。Wi-Fi 版是：**服务端**把 `.bin` 放在某个 host/port/path，
`play` / `strategy_bin` 只下发 URL，设备自己去拉。

- **谁来生成 `.bin`？** 四份 PDF 只字未提。如果要服务端做，就得把我们端上那套
  编码（含 Spectra6 六色抖动、屏型、方向、CRC）搬过去并保持逐像素一致；
- 规格书写着「支持图片格式 JPG、BMP、PNG」「刷图方式：TF 卡刷图、**APP 刷图**」，
  与协议里「设备下载 `.bin`」对不上——**「APP 刷图」到底是哪条路径必须问清楚**；
- 这是整件事里**工作量和不确定性最大**的一块，比配网大得多。

### 5.2 🔴 设备归属 / 绑定流程缺口

`device_config` 带 `batchKey` / `deviceId` / `uid` 是**服务端下发给设备**的，
而 App 怎么"认领"一台刚配好网的设备，文档里没有。
唯一的线索是 `login` 那句「**APP 扫码设备配网成功后**上报一次数据」——暗示有二维码
（设备上贴的 DeviceId/SN）。这条链路（扫码 → 后端建绑定 → 下发 device_config）
**需要后端给接口**，端上才有得做。

### 5.3 🟠 BluFi 安全模式未定（见 §4.2）

不加密 = Wi-Fi 密码在空口明文广播出去；加密 = 纯 Dart 实现成本陡增。这是个要拍板的取舍。

### 5.4 🟠 配网窗口和错误计数会直接影响交互

规格书给的是硬性时间：首次配网 10 分钟、**二次配网只有 3 分钟**、
**连续 5 次密码错误直接关闭配网模式**。
App 必须：把剩余时间显示出来；密码错误要明确提示（别让用户连试 5 次把设备关进不可配网状态）；
超时后引导「BUTTON 双击重新进配网」。这些在我们现有的绑定页上没有对应概念。

### 5.5 🟠 两个产品族进同一个 App

Wi-Fi 版有 TF 卡、轮播策略、定时休眠、OTA/FPGA 升级、国家码；现有 BLE 相框没有。
详情页、设置页、投屏动线都要按设备类型分流。**设备模型（`DeviceItem`）要能表达
"这是哪一类设备"**，否则每个页面都要各写一遍 if。

### 5.6 🟡 平台限制（我们已经踩过的坑）

- Android 同一个 app **30 秒内起扫超过 5 次**会被系统静默降级（本仓已有账本 `_scanStarts`），
  配网重试编排要复用它，别另起一路扫描；
- Android 12+ 的 `BLUETOOTH_SCAN/CONNECT` 权限、iOS 的蓝牙权限与后台限制照旧；
- 配网期间 App 要同时用蓝牙（连设备）和 Wi-Fi 信息（拿当前 SSID）——**拿当前 SSID 在
  iOS 上需要 Access WiFi Information entitlement，Android 需要定位权限**，
  这条在花盆项目上踩过，别在这里重来一遍。

### 5.7 🟡 5 GHz / WPA3 / 隐藏 SSID / 国家码

硬件是双频，所以不像 2.4G-only 设备那样要拦 5G 网络——**但反过来，用户手机连的是 5G 时，
下发的 SSID 是否需要额外信息（信道/国家码）要确认**。协议里专门有 `wifi_set_country_code`
和 `country` 变更通知，说明国家码是个真会出问题的点。WPA3、隐藏 SSID 是否支持，文档没说。

### 5.8 🟡 AP 配网那条路（方法一）的安全性

热点密码**固定** `1234567890`、网页 `192.168.4.1` 明文改 MQTT 服务器地址/账号/密码。
如果这条路在量产固件上默认开着，等于任何人靠近设备就能把它指向自己的 MQTT 服务器。
**建议向硬件方确认量产是否关闭或加限制**；App 侧不要引导用户走这条。

### 5.9 🟡 协议文档本身的毛病（照抄会踩）

实现前要向硬件方逐条核对：

- `wifimode` 表里写 `timingtime`，示例里是 `timingTime`（大小写不一致）；
- `wifi_sleep` 一节的示例 **action 写成了 `wifimode`**，字段名也从 `live`/`timingtime`
  变成了示例里的 `beginTime`/`endTime`；
- `heart` 的 `statype` 在表里是 int、示例里是 `"type": 3`（键名都不一样）；
- `ota` 表里写 `dataport`、示例里是 `port`；`down_int_img` 同样；
- `device_config` 的 `batchkey`/`deviceId`/`uid` 表里标 int、说明却是「12 位随机字符串」；
- 状态码表里 `100` 是"收到下行需要 ack"，而各 `*_ack` 示例里 `result` 给的是 `1`——
  **成功到底是 0、1 还是 113？**（自定义 BLE 消息那边明确写的是 0 = 成功）。

## 6. 待确认清单

**给硬件方 / 固件：**

1. BluFi 是否启用安全协商（DH + AES-128-CFB + CRC16）？能否提供关闭/不加密模式？
2. BluFi 的 service / characteristic UUID 是否就是乐鑫默认的 `FFFF` / `FF01` / `FF02`？
3. 广播包结构：除了名字 `IJ_<MAC>`，有没有厂商数据？里面有没有屏型/电量（我们现有列表要显示）？
4. 主控芯片型号与 BluFi 版本；量产固件版本（要 ≥ V0.2.7 才是 `host` 字段）。
5. 配网期间设备的 BLE 是否一直可连？配网成功后 BLE 是否关闭（心跳里有 `ble: on/off`）？
6. 方法一（AP + 192.168.4.1 + 固定密码）量产是否保留？
7. 「APP 刷图」在 Wi-Fi 版上指的是哪条路径？还有没有 BLE 直传图的能力？

**给服务端：**

8. `.bin` 由谁生成、按什么规格（屏型/六色抖动/方向/CRC）？端上现有编码是否要搬过去？
9. App 认领设备的接口（扫码 → 绑定 → 下发 `device_config`）是什么？
10. `play` / `strategy` / `strategy_bin` 由谁触发——App 选完图调后端接口，还是后端定时？
11. MQTT 的 host/port/usr/pwd 从哪来？是 App 从后端取了再经 BluFi 下发（文档的口径），
    还是固件出厂就写死？前者意味着**这四个值会经过手机**，要考虑凭据下发的安全性。
12. 成功状态码到底是 0 还是 1（见 §5.9 最后一条）。

## 7. 建议的落地顺序

1. **先摸真机**：拿一台 Wi-Fi 版样机 + EspBlufi 官方 App 走通一次配网，抓包确认
   UUID、安全模式、广播结构。这一步能把 §6 里一半的问题问掉；
2. **再定架构**：`.bin` 谁生成、设备怎么绑，这两条定了才知道 App 要做多少；
3. **然后做配网**：按 §4.2 选路线，先做「不合并搜索」的独立入口跑通，
   跑通之后再谈要不要并进现有搜索列表（§3.4）；
4. **最后做设备分型**：`DeviceItem` 加设备类型，详情/设置/投屏按类型分流。

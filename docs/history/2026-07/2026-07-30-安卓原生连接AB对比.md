## Problem

用户反馈：**同样的弱网设备，别人的 APP 连得上、当前项目连不上**；提出两个问题——
是不是 Flutter 的性能瓶颈？要不要把蓝牙连接用安卓原生再实现一次做对比？

对照物不明确（用户只说"别人的能连上"，没指明是哪个 APP），所以只能按实测走。

## 判断：不是 Flutter 的性能瓶颈，但插件层要背一部分锅

这两件事必须分开，混在一起就会做错决策。

**建连本身与 Dart 快慢无关。** CONNECT_IND 的发送时机、重传、链路参数协商全部发生在
`com.android.bluetooth` 进程和控制器固件里。Dart 只做一件事：调一次 `connectGatt`，然后等回调。
MethodChannel 单次往返是亚毫秒级，而 CONNECT_IND 窗口是几十毫秒到几秒。**再快的 Dart 也改变不了
一次都没发对时刻的定向连接。** 所以"换成原生就更快"在建连这一步上不成立，
不能拿它当假设直接重写整个传输层。

**但 flutter_blue_plus（下称 FBP）挡住了几个真正管用的旋钮，扫描这条路上也有实打实的开销。**
从代码里读出四个可疑点，按怀疑度排序：

| # | 可疑点 | 位置 | 说明 |
| --- | --- | --- | --- |
| ① | `autoConnect` 排在超时阶梯最后 | `device_ble.dart:230-242` `:806` | 正常信号要先白等 `5s+400ms+8s=13.4s` 才打这张牌；弱信号候选也要 5s。文档自己写了它是弱信号唯一有效的牌，却放在最后。 |
| ② | 扫描无硬件过滤，全部广播包过 platform channel | `device_ble.dart:474-486` | 无 `withServices`/`withMsd` + `continuousUpdates:true, continuousDivisor:1`。周围三十几台设备时是每秒几百条消息过 JNI→channel→Dart，Dart 还要给每包算 `_displaySignature`。**这是插件层唯一称得上"性能瓶颈"的地方**，后果是 UI isolate 被塞住、弱信号闸的 1.5s 计时被拉偏。 |
| ③ | "看到广播"到"发起连接"隔了太久 | `ble_controller.dart:783` 附近 | 扫到 → `until` 收网 → `stopScan` → 120ms 沉淀 → `connect()`。相框广播间隔约 3s，这一串几百毫秒下来，那个广播事件早过去了。原生可以在扫描回调里当场 `connectGatt`。 |
| ④ | 重试循环可能泄漏 GATT client | `device_ble.dart:786-805` | 每轮失败调 `disconnect()` 后立刻进下一轮，没等 `STATE_DISCONNECTED` 落地。安卓每个 app 的 GATT client 句柄有限，漏掉 `close()` 的症状正是"试几次之后怎么连都是 133、重启 App 才好"。**本机无法查 FBP 源码，需真机验证。** |

另外发现一个 FBP 完全不暴露、而系统自己提供的弱信号旋钮：
`ScanSettings.setMatchMode(MATCH_MODE_AGGRESSIVE)` + `setNumOfMatches(MATCH_NUM_MAX_ADVERTISEMENT)`
——允许"只收到很少几包、信号很弱"时也上报。**注意它只对带 `ScanFilter` 的硬件过滤扫描生效**，
所以必须和过滤一起开，而过滤本身又要求广播每包都带厂商数据（真机未必如此，
`device_ble.dart:346` 正是因为这个才故意不过滤）。这一组耦合只能靠实测拆开。

## 做法：先量，别先重写

不做全量原生传输层重写。会话所有权没法拆——一旦原生持有 GATT，FBP 的 `BluetoothDevice` 就接管不了，
意味着连接/MTU/收发/通知/断开必须整套搬到 Kotlin，`device_ble.dart` 那 1948 行要拆成"协议层 + 传输层"。
这活能干，但在拿到数据之前干，赌的成分太大。

改为做一个**原生 A/B 探针**：Kotlin 跑一次与 `FrameBleClient` 完全同构的冷连接
（扫描 → 匹配 → `connectGatt` → 发现服务 → `requestMtu` → 订阅 FF02 → 发 0x01 → 收 ACK 验身），
每步打时间戳，接进「投屏性能自检」页，**两个按钮手动交替按**，比成功率与"失败停在哪一步"。

### 两条路径怎么保证可比

| | 现有路径按钮 | 原生路径按钮 |
| --- | --- | --- |
| 走什么 | `BleController.scan` + `BleController.connect`（含弱信号闸、超时阶梯、autoConnect 兜底） | `BleNativeProbe` 的 Kotlin 实现 |
| 为什么不走 `connectBoundDevice` | 那条入口还含系统已连接表与直连缓存两条快路径，命中时几乎瞬时完成，与原生的完整扫描不在同一起跑线 | — |
| 同起跑线 | 「每轮先清直连缓存」开关默认开，逼它走完整扫描 | 默认完整扫描 |
| 每轮收尾 | `finally` 里必定 `disconnect()` | 必定 `disconnect()` + **`close()`** + 400ms + 沉淀 |
| 验身 | `serialsMatch(0x01 返回值, 目标)` | 同一套规则（Kotlin 侧逐条对齐 `serial_match.dart`） |

⚠️ 目标序列号来自**广播**，只有 4 字节短 ID（8 个十六进制字符），而 0x01 返回 6 字节完整 ID。
验身**必须**用 `serialsMatch`（短值是长值的前缀或后缀），写成精确相等会让每次 trial 都误报
`identity-mismatch`。两侧初版都踩了这个坑，已修。

### 原生侧的四个旋钮（页面上可切）

| 旋钮 | 默认 | 测什么 |
| --- | --- | --- |
| 每轮先清直连缓存 | 开 | 保证同起跑线（作用于现有路径） |
| 原生：硬件扫描过滤 + AGGRESSIVE | 关 | 可疑点 ② + 系统弱信号旋钮。**开了如果反而扫不到，说明广播不是每包都带厂商数据**，这条路直接判死 |

## 怎么测

入口：设置 → 更新 BoltStar → 连点版本号 7 次 → 「投屏性能自检」页顶部第一张卡。

1. 把相框放到**会复现问题的位置**（隔墙 / 远距离，RSSI -70~-85dBm）。位置定了就别动。
2. 「扫描并选择设备」选中目标。
3. **交替按两个按钮**，各 8~10 次。⚠️ 不要一口气按满一边——射频环境会漂，
   分段交替才能让两条路径共享同一段环境，否则比的是"前五分钟 vs 后五分钟"。
4. 先跑一组全默认（原生三个旋钮全关），这是最干净的"原生 vs FBP"对照。
5. 再单独打开某一个旋钮各跑 8 次，看是哪个旋钮带来的差异。一次只动一个。
6. 「复制报告」贴回本文。

### 判读标准

- **成功率差距 < 10%（各 10 次内差 1 次）**：噪声，不构成重写理由。去查编排参数和固件广播。
- **原生显著赢，且默认三关也赢**：差异来自 channel 往返与 GATT 生命周期管理，
  值得投入做完整原生传输层。
- **原生只在某个旋钮打开时赢**：那个旋钮就是答案——大部分可以在 Dart 侧直接实现
  （`withMsd` 硬件过滤、提前 autoConnect），**不需要重写传输层**。
- **两边都停在 `scan`**：不是连接问题，是设备没在广播（被别的 App 占着 / 起扫配额被降级）。
- **原生报 `connectGatt 返回 null`**：GATT client 句柄耗尽。探针自己每次都 `close()`，
  所以这说明是**别的组件**在漏——直接印证可疑点 ④。
- 关注 `广播包=N/M台`：这个数字就是不过滤扫描时 FBP 要搬过 platform channel 的量。
- **「原生：硬件扫描过滤」这个开关是给 FBP 探路的**：开着还能稳定扫到 ⇒ 固件确实每包都带
  厂商数据 ⇒ 再给 FBP 的连接扫描加 `withMsd` 才安全；开着就扫不到，这条路直接判死，
  省下一次改动。别把它只当原生侧的旋钮。

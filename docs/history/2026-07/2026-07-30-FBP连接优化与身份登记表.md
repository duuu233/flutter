## 为什么先做这一轮

上一轮把原生 A/B 探针搭好了，但**不能直接开测**：现有 FBP 路径上还压着几处已知的、
能自己修的问题。带着它们去比，原生赢了也分不清是赢在「原生」还是赢在「顺手改的那几处」。
所以先把 FBP 这条路调到最好，再比才有意义。

## 一、最先修的其实不是射频问题：身份闸把好设备拦在扫描之前

`connectBoundDevice` 的第一行就是身份闸：

```dart
if (!isCompleteDeviceSerial(serial)) {
  return _l10n.bleIncompleteDeviceIdentity;   // 「请删除后重新绑定」
}
```

闸门本身是对的——缺完整 6 字节 ID 时用短 ID / 名称 / 尺寸兜底连接必然串台。
错的是**「设备明明有完整 ID，只是这一刻没人把它交到调用方手上」**。

Flutter 侧的漏口在 `refreshDevices`：它是**整体替换**设备列表，而
`_carryOverBleFields` 搬电量、固件版本、播放模式、轮播态……**唯独不搬 `serialNumber`**。
于是只要某次列表接口返回的行缺 `deviceId`（后端抖动、历史短 ID 记录），
此前 0x01 验身拿到的完整 ID 就当场丢失，之后这台好设备的**每一次**连接都会被闸门拦下，
**连扫描都不会发起**——用户看到的是「连不上」，但它跟信号、距离、固件毫无关系。

小程序 2026-07-30 已用「设备身份登记表」修掉同一类问题（它那边的触发路径是详情页
`selectedDevice` 继承落空），其变更记录的 Follow-up 里明写着「Flutter 未同步」。本轮同步。

### 实现

新增 `lib/src/device/device_identity_registry.dart`：`后端记录主键 → 完整 6 字节 Device_ID`，
SharedPreferences 落盘 + 内存镜像，与小程序 `utils/device-identity.js` 同语义。

**补齐顺序固定，登记表只作最后兜底、永不反向覆盖后端最新值：**

```text
记录自身的完整 ID  >  本地上一版记录(_carryOverBleFields)  >  登记表
```

| 时机 | 动作 | 位置 |
| --- | --- | --- |
| 列表接口返回记录 | 带 ID 的登记；缺 ID 的查表补上 | `state._completeDeviceIdentities` |
| 上一版记录里有、这一版没有 | 就地补上（第二档） | `state._carryOverBleFields` |
| 连接后 0x01 验身通过 | 登记（**最权威的一手来源**）+ 记录缺 ID 时就地补上 | `state._applyConnectedInfo` |
| 删除设备 | `forget(deviceId)` | `state.deleteDevice` |
| 退出登录 / 注销 / 登录态失效 | `clear()` | 三处会话清理 |

**只收完整 6 字节 ID**：广播 4 字节短 ID、BLE 临时句柄一律不进表，否则等于把
「只能筛候选的短 ID」升格成身份，正是 EF6-370 串到 EF6-589 那类串台的来源。
**键只取记录自己的主键**，不接受「另一台的 id」——那等于用登记表制造串台。

`_applyConnectedInfo` 是登记 0x01 结果的唯一入口，两个调用点（`connectDevice`、
`refreshConnectedDeviceInfo`）都已确认当前 BLE 会话就是这台设备，占位设备跳过。

## 二、扫描热路径：每包 O(N) 字符串运算 → O(1) 查表

`FrameBleClient.scan` 的 `visible()` 在 `until != null`（**所有连接路径**）时，
每收到一个广播包就要重算一遍；而 `isAllowed` 对每台已发现设备都要做
字符串拼接 + `toUpperCase` + `contains`，名字不命中的还要再解析一遍厂商数据。
我们又开着 `continuousUpdates + continuousDivisor:1`（每包都上报，这是弱信号必须的）。

在三十几台设备的环境里，这就是**每秒几百次 × N 台**的字符串运算压在 UI isolate 上。
后果不是「连不上」，而是目标设备那一包排队变晚、弱信号闸的「最多等 1.5s」被拉偏。
这是插件层唯一称得上「性能瓶颈」的地方，**而且完全在我们自己的代码里**。

判定的输入只有名字和厂商数据，两者恰好就是 `_displaySignature` 的成分：
**签名没变 ⇒ 判定不可能变**。于是加一层 `allowed` 缓存，只在「新设备 / 签名有变化」时重算。
「首包没带名字的设备，后续包补齐后追溯性进入列表」这一行为完全不变——
名字到了签名就变，缓存跟着刷新。

## 三、极弱信号：常规建连一档都不走，直接上 autoConnect

原先阶梯只有两档：正常 `5s → 8s → autoConnect 15s`，弱（< -70dBm）`5s → autoConnect 15s`。
但 -80dBm 以下常规 `connectGatt` 的 CONNECT_IND 命中率已接近于零，那 5 秒是纯白等。

新增第三档：

| 档位 | 判据 | 阶梯 | 最坏耗时 |
| --- | --- | --- | --- |
| 正常 | ≥ -70dBm | 5s → 8s → autoConnect 15s | 28.4s |
| 弱 | < -70dBm | 5s → autoConnect 15s | 20.4s |
| **极弱（新）** | **< -80dBm** | **直接 autoConnect 20s** | **20s** |

省下的 5 秒原样加给 autoConnect（`androidAutoConnectFallbackVeryWeak`），
**总预算不变**，只是全花在真正管用的机制上。`rssi == 0`（读不到）天然落进「正常」档。

档位选择收敛到 `BleController._attemptTimeoutsForRssi` 一个函数；空阶梯在
`_connectWithRetry` 里有兜底：若同时又不允许 autoConnect（直连快路径），回落默认阶梯，
绝不会变成「什么都没试就报失败」。

## 四、建连失败后等断开真正落地再重试

改前：失败 → `disconnect()` → 立刻退避 400ms → 重连。
但 `disconnect()` 返回只代表请求已下发，链路真正拆掉是随后一个异步事件。
半连状态上发 `connectGatt`，安卓侧最典型的表现就是 `status=133`；更糟的是
**每轮重试都会新建一个 GATT client**，而每个 app 的句柄数有限，攒满之后就变成
「怎么连都是 133、重启 App 才好」——这正是 A/B 文档里怀疑的第 ④ 条。

新增 `_settleDisconnected`：断开后等 `connectionState` 真的到 disconnected，
上限 600ms。已断开时 `isConnected` 立刻为假、直接返回，不会平白多等；
平台不补发断开事件时靠超时兜底，绝不永久挂住。

## 五、闸门放行的那一台就地捕获

改前是 `until` 里判定命中 → 扫描返回后**再 match 一遍**取目标。两个问题：

1. 同短 ID 的两台都在场时，窗口末尾按 RSSI 重排后「第一个匹配」可能已经换了一台，
   于是连的不是闸门放行的那一台；
2. 建连阶梯是按「开闸那一刻那一帧的 RSSI」选的，重新 match 拿到的是最后一包的 RSSI，
   两者对不上时会选错档位。

现在 `until` 命中即把那个 `ScanResult` 捕获下来，只有「等满整窗才收网」才回落到重新 match。

## 未做：给 FBP 加 withMsd 硬件扫描过滤

理由是**顺序问题，不是否定**。硬件过滤要求相框广播**每一包**都带厂商数据，
而 `device_ble.dart` 的注释明确记着当年正因为「真机广播不一定带」才故意不过滤。
这个前提真假未知，靠猜没有意义。

原生探针的 `useScanFilter` 开关恰好就是这个问题的判定器：
**开着还能稳定扫到 ⇒ 固件确实每包都带 ⇒ 再给 FBP 加 `withMsd` 才是安全的**；
开着就扫不到，这条路直接判死，省下一次改动。所以留到实验之后再定。

## Problem

用户反馈集中在三件事：搜索慢、连接慢、**弱信号设备连不上**，且安卓明显更差。拆开看是六个独立成因，
不是一个「调大超时」能解决的问题。

### 1. 每次复连都要重新扫描一遍

改前 `connectBoundDevice` 的唯一入口是「扫描 → 筛候选 → 建连 → 验身」。而冷连接的耗时里，
**扫描才是最大的一块**：

- 相框被 GATT 占过之后要好几秒才恢复广播（单连接模型下「切换设备」必然踩到这一段）；
- 固件广播间隔约 3s，`until` 命中即停也至少要等到下一个广播包；
- 多台同时在场时还要抢同一条广播信道。

但复连的目标设备**上一次是谁、句柄是什么，本机其实知道**——这段扫描是可以整段跳过的。

### 2. 设备被系统层占着时，扫描永远搜不到

BLE 设备一旦被连上就停止广播。所以只要相框此刻被系统层占着（微信小程序还连着、上个进程被杀时
GATT 没收干净、别的 App 连过），扫描窗口开到 60 秒也搜不到一台。用户看到「设备明明开着就是搜不到」，
还会被引到「是不是没开机」的错误方向。这一类**扫描治不了**——设备就躺在系统的已连接表里。

### 3. 扫到的第一帧恰恰是信号最差的那一帧

`until` 命中即停是上一轮的提速改动，但它有个副作用：擦边收到第一帧就立刻发起连接，
而那一帧往往是整个窗口里链路质量最差的时刻，CONNECT_IND 极易丢。现场表现正是
**高 RSSI 一点就连上、-67~-78dBm 区间经常连不上**。小程序 2026-07-20 已修（`WEAK_SIGNAL_RSSI`），App 没跟。

### 4. 停扫回调返回 ≠ 射频空闲

扫描与 GATT 建连抢同一路射频。绑定页此前已有 120ms 沉淀（`_scanSettleBeforeConnect`），
但**自动重连这条路径上没有**——而复连恰恰是「停扫后立刻建连」最密集的地方。只治了一条路。

### 5. 建连超时阶梯不对，且安卓少了一张牌

改前是固定 12s × 2 次：绝大多数首连失败是瞬时的（GATT 抖动、CONNECT_IND 丢包），
12s 意味着**早失败也要白等 12 秒**，最坏 24s 只换来 2 次机会。
更关键的是安卓侧完全没用 `autoConnect`——这是弱信号设备唯一真正管用的那张牌（见下）。

### 6. Android 起扫频率限制（本轮最隐蔽的一条）

Android 7+ 的 `AppScanStats.isScanningTooFrequently()`：同一个 app **30 秒内起扫超过 5 次**，
之后的扫描**不报错**，而是被系统静默降级（实测表现为整窗几乎收不到广播）。

这条限制专治我们这种重试型编排：`connectBoundDevice` 每轮一次起扫、`until` 命中即停时每轮只占 1~2 秒，
用户连点几台设备就能在半分钟内攒够 5 次。症状是「刚才还能搜到，连点几次之后就再也搜不到了，等一会儿又好了」，
**极易误判成固件问题**。小程序天然少踩：它一路硬件扫描 + 多订阅者共用（`bluetooth.js activeScan`），
并发调用不会各起一路。

## 时间账：一次复连省在哪

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 设备被系统层占着（另一 App / 残留 GATT） | 扫描 12s 后报「未搜索到该设备」，**永远连不上** | 系统表命中，≈瞬时建连 |
| 常规复连（缓存有效、设备在广播） | 扫描 1~5s + 建连 1~2s | 直连 1~2s，**跳过整段扫描** |
| 缓存失效（设备重启 / 安卓地址轮换 / 换机） | 同上 | 白花 ≤3s 探测后回落扫描，缓存自动删除，下次不再白花 |
| 弱信号首连 | 抢第一帧连、失败即重试；安卓无 autoConnect | 等更强一帧(≤1.5s) → 5s → 8s → autoConnect 8s |
| 半分钟内连点多台（安卓） | 第 6 次起扫被系统静默降级，整窗搜不到 | 等窗口滑出再扫，如实记 warn |

## 关键决策

### 为什么 `autoConnect` 是安卓弱信号唯一真正管用的牌

常规建连（`autoConnect=false`）是「主机立刻发起一次定向连接」——CONNECT_IND 只在极短窗口里试，
弱信号/远距离下丢一次就整轮超时，**再调大 timeout 也没用**（不是等得不够久，是压根没在对的时刻发）。
`autoConnect=true` 走的是完全不同的路径：把设备加进控制器白名单，由**控制器**用低占空比持续等它的广播，
等到了再连。慢一点，但对「信号弱、时断时续、广播间隔长（本相框约 3s）」的设备成功率明显更高——
这正是「设备明明在、就是连不上，多点几次某一次忽然又好了」的解法。

三处必须小心，代码里都兜住了：① FBP 要求 `autoConnect` 与 `requestMtu` 不能同用 → `mtu: null`；
② 不同 FBP 版本下 `connect(autoConnect: true)` 有「立刻返回」与「等到连上」两种行为，两种都兜；
③ 等不到必须显式 `disconnect()` 取消挂起的 autoConnect，否则它会在后台一直连下去，
之后用户去连另一台时这条幽灵连接会把设备占住（设备被占就停止广播 → 又变成「搜不到」）。

iOS 没有对应旋钮（CoreBluetooth 的 `connect` 本身就是「一直等到连上」的语义），故该兜底仅 Android。

### 为什么直连缓存存本机、不存后端

`remoteId` 是「设备 × 手机」的函数：Android 是射频 MAC（设备重置/隐私随机地址轮换后会变），
iOS 是本机系统给外设生成的 UUID（换一部手机就完全不同）。存后端等于把 A 手机的句柄发给 B 手机，
B 上拿它直连必然超时白等，**比没有缓存更慢**。SharedPreferences 天然按手机隔离，正好匹配这个句柄的语义。
键用 0x01 完整 6 字节 ID：它既是后端设备记录的稳定身份，也是连上后固件自报的物理身份。

### 快路径为什么不降低身份安全性

直连和系统表两条快路径都没有 ScanResult，也就没有广播厂商数据。这不降低安全性——
**广播短 ID 本来就只能筛候选、不能验身**。两条快路径连上后一律走同一个 `0x01 完整 ID` 验身，
与扫描路径同一把尺子；不符就断开、排除该 remoteId、删除缓存，再回落扫描。

### 为什么系统表候选必须先按广播名白名单筛

Android 的 `systemDevices` 会把**所有** GATT 已连接设备都返回（服务过滤只在 iOS 生效），
耳机、手表都在里面。不筛就会拿 3 秒超时去连用户的耳机。所以先用扫描同款的广播名白名单
（`EF6-370`/`EF6-589`，产品列表接口返回值优先）筛一遍，**名字取不到就直接跳过**——
宁可放弃这次提速。白名单只筛「是不是相框」，认领仍由 0x01 决定。

另：这里只用**已缓存**的白名单，绝不在快路径里 await 产品列表接口——那是一次网络请求，
弱网下能卡好几秒，快路径一旦要等网络就不再是快路径。

### 为什么起扫账本触顶时等待有上限

被系统降级的扫描是「转满整窗一台都搜不到」，等一下明显划算；但绝不为了理论上干净的窗口
把用户按在原地半分钟——上限 10s，到点照常起扫，并记 warn 说明本轮可能被降级。

### 为什么连接失败不再立刻排除候选

连接失败**不等于**「这台不是我要的」。句柄可能刚失效（设备重启/安卓随机地址轮换），
也可能只是一次瞬时抖动——重扫拿到新鲜句柄再连往往就成了。改为同一 remoteId 连失败 2 次才排除，
身份不符则**立刻**排除（那是确定性的结论，与失败不同）。

### 自愈与不留长期回归

- 直连缓存赌不中即删除，下次扫描连上后重新写入；验身串台时同样删除并排除该句柄。
- 直连快路径连续 2 次「直连失败但扫描成功」后，**本进程内自动停用**。这条是为 iOS 准备的保险：
  Android 的 remoteId 就是 MAC，不扫描直接连是标准用法；iOS 能否直连取决于插件底层有没有走
  `retrievePeripherals(withIdentifiers:)`。若这条路在某个平台/版本上根本不通，
  探测就会变成每次复连白花 3 秒——累计两次即自动关掉。

## 风险与回归清单

| 风险 | 判断 | 兜底 |
| --- | --- | --- |
| 直连缓存串台（拿 B 的句柄连 A） | 只有 0x01 完整 ID 验身通过才写入 | 验身不符即删缓存 + 排除句柄 + 回落扫描 |
| 快路径拖慢（缓存长期失效） | 最坏每次多 3s | 赌不中即删缓存；连续 2 次进程内停用 |
| 系统表连到非目标设备 | 白名单筛 + 0x01 验身 | 不符即排除并回落扫描 |
| `autoConnect` 幽灵连接占住设备 | 超时后显式 `disconnect()` | 见「关键决策」③ |
| 起扫等待让用户干等 | 上限 10s，且仅在触顶时 | 到点照常起扫 + warn |
| 高优先级窗口费电 | 仅 2s，且图传会话开着时不回落误伤 | `_settleToIdleAfterConnect` 双条件判断 |

## 一、搜索设备结果页：列表视口 = 4.5 张卡

### 改前：列表吃「剩下的」，雷达雷打不动占 280

```dart
Center(child: SizedBox(width: 280, height: 280, child: 雷达)),
const SizedBox(height: 20),
Row( 已找到 N 台 … 重新搜索 ),      // 高度随扫描状态在 28~42 之间跳
const SizedBox(height: 12),
Expanded(child: SingleChildScrollView(…)),   // ← 列表 = 剩下的全部
```

iPhone 13 上 `Expanded` 实得约 280，一张卡 82 + 间距 12，正好 **3 张多一点**——
就是需求里说的「目前只显示 3 个」。想长到 4.5 张（`4×82 + 4×12 + 41 = 417`），
只能从雷达那儿要。

### 改后：雷达与列表的高度在一个 `LayoutBuilder` 里一次算完

```dart
Expanded(
  child: LayoutBuilder(builder: (context, constraints) {
    const double fixed = 20 + _kCountRowHeight + 12;          // 两条间距 + 统计行
    final double avail = constraints.maxHeight;
    final double radarSize =
        (avail - _kListViewport - fixed).clamp(_kRadarMin, _kRadarMax);
    final double listHeight =
        (avail - radarSize - fixed).clamp(0.0, _kListViewport);
    …
  }),
)
```

四个常量（都写在文件顶部，带账）：

| 常量 | 值 | 来历 |
| --- | --- | --- |
| `_kCardHeight` | 82 | 抄自 `FigmaBindDeviceCard` 的 `height: 82`（那边加了反向指认注释） |
| `_kCardGap` | 12 | 卡间距 |
| `_kListViewport` | `82×4 + 12×4 + 41 = 417` | **4 张完整 + 露出半张** |
| `_kCountRowHeight` | 44 | 统计行**固定**高度 |
| `_kRadarMax` / `_kRadarMin` | 280 / 150 | 上限＝搜索中页尺寸；下限＝「还看得出是雷达」 |

分配顺序就是需求的优先级：**列表先拿够 417，雷达拿剩下的并夹在 150~280**；
屏幕矮到连雷达下限都保不住时，才反过来压列表（那是「一屏装不下」的降级）。

顺带修掉一个抖动：统计行原来扫描中是「文字 + 上下各 12 的热区」≈42、扫描一停换成 28 的
`IconButton`，整页会往上跳一下；现在固定 44。

### 各机型实得（按 `FigmaScreen` 的顶栏/底部槽估算）

| 机型 | 可用高 | 雷达 | 列表 | ≈ 几张卡 |
| --- | --- | --- | --- | --- |
| iPhone 13（390×844） | ≈639 | 150 | 413 | **4.45** |
| 大屏安卓（412×915） | ≈735 | 242 | 417 | **4.5** |
| 小屏 SE（320×568） | ≈424 | 150（触底） | 198 | 2.4（降级，改前约 0.9） |

⚠️ 雷达在 iPhone 13 上会从 280 缩到 150，这是把高度让给列表的代价（产品这轮明确要列表）。
首台设备出现、页面从 searching 切到 found 时雷达会缩一下——真机上要看这个过渡是否刺眼，
嫌跳可以把 `_kRadarMin` 往上调，代价是列表少半张。

### 与小程序的对应关系

小程序那边是同一套思路的 CSS 版：`.bind-content` 竖向 flex、
`.device-list { max-height: 844rpx; flex: 0 1 auto; min-height: 0 }`、
`.radar-wrap--found { height: 340rpx; flex-shrink: 40 }`。
两端数字不同是因为卡片高度不同（App 82dp vs 小程序 ≈168rpx），**「4 张整 + 半张」这条口径一致**。

## 二、首页六宫格：去副标题 + 去箭头 + 图标拉大

### `_HomeEntryCard`

| 项 | 改动 |
| --- | --- |
| 入参 | 删 `subtitle`、`subtitleFontSize`、`arrowAsset` |
| 图标 | `33` → **`48`**（`_iconSize`，对齐小程序 96rpx）；fallback 图标同步按 `_iconSize * 0.9` |
| 图标与标题的间距 | `6` → **`10`**（图标大了一圈，对齐小程序 `margin-bottom: 20rpx`） |
| 内边距 | `only(left: 10, right: 6)` → **`symmetric(horizontal: 10)`**（右边那 6 原是给箭头透明阴影留的） |
| 标题 | **字号基准一个数没动**（产品：主标题字号不变）；仍由 `_entryTitleFontSize` 按六条标题算共用字号 |
| `titleHorizontalReserve` | `10 + 6` → `10 + 10`（可用宽窄了 4，日文最长那条的共用字号会低一点点） |
| 删除 | `_arrowVisualWidth`、`subtitleHorizontalReserve` 两个常量，以及箭头那段 `Transform.translate` |

卡片仍是 `AspectRatio(206/220)`，**高度不变**：副标题两行腾出的高度差不多正好是图标放大的那 15。
360dp 屏上内容 = 48 + 10 + 标题 ≈18 = 76，卡高 ≈105，上下各余约 14。

## 三、⚠️ 事故与修复：误删了 `entryTitle`，release 打包直接编译失败

`1a78117` 推上去之后 release 打包报：

```
home_main_view.dart:280:34: Error: Member not found: 'entryTitle'.
home_main_view.dart:301:34: Error: Member not found: 'entryTitle'.
home_widgets.dart:1323:42: Error: Member not found: 'entryTitle'.
Target kernel_snapshot_program failed
```

**原因**：`home_text_styles.dart` 里 `entryTitle` 与 `entrySubtitle` 两个定义**挨在一起、
共用上方那一大段注释**。我要删的只有 `entrySubtitle`，但改写时是按「注释段开头 → 下一个定义
（`cardTitle`）开头」整段替换的，新文本只写回了注释，把中间的 `entryTitle` 一起带走了。
改完还全仓 grep 过一遍——但查的是**「我打算删的符号还有没有人引用」**（全为 0，看着很干净），
**没有查「还有人引用的符号是不是都还在」**。误删恰好落在后一类里，所以 grep 一点都没报。

**修复**：`3d39f91` 把 `entryTitle` 原样补回（`fontSize: 15 / w600 / height 1.2`，
与 `HEAD~1` 逐字节一致），字号一个数没动。

**这轮之后补上的静态自检**（本机无 Flutter SDK，只能这么兜）：

1. **反向引用检查**：把 `_HomeTextStyles.*` 的全部引用与类里的 `static const` 定义两头对齐 ——
   「引用但未定义」必须为空。（`cardTitle` / `cardSubtitle` 确为「定义但未引用」，但它们
   **改动前就没人用**，是既有状态，且 unused 只是 lint 不阻断编译，本轮不动。）
2. **删除清单检查**：从 `git diff` 的删除行里提取所有消失的定义，逐个确认已无活引用。
   （这条就是原来做过的那一半。）
3. **构造函数参数比对**：解析 `_HomeEntryCard` / `FigmaBindDeviceCard` / `BindDeviceFound`
   的命名参数集合，与全仓每个调用点的实参集合比对「多传 / 缺 required」——
   六处宫格卡与三处 `BindDeviceFound` 全部匹配。

⚠️ 教训写在这里给下一个人：**在没有编译器的机器上删代码，grep 必须做两个方向**。
只查「删的东西还有没有人用」，抓不到「顺手带走了别人还在用的东西」。

# 投屏「预览是正的、设备上反了」：圆形改动排除，落点在竖向导出角

> 文档类型：Historical Change Record
> 日期：2026-09-18
> 环境：SSH
> 分支与起始版本：`main` / `dde5eb6`
> 范围：`lib/src/features/cast/presentation/cast_preview_page.dart`（**只加日志**）、`lib/src/state.dart`
> 反馈：iOS 端 370 的旋转没有正确应用，投屏到设备又反过来了；怀疑是 09-17 的圆形改动

## 一、先给结论：**不是 `be1268f`（圆形）**

`be1268f` 全部改动只有 5 个文件，代码只动两个：

| 文件 | 改了什么 | 能不能影响出图 |
|---|---|---|
| `cast_preview_page.dart` | **3 个 hunk**：新增 `_ScreenClip` / `_kPickupShadow` 两个声明；展示层 `ClipRRect` → `_ScreenClip`；编辑层取景框同样换掉 | ❌ 全在**控件树**里 |
| `state.dart` | `DeviceItem` 加 `shapeType` 字段 + `_deviceFromJson` 解析它 | ❌ 只是多解析一个字段 |

三条硬证据：

1. **`roundScreen` 全仓只有 3 个读取点**，全部在预览页的控件树里
   （展示层裁剪、编辑层 `DecoratedBox`、编辑层裁剪）。出图链路
   （`_bake` / `_exportRotateDegOf` / `CastImageEditor.coverCropToSize` / `DitheringApi` / BLE 图传）
   **一个引用都没有**。
2. **`shapeType != 1` 时控件树与改动前逐字节一致**：`ClipRRect` 同一个 `_kClipRadius`、
   `BoxDecoration` 同一个圆角与同三个阴影值、`_dragging` 判据没变。
3. `ClipOval` / `ClipRRect` / `DecoratedBox` 都**不参与布局**，取景框尺寸 `g.frame`
   （`_bake` 里放大系数 `k` 的唯一输入）不受它们影响。

另外查了**整条投屏链路的近期改动**：`lib/src/features/cast/`、`dithering_api.dart`、
`frame_protocol.dart` 自 2026-09-03（`a19d4c0`）之后，除了这次圆形就没别的提交。

## 二、那问题在哪：竖向导出角

「**手机预览是正的、投到设备上反了**」这个组合，指向的正是竖向导出角：

- 预览**从来不显示导出角**（导出角是给设备屏朝向做的补偿，预览侧还要反向转回来），
  所以角度对不对，预览上根本看不出来；
- 竖向导出角的**唯一来源**是后端设备字段 `verticalRotation`，
  **缺省 0 = 不旋转**（2026-08-04 产品口径，取代了此前的固定 180°）；
- App 侧竖向**历来不转**（08-04 之前也不转），所以屏是倒装的那批设备，
  必须靠后台给这个产品配上角度才能转正。这一点 08-04 的双端变更记录里写明了：
  「后端必须给这批设备下发 `verticalRotation = 180`，否则用户会看到画面倒过来。」

## 三、本轮做了两件事

### 1. 加排查日志（不改任何行为）

- 进预览页打一行：`[预览][设备] … 后端屏=… 出图画布=… 形状=…(方/圆) 竖向导出角=…° 横向导出角=…°`
- 每张出图那行补上 `导出角=…°`（编辑过的按它自己的取景方向，未编辑的恒走竖向角）。

**一次真机就能定位**：那行 `竖向导出角` 是 0 ⇒ 后台没把角度给到 App（配置或接口），
不是端上算错；不是 0 而设备仍旧反 ⇒ 才轮到查角度方向。

### 2. 修掉一条**确实会丢角度**的路径

`refreshDeviceDetail` 把详情接口的返回喂给 `_deviceFromJson` 之后，
**只把 5 个固件字段搬回列表里那台设备**（`isUpdate` / `newVersionNo` / `downloadPath` /
`firmwareSize` / `firmwareVersion`），`verticalRotation` 和 `shapeType` 当时是 `final`、
**搬不回去也没人搬** —— 如果这两条只在详情接口下发、列表接口不下发，
那么「后台配了 180，App 永远拿不到」。

改法：两个字段改成可变，并在详情返回体**真的带了这个键时**才覆盖。
⚠️ 键缺失照样写 0 会把列表已经拿到的角度抹掉，而 **0 是合法角度**（明确不旋转），
两者必须分清，所以专门加了 `_hasAnyKey`（只看键在不在，不看值）。

⚠️ 这条只在**进过设备详情页**之后才生效。若列表接口本来就下发该字段，这条是 no-op。

## 四、还需要确认的（端上查不了）

1. 后台「产品配置」里 **370 这个产品的「竖向旋转度数」现在是多少**；
2. 用户产品**列表接口**到底下不下发 `verticalRotation`（`state.dart` 里记的列表出参没有它）；
3. 若两处都没有 ⇒ 这是后台配置/接口的事，端上改不出来。

另有一条与本次无关、但同样会造成「预览对、设备反」的既有差异，一并记下备查：
**编辑过的图**走 `dart:ui` 解码（自动应用 EXIF 方向），**未编辑的图**走
`package:image` 的 `decodeImage`（EXIF 方向不一定烤进像素）。iPhone 直出照片带方向标记的概率最高。
判别办法：同一张图**先随手拖一下再投**（走编辑链路），若设备上就正了，那问题在这条链路上，
与后台角度无关。

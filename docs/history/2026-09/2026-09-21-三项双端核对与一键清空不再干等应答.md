# 三项问题双端核对：一键清空不再干等 0x12 应答（App 只有这一项）

> 文档类型：Historical Change Record
> 日期：2026-09-21
> 环境：SSH 开发机（本机无 Flutter SDK）
> 分支与起始版本：main / d7dfb80
> 范围：`lib/src/state.dart`（`clearDeviceMemory`）、`lib/src/device/ble/device_ble.dart`（`cancelPending`）、
> 新增 `lib/src/device/ble/clear_watch.dart`、`test/clear_watch_test.dart`
> 当前权威文档：`AI_CONTEXT.md` 删除 / 一键清空那一节

## 背景与目标

产品在小程序上报了三条，要求核对是不是**双端都有**：

1. 官方图库 → 选择图片 → 点击投屏 → 选择设备点「连接并开始投屏」，进入预览页后还是提示未连接；
2. 下载超时提示修改，小程序尽量不要用英文，改中文；
3. 一键清除时长原因导致交互无法完成：「清除后设备都刷出默认图片了，小程序还在转圈圈」。

## 核对结论

| 问题 | App | 依据 |
| --- | --- | --- |
| 1 | **没有** | `official_gallery_detail_page.dart _startProjection`：未连接时先 `state.connectDevice`（带 `castConnectingDevice` 蒙层，失败 toast 原因并停下），连上才下载、进 `CastPreviewPage`；预览页不做连接判断，`CastingProgressPage` 还会按 `isDeviceActuallyConnected` 再连一次。小程序那边是弹层选完设备原样塞后端记录（不带本机 BLE 句柄）进预览，App 不存在这一步。 |
| 2 | **没有** | 图片下载统一走 `RecastDownload.toTempFile` / AI 页 `_downloadToFile`，失败返回 null 由页面给本地化文案（`castRecordImageDownloadFailed`、`aiImageExpired`）；固件包下载超时抛「固件包下载超时，请检查网络后重试」；投屏失败页 `_friendlyFailure` 把 `timeout` 归到 `castFailureTimeout`。 |
| 3 | **有** | `clearDeviceMemory` 与小程序同一套等法：`client.deleteImage` 的应答预算按张数给（每张 2s、6s～180s），等待期间只等这一条应答。设备已刷出默认图、应答迟到或丢了时，转圈要转满预算，再走一轮失败回读（最多 3 次、间隔 4s）。 |

## 变更内容（只改第 3 条）

1. `FrameBleClient.cancelPending(int cmd)`：收回某条指令的 pending、停超时计时器，等待方收到
   `FrameBleErrorKind.aborted`；没在等时返回 false。
2. 新增 `ClearWatch.deleteAll`（`device/ble/clear_watch.dart`）：发 0x12 后 5 秒起、每 3 秒读一次 0x01，
   掩码清空即按成功收尾（`ClearWatchResult.confirmedByPoll`）并 `cancelDelete` 收回 0x12；读失败（设备忙
   0x0B / 超时）或还有剩余就下一拍再看；0x12 自己先回来（成功或失败）以它为准。依赖全部由调用方传入，
   计时器可取消，收尾后不留待处理的 Timer。
3. `clearDeviceMemory`：`client.deleteImage(indexes)` 换成 `ClearWatch.deleteAll(...)`，回读只发 0x01
   （`readTransferInfo`），确认清空时多打一条 trace `delete-images-0x12-confirmed-by-poll`。失败分支（良性码放行、
   回读核对、设备忙、链路失败提示）一行没动。
4. 用例 `test/clear_watch_test.dart`（4 条，`testWidgets` 假时钟）：0x12 先回来不回读；迟迟不回时回读清空即收尾并
   收回应答、之后不再回读；回读失败不误判；0x12 自己失败原样抛出。
5. `AI_CONTEXT.md` 删除 / 一键清空一节补 2026-09-21 条目。

## 关键决策

- **回读而不是缩短等待**：60 张删一次本来就要一两分钟（2026-08 修过「一键清空 60 张误报设备无法连接」），缩短预算
  会让它回到误报；回读能在设备真清完的那一拍就收尾，删得慢的也照样等得到。
- 协议依据：设备处理指令期间收到新指令回 0x0B（规格书 v1.5 §6.6.1）；应答按命令字分别配对（`_pending` 以 cmd 为键），
  0x01 与在途的 0x12 互不干扰。5 秒内回应答的（张数少）一次都不回读，行为与原来相同。
- 与小程序同一做法、同一节奏（`utils/clear-watch.js`，5 秒 / 3 秒）。

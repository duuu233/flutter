## 需求（小程序侧本轮两项）

1. 折叠屏下首页只显示一半内容且滑不动，需要适配或加滚动；
2. 「我的」去掉「设备照片」「投屏管理」两个模块，合并为「我的相册」：
   - 列表 = 投屏成功的照片，按电子纸设备分类；
   - 可选中再次投屏（可编辑后投一张新照片），多选/全选按批量传输走；
   - 可选中删除（同时删设备与 App 记录），支持多选/全选；
   - 底层用投屏记录逻辑但只显示成功；沿用设备照片页 UI 与全选；
   - 「刷新」按钮改为投屏记录的「再次投屏」；删除按钮沿用图库那套（删设备图片 + 相册记录）。

## 第 1 项 · 折叠屏：**App 无需改动**（已核对，非「未做」）

小程序那边的根因是三条微信端特有的东西叠加，Flutter 一条都不成立：

| 小程序成因 | Flutter 现状 |
| --- | --- |
| `pages/home/home.json` 写了 `"disableScroll": true`，页面级滚动本来就关着 | 不存在该配置概念；页面滚动由 widget 自己决定 |
| 布局按 `rpx` 写死，而 `rpx = 屏宽/750`，折叠屏展开后屏更宽 → 内容整体等比放大、超出更矮的窗口 | 全部用逻辑像素，屏幕变宽不会把内容撑高；投屏入口卡等宽度敏感处早已改 `Expanded` + `AspectRatio`（见 `home_main_view.dart` 的注释） |
| 根容器 `min-height:100vh; overflow:hidden`，超出部分直接被裁掉 | 首页主视图、绑定流程视图、「我的」页都已经是 `SingleChildScrollView + ConstrainedBox(minHeight: constraints.maxHeight) + IntrinsicHeight`：**够高时用 `Spacer` 撑开、不够高时可滚动** |

核对到的具体位置：

- `features/home/presentation/home_main_view.dart` `build`（已绑定 / 未绑定两种场景共用）；
- `features/home/presentation/home_bind_device_view.dart` `build`（搜索中 / 未发现 / 已发现）；
- `features/mine/presentation/mine_page.dart` `build`；
- 「我的相册」页是 `GridView`，本身就是滚动容器。

折叠/展开时窗口尺寸变化由 Flutter 自身的 `MediaQuery` + 重新布局处理，不需要小程序那种
`onResize` + 手工下发窗口高度的做法。**结论：本项不改代码，只做核对记录。**

### ⚠️ 不要把小程序初版那套「JS 测窗口高度」同步过来

小程序本轮初版曾把窗口高度写成 `wx.getWindowInfo().windowHeight` 下发给 CSS，当天就在真机上
翻车（背景底部露缝 + 展开态冷启动滑不动），已回滚为纯 `100vh`，详见小程序侧
`photo-album/docs/changes/2026-08-04-折叠屏滚动适配与我的相册合并.md` 的「修正记录」。

**Flutter 不存在这个隐患，本次专门审过一遍**，结论是全项目没有「把测量结果缓存下来当布局尺寸」的写法：

| 检查项 | 结果 |
| --- | --- |
| `physicalSize` / `window.size` 参与布局 | 无（`PlatformDispatcher` 仅用于 `onError` 崩溃上报） |
| `MediaQuery` 高度被存进 State 字段 | 无。全项目只有 3 处 `MediaQuery.`，且都是 build 期直读 `padding.bottom`（安全区） |
| `RenderBox` 实测尺寸被缓存 | 无 |
| 预览页取景舞台 | `cast_preview_page.dart _buildStage` 用 `LayoutBuilder`，且 `_stageSize` 变化时会重新 `_enterEdit()` 重算几何——**折叠中途也会跟着更新** |

即：Flutter 的尺寸全部在 build 期由 constraints / MediaQuery 推导，窗口一变就自动重算，
天然免疫这类问题。后续若有人想「对齐小程序」而引入缓存尺寸，请先读本节。

> 顺带记录一个**反向差异**（小程序欠 Flutter 的，不在本轮范围）：小程序
> `subpackages/projection/preview/preview.js` 的 `_measureStage()` 把舞台尺寸缓存在
> `this._stageRect`，注释写明「初始布局完成后只量一次」。在折叠屏上，若用户在预览页中途折叠/展开，
> 取景框几何会停留在旧尺寸。Flutter 侧因为走 `LayoutBuilder` 没有这个问题。
> 该页是文档标注的高风险区（手势 + 离屏导出 + 旋转耦合），建议单独评估后再改，不要顺手动。

真机仍建议在折叠屏上过一遍（尤其展开态的宽屏比例、三折叠的三种形态），若发现某页溢出，
按上面这套滚动骨架补即可。

## 第 2 项 · 「我的相册」

### 模块合并

`features/mine/presentation/mine_page.dart`：常用功能由三卡改两卡
（`我的设备 / 设备照片 / 投屏管理` → `我的设备 / 我的相册`）。卡片由 102 定宽 + `spaceEvenly`
改成 `Padding(_inset) + Expanded` 等分、中缝 10.5，与小程序 `.quick-card { flex: 1 1 0 }` 同口径
（两卡还用 `spaceEvenly` 会在中间空出一大块）。

投屏记录页 `cast_management_figma_page.dart` **保留且行为未改**：它仍是查看**失败**记录与重新投屏的
地方，入口只剩投屏结果页（`casting_progress_page.dart` → `AppRoutes.figmaCastManagement`），
与小程序一致（小程序那边是结果页的「投屏明细」）。

### 页面与数据（`features/gallery/presentation/gallery_page.dart`）

页面文件与路由名（`AppRoutes.figmaGallery`）不变，UI 原样保留，数据口径整体换成投屏记录：

```text
进入页面 _loadAll()
  → refreshDevices()                     // 设备下拉 = 分类器，必须先回来才知道筛哪台
  → _ensureDeviceFilter()
  → 并发：refreshAlbum()                 // 相册照片：槽位账本 + 原图，只在 JS 侧用，不渲染
         refreshCastRecords(             // 网格数据源
             userProductId: 当前设备,
             deviceUploadState: 1)       // 只要成功
  → 本地再按 status == success 兜一层（后端忽略参数时也不串档）
  → fetchDeviceClearImgStatus()          // 一键清除提醒，逻辑未变
```

- **按设备分类**由后端按 `userProductId` 过滤完成，切设备重新请求（列表区局部 loading，
  与投屏管理页切 tab 同一套观感）；
- 网格缩略图取 `CastRecord.thumbUrl`（后端 `imgThumb`），即**当次投屏的那张**，与设备画面一致；
- 选中集 `_selectedIds` 存的是**投屏记录 id（upirId）**，不再是相册照片 id。

### 新增：记录 → 相册照片的关联键

`state.dart` 的 `CastRecord.photoId` 字段本来就声明了，但 `_castRecordFromJson` **从来没有赋值**。
本轮补上：`data['uProductImgId'] ?? data['uproductImgId']`（后端两种大小写都出现过，
对齐小程序 `records.js resolveAlbumOriginalUrl`）。删除定位槽位、删相册记录、取原图全靠它。

### 再次投屏（底部橙色圆钮，取代原「刷新屏幕」）

与投屏管理页的「再次投屏」完全同链路：连设备 → 下载服务器图片到本地 → 进 `CastPreviewPage`
构图 → 「开始投屏」照常出帧 + BLE 图传 + `setUserProductUpload` **建新记录**。
所以再次投屏产出的是一张新照片、一条新记录，不改动被选中的那条。

- **单选**投一张；**多选/全选**一次把选中的多张交给 `CastPreviewPage(imagePaths: [...])`，
  走与手选多图完全相同的批量链路，上限复用 `CastUploadLimit.batchLimit`（常规 10 / 白名单 100），
  超出直接提示不放行；
- 图源优先「相册里同一张照片的原图」（按 `photoId` 关联 `AlbumPhoto.imageUrl`），
  退回记录里的投屏图——记录里的 `img` 是按设备尺寸转换过的，直接预览会显得被拉伸；
- 选中项按**网格展示顺序**投，不是 `Set` 的迭代顺序；
- 小程序的预览页能直接吃远程 URL，Flutter 的 `CastPreviewPage` 只接受本地路径，
  所以批量再次投屏要**逐张下载**。下载实现收口到新文件 `features/cast/recast_download.dart`
  （`RecastDownload.toTempFile`），投屏管理页原来的私有 `_downloadToTemp` 一并换成它，两处不再各写一份。
- 连接与下载分两段 `AppLoadingDialog`（它的文案不能中途改，批量下载几十秒里一直显示
  「正在连接设备…」会让用户以为卡在连接）。
- 整段包一个 `try/finally` 释放 `_recasting` 重入锁：中途任何一条 return 都必须解锁，
  否则按钮会永久点不动。

### 删除（底部红色圆钮）

沿用图库删除链路，末尾追加一步：

```text
deleteAlbumPhotos(photoIds)      // 设备槽位 0x12（含删到屏显图时补 0x24 刷屏）→ delUserProductImg
  → deleteCastRecords(recordIds) // 新增：删来源投屏记录
  → 重新对账
```

- **必须删来源投屏记录**：本页列表就是按成功记录铺的，只删设备与相册记录的话，下次进来照片还在；
- `state.dart` 新增 `deleteCastRecords(Iterable<String>)`：后端无批量接口，串行逐条调用，
  **允许部分失败**（设备与相册记录已经删掉，不能整体回滚），返回 `(total, failed)`；
  有失败时页面提示「照片已删除，投屏记录未全部删除，请稍后重试」；
- 记录关联不到相册照片（照片已被删 / 后端没回 `uProductImgId`）时跳过设备与相册删除，
  只删记录本身，并按「照片在此设备异常」提示——不能因此挡住整批删除，否则这类记录永久卡在列表里；
- 设备/相册删除失败时**不动**投屏记录（留着才能重试）。
- 全批都没有相册照片时不再要求蓝牙授权（没有设备操作可做）。
- **相册账本整份没加载成功时直接拦下删除**（`photoIds.length < records.length && state.albumLoadError`）：
  否则 `photoId` 一律换算不到，会退化成「只删记录、不删设备上的图」，相框上留下再也删不掉的孤儿图片。
  App 与小程序在这里的表现不同才需要这道闸——小程序那边接口失败时整页是「加载失败」，根本点不到删除。

### 保持不变

设备下拉（`DeviceFilterChip`，去重 + 重名补序列号尾号）、一键清除提醒、`_resolveDeviceImageIndex`
槽位解析、`imgIndex = 0` 合法、删除后补刷屏、跨设备保护，全部原样。

## 风险与待确认

- **未编译**：本机无 Flutter SDK，`flutter analyze` / `flutter test` 都没跑。合并前必须在有 SDK 的
  环境跑一次；重点看 `gallery_page.dart` 的 `_recastSelected`（`final` 变量在 try 里赋值、
  `use_build_context_synchronously`）与 `deleteCastRecords` 的记录类型。
- **一键清空 / 另一端删除后的幽灵条目**：`clearUserProductImg`、`delUserProductImg` 是否级联删除投屏记录
  **待后端确认**（小程序侧同一问题）。若不级联，设备被一键清空后「我的相册」仍会列出这些照片；
  页面已有的「请重新上传图片」弹窗会提示，用户全选删除也能清掉（设备侧解析为 -1 自动跳过）。
  反之若后端已级联，本页追加的记录删除会失败并误报「投屏记录未全部删除」。
- **分页上限**：相册照片与投屏记录都按 `pageSize: 100` 拉取。相册超过 100 张时较早的记录可能关联不到
  相册照片，会退化成「只删记录、不删设备槽位」。分页策略**待后端与产品确认**。
- **`refreshGalleryPhotoOnScreen` 成了死代码**：手动「刷新屏幕」入口两端都已下线（删除后的自动补刷屏
  仍在 `deleteAlbumPhotos` 里）。产品确认不再需要该入口后，可连同 `galRefreshScreen` / `galRefreshing`
  一起删除。
- 「我的」页的「N 张照片」仍取账号级 `imgCount`（相册口径），与「我的相册」按设备分组后的条数不是同一口径。

## 建议回归（真机）

1. 「我的」只剩两张卡且等分排布，四语种下标题不换行；
2. 进「我的相册」：只显示投屏成功的照片，切设备能正确分档，下拉刷新可用；
3. 单选「再次投屏」→ 预览页构图 → 投屏成功后返回，列表多出一条；
4. 多选/全选「再次投屏」：预览页能左右切图逐张构图，超过 10 张给出上限提示；
5. 单选与多选删除：设备上的照片确实消失，返回列表也不再出现（记录已删）；
6. 删除一条「相册里已经没有对应照片」的记录：不报错、记录被清掉；
7. 折叠屏折叠/展开首页与「我的」都不溢出、可滚动。

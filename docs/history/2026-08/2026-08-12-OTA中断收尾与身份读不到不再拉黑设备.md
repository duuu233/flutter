小程序侧现场两句话：**「升级失败，设备就连接不上了」**、**「退出小程序重进又正常」**。

## 一、「0x01 读不到」≠「这台不是我要的」

**现场**：升级失败/中断之后回详情页点连接，一路「未搜索到该电子纸设备」——**设备就在眼前**。

`_verifyBoundDeviceIdentity` 此前返回 `bool`，两件完全不同的事都是 `false`：

```dart
catch (error) { … return false; }             // 0x01 读不回来（超时/异常）
…
return verifiedDeviceSerialMatch(serial, actual);  // 读到了，但不是这台
```

三个调用方（扫描主路径 / `_tryDirectConnect` / `_tryConnectSystemDevice`）拿到 `false` 一律按
**串台**处理：`excludedDeviceIds.add(remoteId)` + 删掉 `BleDirectConnectCache`。

而 OTA 刚失败/中断时最容易撞上的恰恰是**前者**：设备还在收拾自己的 DFU 状态机，0x01 读超时是常态。
于是第一次重连就把**正确的那台**永久排除出本次编排，后面几轮无论怎么扫都只剩「未搜索到」，
直连缓存也一并没了 —— 下次复连还要白花一整轮扫描。

> 与小程序是**同一个现场、相反的成因**：小程序是**该断不断**（连接留在设备上，设备被占着不广播）；
> App 断得很干净，却**断了还顺手把它拉黑**。

**改法**：`bool` → `enum _IdentityVerdict { verified, mismatched, unreadable }`。

| 结局 | 断链 | 排除候选 | 删直连缓存 |
| --- | --- | --- | --- |
| `verified` | 否 | — | — |
| `mismatched`（读到了，不是这台 / 屏型不符） | **是** | **是** | **是** |
| `unreadable`（读超时 / 异常 / 应答里没有 Device_ID） | **是** | **否**（按「连接失败」同款，允许原地重连一次，反复读不到才排除） | **否** |

断链对三种失败一视同仁——连上了却不能用的链路留着，只会让**单连接的设备被自己占住不广播**，
下一轮扫描必然搜不到。断链是幂等的，代价只有下一轮重扫。

「反复读不到才排除」复用了已有的 `connectFailures` / `_maxConnectFailuresPerCandidate` /
`retryTarget` 机制（原地重连、不重扫），没有新增控制流。

## 二、中断之后要给设备收尾

**现场**：升级传到一半退出升级页，回详情页显示「已连接」，但读设备信息一直转圈到超时。

`dispose()` 此前只有 `_aborted = true`，设备侧一点收尾都没有。代价两层：

1. 设备的 DFU 状态机停在半截，同一条 GATT 连接上再 START 必被回 `0x05`。
   `BleController.upgradeFirmware` 的 wedged-retry 能自愈（断链 → 等 3s → 重连 → 整轮重来），
   但那是**下一次升级白白多花的一整轮**，本来这一刻断一次链就免了。
2. 连接还留着，而设备正忙着收拾自己：详情页/首页拿这条链路读 0x01、读电量会一直等到超时，
   界面上却写着「已连接」。

**改法**：新增 `_resetDeviceAfterInterrupt()`，在 `_runUpgrade` 的 `OtaAbortedException`
与 `catch(error) + _aborted` 两条分支里调用，做一次 `_ble.disconnect()`（best-effort，失败只记日志）。

> ⚠️ 关键细节：收尾必须放在 **`if (!mounted) return;` 之前**。中断最常见的成因就是页面被 pop
> （`_aborted` 正是 `dispose` 打的），此刻 `mounted` 已经是 `false`，放在后面等于永远不执行。
> 干跑（`dryRun`）不碰蓝牙，直接跳过。

## 三、中断要能及时收手

小程序同轮把 `shouldAbort()` 补进了 `doStart` 与头信息重发循环，App 这两处同样漏了
（数据窗口那层早就有）：

| 位置 | 最坏空转 | 补了什么 |
| --- | --- | --- |
| `_doStart` 的特征×objType 穷举 | ~15s（3 特征 × 2 objType × 2.5s） | 每换一个组合先查 `shouldAbort` |
| 头信息重发循环 | ~33s（3 次 × 10s 超时 + 两次退避） | 每次 attempt 开头先查 `shouldAbort` |

这段时间里我们一直占着设备，而**设备被占着时不广播**——用户已经退出页面了，其它入口却连搜都搜不到它。
`shouldAbort` 已经是 `upgradeFirmware` 的现有参数，只是往下多传了一层给 `_doStart`。

## 未同步 / 未决

1. 小程序的 `releaseStrayConnections` **不移植**：App 侧的等价问题由 `_tryConnectSystemDevice`
   以更优的方式解决（连它，而不是放掉再重扫）。若将来发现「本进程持有、但 `_client` 不认」的
   GATT 客户端泄漏，再单独议。
2. 小程序侧同期还有一批 iOS 虚拟支付的改动（`-15001 INVALID_PLATFORM` = 微信客户端 < 8.0.68），
   **与 App 无关**：App 的 iOS 走原生 Apple IAP（`setApplePayVerify*`），不是
   `wx.requestVirtualPayment`。
3. 小程序 `docs/protocols/ota-dfu.md` 记的「START 是否会立即擦除正在运行的分区」仍**待固件方确认**。
   若答案是「会」，则「中断是安全的」这个前提要重估，本文第二节的口径也要跟着改。

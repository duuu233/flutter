## Background

小程序把「我的图库」的两个接口（`getUserProductImgList` / `delUserProductImg`）从端上整体删掉了：
「我的相册」自 2026-08-04 起铺的就是**投屏成功记录**，删除自 2026-08-10 起只认记录自己的 `imgIndex`、
`delUserProductImg` 早已屏蔽——图库列表最后只剩两个消费方，两个理由都已不成立：

1. **再次投屏「取图库原图」**：旧理由是「记录里的 `img` 是后端按设备尺寸转换过的图，直接预览会被拉伸」，
   写于 2026-07-06；自 2026-07-22 `setUserProductUpload` 改传**原图**（只按设备长边等比缩、不改比例）起
   就已失效。图库那条照片与这条投屏记录本就是**同一次上传产生的同一张图**，绕一跳换不到任何画质/比例
   差别，只多一个请求。
2. **默认设备规则「第一台有照片的设备」**：判据取自图库照片的归属设备，与本页数据源（投屏记录）不同源。

App 侧本轮逐条对齐。**端上删除的定义收成两步**：删设备槽位(`0x12`) + 删来源投屏记录；
图库照片的清理归后端。

## 1. 接口层（`boltfox_api.dart`）

删除 `getUserProductImgList` / `delUserProductImg` 两个方法（后端接口仍在，只是端上不再有消费方），
原位留了一条写明理由的墓碑注释，对齐小程序 `utils/api.js` 的同款做法。

## 2. 状态层（`state.dart`）

| 删除 | 为什么它站不住了 |
| --- | --- |
| `AlbumPhoto` 类、`_albumPhotos`、`myAlbum`、`_albumIdRank`、`_albumPhotoFromJson`、`_albumOrderFallbackEpoch` | 图库列表整份下线，账本没有来源 |
| `refreshAlbum` | 同上；它还是「我的相册」首屏 `Future.wait` 的一半——**一个用不上的接口有权把整页打成「加载失败」** |
| `albumLoaded` / `albumLoadError`（含私有字段） | 同上 |
| `deleteAlbumPhotos(Set<String> photoIds)` | 入参是图库照片主键，改成按槽位删（见下） |
| `devicePhotoAbnormalMessage` | 旧链路里「记录没给 `imgIndex`、又推算不出位置」的提示。新口径下缺索引在**页面侧就整批终止**了，到不了这一步 |
| `refreshGalleryPhotoOnScreen`（手动刷屏 0x24） | 2026-08-04 页面合并后就没有调用方，且以图库账本为输入。删除时删到屏显图的**自动补刷屏**不受影响，仍在新方法里 |
| `_resolveDeviceImageIndex` / `_inferDeviceImageIndex` | 「按上传先后推算槽位」的回退，输入是同设备在库照片的排队顺序。索引来源已收敛成记录自己的那份，缺了就整批终止，刻意不再推算 |
| `CastRecord.photoId`（后端 `uProductImgId`）及其映射 | 它只喂过「按记录找图库原图」和「按图库照片解析槽位」两处，两处都改成直接吃记录自己的 `img` / `imgIndex` |

新增两个替代口子：

```dart
// 选中的投屏记录 → 待删槽位；任意一条缺索引/非法（含越界，IMG_MASK 只有 96 位）→ null，整批终止
static List<int>? resolveDeleteSlots(Iterable<CastRecord> records)

// 删除的「设备侧那一半」：0x12（含删到屏显图时补 0x24 刷屏）；不再碰任何后端图片记录
Future<ActionFeedback> deleteDevicePhotoSlots({required String deviceId, required List<int> slots})
```

**没有变的**：读 `0x01` 的 `IMG_MASK` 把待删槽位分成「设备上还在的 / 已经不在的」两拨
（`splitSlotsByDeviceMask`，掩码读不到时一张都不判 gone）、设备忙 `0x0B` 的原样提示、
`0x05`/`0x07` 良性结果码放行、删到屏显图时补刷屏——整段逻辑原样搬进新方法。

顺带一处口径修正：**一键清空**成功提示里的「共移除 N 张」原先数的是图库账本里这台设备的在库照片，
账本没了，改数**清空前 `0x01` 掩码的占位数**——设备掩码本就是更准的那一份（另一端已删的不会被算进来）。

## 3. 页面（`gallery_page.dart`）

- **首屏/重入**：`Future.wait([refreshAlbum(), _refreshRecords()])` → 只拉记录，顺带修掉上面说的
  「用不上的接口能把整页打成加载失败」。
- **默认设备四档 → 三档**（对齐 `pickDefaultFilter`）：保留当前选中 → 连接中的设备 → 第一台。
  删掉的是夹在中间的「第一台有照片的设备」：判据与本页数据源不同源，要按「哪台有照片」排就得把每台
  设备的记录都拉一遍（一台一个请求），代价远大于收益；「连接中的设备」已覆盖最常见的场景。
- **删除**：确认框 → `resolveDeleteSlots`（缺索引 → 新文案「投屏记录未返回有效的图片索引，无法删除」，
  整批终止）→ 定位目标设备 → 权限门禁 → `deleteDevicePhotoSlots`（0x12）→ `deleteCastRecords`（允许部分失败）。
  删掉了 `_photoOfRecord` 和「相册账本没加载完就拦下」那道防线——账本本身已不存在。
- **再次投屏**：图源直接用 `record.imageUrl ?? record.thumbUrl`，不再按 `uProductImgId` 回图库找原图。

## 6. 与小程序有意不同 / 不适用

- 小程序 `projection/records/records.js` 那处 `resolveAlbumOriginalUrl`（再次投屏绕图库取原图）
  **App 侧从来没有**：`cast_management_figma_page.dart` 一直用 `record.imageUrl ?? record.thumbUrl`，无需改动。
- `utils/request.js` 的中文接口名表、`utils/mock.js` 的 `/album/photos` 路由：App 没有这两层，不适用。
- ⚠️ **明确保留**（与小程序同）：`getUserProductClearImg` → 弹「请重新上传图片」→ `editUserProduct`
  复位 `isClearImg`。它查的是 UserProduct 侧的**设备状态**，不属于图库列表链路，也是用户唯一能感知到
  「设备在别处被一键清空过」的入口。

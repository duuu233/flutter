## 第 1 项 · 「我的相册」卡片张数 = 全部设备的投屏成功记录条数

### 为什么改

2026-08-04 把「设备照片」「投屏管理」合并成「我的相册」后，列表数据源换成了投屏成功记录，
但「我的」页卡片上的「N 张照片」还是账号级 `imgCount`（相册口径，含投屏失败的、已从设备删掉的），
和用户点进去看到的列表对不上——即上一份文档 Known Issues 里记的那条。

### 实现

`PhotoFrameState` 新增：

| 成员 | 说明 |
| --- | --- |
| `refreshMineCastSuccessCount()` | 拉计数：`getUserProductImgRecordList` 带 `deviceUploadState: 1`、**不带 `userProductId`**（卡片是全部设备的合计） |
| `minePhotoCount` | 改为返回这份计数（不再是 `imgCount > 0 ? imgCount : myAlbum.length`） |
| `mineCastSuccessLoaded` | 首屏是否已出结果，「我的」页据此显示 `--张照片` 还是真实数字 |

关键点：

- **不写 `_castRecords`**。那份列表是图库页/投屏管理页按各自的设备与状态条件拉的，
  被这里的全量结果覆盖会串页；所以单独存一个计数，而不是复用 `castRecords.length`。
- 少打请求：整页都是成功记录时直接采信分页元数据 `recordCount`（一次请求就拿到真实总数，
  超过一页也不截断）；后端忽略过滤参数时 `recordCount` 是「成功+失败」的合计，只能逐页翻并按状态数，
  判停优先看 `pageCount`/`recordCount`（同 `refreshFaq` 的口径：后端可能无视 pageSize 按默认值分页），
  20 页封顶做死循环保险丝。
- 失败保留上次成功值（弱网进「我的」把张数清零，用户会以为照片没了），但照样结束首屏加载态。
- 登出 / 注销 / 会话失效三处清理点都要复位计数与 loaded 标记，否则下一个账号先看到上一个人的数字。
- `mine_page.dart` 的 `_reload()`（`initState` + `didPopNext`）把原来的 `refreshAlbum()` 换成
  `refreshMineCastSuccessCount()`——张数不再取自相册列表，本页也就不必再拉相册了。

`UserProfile.imgCount` 仍照常解析，只是不再用于「我的」页展示。

## 第 2 项 · 折叠屏适配方案

### 结论：App 侧的「方案」早就在，本轮补齐一个缺口

小程序这轮把首页那套做法抽成了公共方案（`styles/fold-adapt.wxss` + `utils/fold-adapt.js`，两种模式）。
Flutter 的对应物是 **`FigmaScreen`**（`lib/src/shared/widgets/figma_common.dart`）：

| 小程序 | Flutter |
| --- | --- |
| `.fold-viewport`（一屏高 + 纵向 flex） | `Scaffold` + `SafeArea` + `Column`（本来就是一屏高） |
| 顶部导航留在滚动区外 | `FigmaTopBar` 在 `Expanded` 之外 |
| `.fold-scroll`（`flex:1 1 0` + `min-height:0`） | `Expanded(child: SingleChildScrollView(...))`（`scrollable: true`，默认值） |
| 固定底栏留在滚动区外 | `bottom` 槽位（在 `Expanded` 之外） |
| `.fold-scroll-body`（`min-height:100%`） | **本轮新增** `fillViewport: true` |
| 页面高度只用 `100vh`，不用 JS 快照 | 不适用（约束由父级 `LayoutBuilder`/`BoxConstraints` 给，天然跟随窗口） |

也就是说：凡是用 `FigmaScreen` 默认参数的页面，一直都是「导航固定 + 内容可滚 + 底栏固定」，
折叠屏展开、分屏、横屏、系统大字号都不会把内容顶到够不着的地方。全库 `Scaffold` 页面逐个核对，
只有 `shell_page`（Tab 容器）与 `splash_page`（居中 Logo）没有滚动子树，两者都不承载会超高的内容。

### 本轮新增：`FigmaScreen.fillViewport`

缺口在传了 `scrollable: false` 的页面。这类页面分两种：

1. body 里已经有自己的滚动区（`Expanded(child: ListView/SingleChildScrollView)`）——图库、投屏管理、
   AI 会话/对话、操作指南、协议正文、我的设备、发现设备列表等，**本来就是对的，不动**；
2. body 是「靠 `Spacer`/固定间距按一屏排版」的静态页——一屏装得下时排版正确，装不下就直接
   RenderFlex overflow 被裁掉且滚不动。

第 2 类本轮改用新的 `fillViewport: true`：

```dart
LayoutBuilder(builder: (context, constraints) => SingleChildScrollView(
  padding: bodyPadding,
  child: ConstrainedBox(
    constraints: BoxConstraints(minHeight: 视口高 - bodyPadding.vertical),
    child: IntrinsicHeight(child: body),
  ),
))
```

内容不够高时 `minHeight` = 视口高，`Spacer` 照旧按比例分配剩余空间，**观感与改动前逐像素一致**；
内容超过视口时按内容高度排并允许滚动。这与「我的」页/登录页/注册页早就在用的骨架是同一套
（`SingleChildScrollView + ConstrainedBox(minHeight) + IntrinsicHeight`），只是收口进了 `FigmaScreen`。

⚠️ **body 里已有无界滚动子树的页面不要打开 `fillViewport`**：`IntrinsicHeight` 量不出它们的固有高度。

接入页面：`bind_device_searching.dart`、`bind_device_not_found.dart`
（280×280 的雷达 + 标题 + 说明 + 帮助链接 + 底部按钮，短窗口下确实会溢出）。

### 与小程序的差异（不是漏做）

- 小程序投屏预览页要靠 `@media (min-aspect-ratio: 3/4)` 让编辑舞台让高度；
  Flutter 的 `cast_preview_page` 用的是 `Expanded(child: _buildStage())`，
  舞台本来就按剩余空间伸缩，窗口一矮自动变小，无需媒体查询。
- 小程序要在 `onResize` 里重测状态栏/底部安全区；Flutter 的 `MediaQuery`/`SafeArea` 自动跟随，
  没有对应动作。
- 小程序 `device/bind` 要把写死的 `88rpx` 导航高换成实测值；Flutter 顶栏是固定 56 逻辑像素的
  真实控件，不存在这个换算误差。

## Known Issues / Risks

- **未编译**：本机无 Flutter SDK，`flutter analyze` / `flutter test` 未跑。
- `fillViewport` 只在两页启用，其余 `scrollable: false` 的页面依赖「body 自带滚动区」这一前提；
  以后给这类页面加静态内容时要么保持 body 可滚，要么改用 `fillViewport`。
- 计数在后端忽略 `deviceUploadState` 时最多翻 20 页（2000 条），超出部分不计入（刻意的上限，
  与小程序一致）。
- 同一张照片多次成功投屏会有多条成功记录，卡片与列表都按记录计数、两边一致，
  但与设备上实际图片数不是同一回事（结论同 2026-08-04）。

## 建议回归（真机）

1. 「我的」页张数：投屏成功后返回应 +1，删除照片后应 -1，多设备账号应是各设备之和；
   弱网/断网时保留上次数字而不是清零；换账号后不残留上一个账号的数字。
2. 绑定设备的「搜索中 / 未发现设备」两页：折叠屏展开、横屏、分屏、系统最大字号下不出现
   overflow 条纹，内容能滚到底部帮助链接；一屏装得下时排版与之前一致。
3. 折叠/展开来回切、分屏、三折叠三种形态下各页不溢出、可滚动。

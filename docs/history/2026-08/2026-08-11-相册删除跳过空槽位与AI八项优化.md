## 一、删除：跳过设备上已经没有的槽位

### 上游现象

同一台电子纸设备被两部手机连过，另一端删掉了 A：

```
设备：[0]空 [1]B [2]C        本机记录：A→0  B→1  C→2（A 那条后端记录还在）
本机「我的相册」仍列出 A/B/C，全选删除 → 整批失败：「掩码不一致(该位置已有图/索引越界)」
```

0 号位在设备上已是空槽，客户端却把它和 1、2 一起塞进 `0x12` 的 `IMG_INDEX_MASK`，
固件按 v1.5 §6.6.1 回 `RESULT=0x07`，**没问题的 B、C 也跟着删不掉**。

### 新口径（2026-08-10 产品确认，两端一致）

删除以「**从我的相册里消失**」为准，设备侧尽力而为：

| 情况 | 设备侧 | 后端记录 |
| --- | --- | --- |
| 槽位上还是这张图 | 发 `0x12` 删掉 | 删 |
| 槽位在设备上已空（另一端删过） | **跳过**，不影响同批其它张 | 删 |
| 槽位上现在是另一端后传的**别的图** | 仍**按索引删掉**，不做内容比对 | 删 |
| 设备忙 / Flash 写失败 / 传输中断 / 断连超时 | 如实中止 | 不删 |

### App 侧改动

1. **`FrameProtocol`**（`lib/src/device/ble/frame_protocol.dart`）新增
   `skippableDeleteResults = [0x05, 0x07]` / `isSkippableDeleteResult` / `isSkippableDeleteMessage`
   —— 对齐小程序 `utils/frame-protocol.js` 的 `SKIPPABLE_DELETE_RESULTS`。

2. **`FrameBleException` 带上原始结果码**（`device_ble.dart`）：新增 `resultCode` 字段与
   `FrameBleException.isSkippableDelete(error)`（先认码、无码才退回文案匹配）。
   「一键清空」与「我的相册删除」两条链路自此**同一套口径、同一份实现**，
   `state.dart` 里那份靠中文正则匹配的 `_isMissingDevicePhotoError` 删除。

3. ⚠️ **`deleteImage` 此前吞掉了失败结果码**：它只 `parseMaskResult(ack.data)`、从不看 `RESULT`
   （`0x0B` 设备忙在 `request` 里单独拦截，其余一概放行）。也就是说固件回
   「Flash 写入失败(0x04) / 传输中断(0x09) / 掩码不一致(0x07)」时 App 会**当成删除成功**，
   照删后端记录，图却还留在相框上。现在如实抛出并带结果码，由调用方决定放行还是中止。
   这条不在上游需求里，是同步过程中在 App 侧发现的既有缺陷。

4. **`deleteAlbumPhotos`**（`state.dart`）：
   - 读一次 `0x01` 的 `IMG_MASK`，用纯函数 `PhotoFrameState.splitSlotsByDeviceMask` 把选中槽位
     分成 `onDevice` / `gone` 两拨；`onDevice` 为空就整条 `0x12` 都不发；
   - **掩码读不到不再中止删除**（此前 `readTransferInfo` 一失败就报「设备删除失败」，
     弱网下谁也删不掉）：按记录里的真实 `imgIndex` 原样下发，交给良性结果码兜底。
     此时**一张都不判 `gone`**，否则会退化成「记录全删了、图还留在设备上」；
     ⚠️ 与「设备真的一张图都没有」区分 —— 那是 12 个 0 的**合法掩码**，全判 `gone` 才对；
   - `0x12` 抛错时：设备忙单独提示；`0x05/0x07` 按已删继续删记录；其余如实中止。
   - 「照片在此设备异常，请删除重新上传」的提示口径收窄：**只**在「记录没给 `imgIndex`、
     又推算不出位置」时出现。另一端删过属于正常跳过，静默按「已删除」提示 ——
     原来那句话在这种场景下是自相矛盾的（刚被删掉，却让用户「删除重新上传」）。

5. `_resolveDeviceImageIndex` 的 ② 回退推算抽成 `_inferDeviceImageIndex`：删除链路要区分
   「槽位已空」和「定位不到」两种 -1，刷屏(0x24)那条链路行为一字未改。

### 与小程序仍存在的差异（本轮**不**改）

- **记录缺 `imgIndex`**：小程序整批终止（绝不猜位置）；App 保留既有的「按上传先后推算槽位」
  回退（`_inferDeviceImageIndex`），推不出才跳过并提示。这是 App 侧更早的设计，
  改动它会牵动刷屏链路，不在本轮范围内。
- App 删除后会在「删到当前屏显图」时补一次 `0x24` 刷屏，小程序没有这一步。

### 测试

新增 `test/album_delete_skip_missing_slot_test.dart`：分拨的四种情形（含掩码为 null 与
空掩码的关键区分）、良性结果码白名单、带码/无码两种判定、设备忙不放行。

⚠️ 本机没有 Flutter SDK，**`flutter analyze` / `flutter test` 未在本轮执行**，需在有 SDK 的
环境补跑。

### 第 5 项：两端有意不同

- 小程序：原「会话列表」的位置改为**返回**，「会话列表」排到返回键**右边**（它的顶栏右侧被
  微信原生胶囊占着）；
- **App：返回仍在最左，「会话列表」放到最右**（需求明确要求）。App 顶栏右侧没有原生胶囊，
  空着反而失衡。
- 「进 AI 隐藏底部 tabbar、输入卡下移」在 App 侧**本就不存在**：AI 页是 push 进来的整页，
  从来没有底部 tab 栏。

### 关键实现说明

- **Token 胶囊从聊天页顶栏移除**：标题要真正屏幕居中，两侧就得等距，右边挂一颗 100+ 宽的胶囊
  时标题只能偏左，两者不可兼得。余额展示位统一到「历史会话」页（与小程序同口径）。
- **`AiToken`**（新增 `lib/src/features/ai/ai_token.dart`，对齐小程序 `utils/ai-token.js`）：
  余额读写从聊天页私有常量提取为公共模块，两页共用。
  ⚠️ 顺带把 `limitEnabled` 设为 **false**（小程序 2026-08-03 就关了，App 一直开着）：
  余额是本地假的、支付未上线，App 侧等于埋着「聊满 100 次就再也发不出消息」。
  关掉后不扣费、不拦截、恒显示默认值；接后端时改回 true 即可，逻辑原样保留。
- **长按分区**：Flutter 这边天然成立 —— 正文是 `SelectableText`，它在手势竞技场里自己吃掉
  落在文字上的长按（选字/复制），只有气泡内边距等空白处才冒泡到气泡的 `onLongPress`。
  图片则显式给一个空的 `onLongPress` 认领手势，长按图不再弹「删除整条」。
- **删除会话「点不动」的真因**（与小程序同源）：左滑手势原先罩住**整条轨道**，手指落在已滑开的
  删除按钮上也算新一轮滑动，点按时那一两像素抖动就把卡片吸附回去。手势收到**卡片**上即可。
  删除按钮宽度 68 → 80、滑开位移 76 → 88（＝小程序 160rpx / 176rpx）。
- **发送图标几何**：`ai-send-active.png` 是 141×141 画布，实心橙圆只占中间 45.4% 且圆心偏上
  （y=63.5 而非 70）。按 35 画时圆只有 ~16，比左邻麦克风（24）还小。现按 57 画（圆 ≈26）
  并下推 4.61%，让「圆」而不是「圆+阴影」上下居中；命中盒仍是 35，三态切换不位移。
- 用户自己发的图气泡也补上常驻操作条：长按菜单撤掉后，那是「下载/投屏」仅剩的入口。
  该气泡只有 215 宽，英文/日文标签更长，故这一处包了 `FittedBox(scaleDown)` 防溢出。

- `_activeImageMessageId` / `_activeImageIndex`（「展开中的操作条」状态）；
- `_onImageLongPress`；l10n 的 `aiMessageActions`。

## Background

小程序侧把「固件 2026-08-07 那轮传输优化」的参数从调试台升为真实投屏默认值，并在随后的真机回归里
连修了四轮。App 侧此前一直按老口径跑（每包 236 字节 / 窗口 10 / legacy 调速），本次一并对齐。

## 1. 传输参数（`device_ble.dart` / `ble_tuning.dart`）

| 参数 | 改前 | 改后 | 位置 |
| --- | --- | --- | --- |
| 0x21 每包数据上限 | 236 | **489** | `FrameBleClient.imgDataChunkMax`（新增常量）+ `dataChunk` |
| 窗口上限 | 10 | **50** | `transferWindowMaxPackets` |
| 窗口默认值 | 10 | **50** | `BleTuning.defaultWindowPackets` |
| 调速策略 | legacy | **AIMD 自适应** | `uploadImage` 数据段循环 |

**没有变的**：图传连接间隔仍是平台默认 **Android 7.5ms / iOS 15ms**；每包发送间隔仍是极速 3ms
（`BleTuning.defaultPaceMs`）。iOS 不能更低——Apple 规范拒绝 <15ms 的参数更新请求。

`dataChunk` 的夹取规则一字未改，只是上限跟着抬到 489：整帧 = 数据 + 8，单次可写 = MTU-3，
即 **数据 ≤ MTU-11**。所以顶不到 MTU 500 的链路自动收缩，MTU 247→236（与改前完全一致）、
iPhone 常见的 185→174，**无需任何平台特判**。

## 2. AIMD 拥塞控制（本次的重点，与窗口 50 是一组）

⚠️ **窗口 50 与 AIMD 是同一个决定的两半，回滚必须一起回**：老策略在大窗口下会退化成
「灌满 → 设备缓冲溢出丢包 → 其后整窗按序作废 → 等满超时 → 从丢包处整窗重发」的死循环，
窗口越大每转一圈代价越大。

App 侧原本的调速与小程序 legacy 同款，**连那个 bug 都一样**：

```dart
// 改前：「减速兜底」被配置值封顶，实际永远降不下速
curPace = curPace + paceStep > paceMs ? paceMs.toDouble() : curPace + paceStep;
```

现已换成与小程序 `createAdaptivePacer` 同口径的实现：

- **丢包记忆（类 TCP ssthresh）**：超时后窗口减半，并把 `capWindow` 钉在减半值；此后窗口最多
  涨回 cap，只按每 `capProbeAfter=8` 个干净窗口 +1 小步上探。
  设备收包缓冲是**固定容量**、不是随行情波动的网络拥塞——不钉住的话会反复「涨回→再溢出」，
  每次付出 1~2s，一张几百包的图撞墙几十次（小程序真机实测「参数更大反而慢好几倍」的主因）。
- **pace 快速回落**：退让上限 `paceBackoffMaxMs=16`（原来 legacy 那条路能抬到 150），
  每 `paceRecoverAfter=2` 个干净窗口砍半回落到起点。窗口才是防溢出的主控，间隔长期抬着只会白拖慢。
- **自适应 ACK 超时**：`ackTimeout = clamp(ema(推进耗时)×4 + 150, 300, 3000)`，替代固定 600ms。
- **宽限一轮再判丢包**：第一次超时先多等一轮（超时×2，上限 3000ms）。
  ⚠️ 重试后**不重置** `graceUsed`——每次重试都重置的话，同一个卡点每轮都白付一次双倍超时。
- **会话级稳态记忆** `_tunedWindow`：每张传完把收敛出的 `capWindow` 记到会话上，
  同一条连接的下一张直接从稳态出发，多张连传只有第一张付收敛成本。

## 3. 旋钮口径版本戳（`BleTuning`）

`BleTuning.load()` 会从 SharedPreferences 读回上次调好的值——**默认值改了但旧存储值还在**，
新默认等于从没生效过。小程序侧正是踩了这个坑：真机 stats 里 `window: 10 / configuredPace: 0`
是早先在调试台存的，排查时一度误判成「50 包把设备压垮了」。

新增 `_kEpoch` / `_epoch = '2026-08-14-w50'`：`load()` 时版本不匹配即整组作废并清掉、回落出厂值；
`save()` 时盖上当前口径戳。以后再改默认值同步升这个常量即可，不必要求用户手动 `resetToDefaults`。

## 4. 进度条连续平滑（`smooth_progress.dart` 新增）

BLE 的真实进度天生跳变——固件每 10 包才回一次 0x23，窗口 50 包时一次应答推进几十包，
直接透传就是「冲一段 → 停 0.2s → 再冲一段」。

解法**不是**提高刷新频率（会抢占主 isolate、拖慢图传本身，原来的 120ms 节流防的就是这个），
而是**减小每次更新的幅度**：只在取整值变化时 emit，整场 ≤101 次，比原来「最多 8 次/秒」还少。

`SmoothProgress` 与小程序 `utils/smooth-progress.js` 同源，含四版演进的全部教训：

1. v1 追平即停表 → 「0→7% 丝滑、停 0.2s」——增量几拍冲完就干等；
2. v2 按预计间隔铺开 → 段间不停，但 ACK 稍晚仍会先走完停一下；
3. v3 计划超前 `_planAhead=1.5` + 仅逾期才吸附 → 每段只走 2/3、剩 1/3 作缓冲吸抖动；
4. v4 **受控前瞻**（产品拍板「可酌情浮动百分之几、失败必须立即停」）→ 允许领先真实目标
   ≤`_leadMax=3`，每拍步长取「计划腿」与「速率腿」的较大者，锥减渐近逼近。
   ⚠️ 两条腿写成互斥分支是走过的弯路：前瞻只在「恰好追平」才切入，中段几乎不会发生
   （仿真实测最大领先 0.0%）——取较大者合并才真正生效。

不变量：
- 显示值 ≤ 真实目标 + 3，且**未真实完成前永不显示 100%**（99 封顶）——100% 只能由
  真实完成给出。产品口径：「99% 处可以停顿等设备真到 100%，保证终点时刻一致」；
- 单调不减（`freeze` 是唯一例外）；
- 落后不超过 `_maxLag=12`（传输突然提速时补齐超出部分，不拖后腿）；
- **失败即 `freeze()`**：连前瞻领先出去的部分一起钳回真实目标——这是「允许造一点假」的对价条款，
  失败画面上停着比真实更高的数字就是在骗用户。已接在 `projection_service` 图传 catch 分支。

驱动源是累计 ACK **已确认**的包数（不是发出去的包数），所以不存在「失败当成功」。

配套把 `cast_result_common.dart` 里橙条的补间时长由 **250ms 改为 33ms**：补间必须 ≤ 渲染节拍，
否则上一格没补完下一格就来了，橙条会一路拖在数字后面（250ms 是给「8 次/秒跳变」配的）。

## Risks / Follow-up

- ⚠️ **本机无 Flutter SDK，未跑 `dart analyze` / `flutter test`，也未真机**。合入前必须补跑。
- 小程序侧真机踩到过一个 **WeChat API 特有**的坑：`setBLEMTU` 成功回调回显的是**请求值**而非
  真实协商值，按虚高 MTU 分包会写出被链路静默丢弃的大帧、传十几包后彻底卡死；且会话复用时
  沿用建连那刻的陈旧 MTU 会重现同一故障（修法：协商两次取小 + 复用前 `getBLEMTU` 复核）。
  **App 侧暂未做等价处理**——`flutter_blue_plus` 的 `requestMtu` 返回的是 Android
  `onMtuChanged` 回调里的真实值、iOS 的 `mtuNow` 也是 CoreBluetooth 的实测值，理论上不会虚高。
  但这条只是推断，**真机若出现「传几十包后停住不动」，第一嫌疑就是它**，届时按小程序那套补。
- 老固件（不含 08-07 那轮优化）会拒收/丢弃 489 字节大包。小程序侧曾加过「零推进自动降级到
  236/窗口 10」的兜底，但被用户实测推翻（那台设备在调试台跑 489 极快，证明是客户端 MTU 问题
  而非固件），**已全部移除**；App 侧同样不引入无判据的降级猜测。
- 真机回归口径：同一张图对照改前后的 `dataMs / throughput / retries`；关注日志新增的
  `win=50->minN->capM` 三段——cap 稳定钉在某个档位说明丢包记忆生效，反复涨回则要复查。

## 第 2 项 · 为什么 App 改的是「预热」而不是「轨道结构」

同一句反馈，两端的成因**不一样**，别把小程序那版改法照搬过来：

- **小程序**是自绘轨道的三个**固定槽位**只换 `src`，微信 `<image>` 在新图解码完成前继续显示旧位图，
  落位瞬间露出的是刚滑走那张 —— 那边的修法是把三格改成带 `wx:key` 的列表，让节点跟着图片走。
- **Flutter** 用的是底层 `PageView.builder`，页 element 按 index 建、落位时不会被换成别的图，
  **不存在这个复用错位**。它的短板在另一头：邻页是**手指开始滑动的那一刻**才建 `Image.file` 的，
  几 MB 的手机照片读盘 + 解码常要一两百毫秒，正好压在 `_kSlideDuration = 300ms` 的过场里——
  过场里先是一张白卡（`ColoredBox` 的白底），落位后图才姗姗补上，观感同样是「重新加载了一遍」。

```dart
void _precacheNeighbors(int index) {
  for (final i in <int>[index - 1, index + 1]) {
    if (i < 0 || i >= _paths.length) continue;
    final path = _previews[i]?.path ?? _paths[i];   // 与 _buildPager 同一取源优先级
    precacheImage(FileImage(File(path)), context, onError: ...);
  }
}
```

放在 `_enterEdit` 末尾（进页首帧量到舞台后、以及每次切图落位后都会走到），对齐小程序早就有的
`_prefetchNeighbors`。取源必须与 `_buildPager` 一致（`_previews[i]?.path ?? _paths[i]`），
否则预热的是原图、过场里显示的是烘焙缓存，等于白热一次。
失败只 `debugPrint` 吞掉：预热失败不该冒泡成未捕获异常，真正展示时 `Image.file` 自己的
`errorBuilder` 还会兜底。

> ⚠️ `_previews[i]` 变了（用户编辑后重新烘焙）时不需要额外补预热：烘焙发生在切图过场里，
> 落位后的 `_enterEdit` → `_precacheNeighbors` 正好会把那张新路径预热上。

## 第 4 项 · 容量行口径

`已用/上限`（如 `8/51`）；未连接仍是 `--` —— 内存占用只有连接后读 `0x01` 才拿得到，
未连接时用后端回落值会误导用户。行文案（`devMaxPhotoCount`）与取值成对，改一个必须改另一个。

## 一、收尾窗口被当成丢包（协议层）

**现场**：`OTA 传输中断：已发送 673/673 包后，设备未在 1.5s 内应答（疑似丢包）`——数据其实**已全部发出**。

设备按 PRN 信用窗口每收满 3 包回一次 DATA ACK，而 673 = 3×224 + **1**：最后一窗只有 1 包，
本就等不到应答。规格书 §6.3.3 原文「固件返回 3，APP 每发送 3 个 DATA 包等待一次 ACK」、
§8 流程图 `loop [每 PRN 个 DATA 包]` —— **收尾不足一窗的包，规格书没有为它定义应答**。

改法（`_transferData`）：收尾窗口的 ACK 按「可选」处理，直接发 END。整包完不完整由 END(`0xF3`) 的
`total_bytes == bin_size` + CRC32 裁决（不匹配设备回 `0x09`），真丢包一样抓得住。

## 二、失败后不断链，设备卡在 DFU 状态（控制层）

**现场**：第一次中断后，之后每次点升级都是 `OTA 启动被拒绝：设备状态错误（ACK=FC F1 05 F2）`。

连接还留着，设备状态机停在升级态，同一条 GATT 连接再 START 必被回 `0x05`。

改法（`BleController.upgradeFirmware`）：把一轮 DFU 抽成 `_runDfuAttempt`；失败若属于
「设备侧状态没复位」（见下 `OtaFailureKind`），就 **断链 → 等 3s → `connectBoundDevice` 重连 →
从 START 整轮重来一次**；两轮都不成才提示「请断电重启设备」。
已进入 payload 传输之后的失败**不自动重试**，交给用户重新发起。

> 与规格书的出入：§8 流程图失败分支写的是设备「保持连接或等待 APP 重新发起 DFU」，
> 而真机回 `0x05` 拒绝同一连接上的再次 START。断链复位是端上兜底，该差异建议向固件方确认。

## 三、头信息握手：不应答 / 回 0x05（协议层）

**现场**（复位后）：START 应答正常，却收不到 128 字节头信息的校验结果；加了延时后变成设备**会**应答，
但回 `0x05`。

关键点：FF11 属性是 `Write Without Response, Notify`（§6.3.2）——**无应答写被丢是静默的**，
设备收到 START 后正在初始化写入区（擦 Flash），这时发过去的头信息很可能就丢在忙碌期里。三层兜底：

1. START ACK 后先等 **300ms** 再发头信息。只等一小会儿是因为反向也有风险：固件若同样有
   「约 1s 没等到下一包就中断」的口径（§6.4 图传即如此），久等反会让它先把这轮 DFU 判死；
2. 同一连接内最多发 **3 次**头信息，每次等 **10s**（原 5s），退避 1.5s/3s。依据 §6.3.4
   「设备端通过首包长度判断为头信息」——只要它还没收下过，重发的仍按头信息处理；
3. 三次都过不去才按「会话卡死」走第二条的断链复位。

**`0x05` 与 `0x0A~0x0E` 分开对待**：`0x05`（设备状态错误）= 此刻不能受理，可重试；
`0x0A~0x0E` = 这个包不对，立即停止并把设备语义透传给用户，绝不重发。

重发的代价写进了 END 的错误文案：若设备其实已收下第一包、只是应答丢了，重发的 128 字节会被
计入 bin 数据，END 回 `0x09` 时会带上这条线索。

## 四、发包前的本地预检（协议层，新增）

刷错固件不可逆，「传错文件」不该等刷到设备上才由错误码兜。`_prepareFirmware` 新增
`_assertPackageLooksRight`：按 §6.3.4 字段表解析那 128 字节头信息（**只读不改**，仍原样发送），
四类明确不对的在碰蓝牙前就终止——

| 检查 | 拦截理由 |
| --- | --- |
| 偏移 0 不是 `OTAINFO\0` | 根本不是 OTA 包（传错文件/下载截断） |
| 头部长度字段 ≠ 128 | 不是本协议的包 |
| 声明 bin 大小 ≠ 文件实际 payload 长度 | 包不完整 |
| 固件类型与设备面板不符 | 刷错面板会变砖 |

**CRC16 / CRC32 / 版本号不同形只记日志不拦**：规格书没写这两个校验的多项式口径，本地算法与固件
不一致会把好包挡在门外；这两项本就由设备校验（`0x0D` / `0x09`）。面板由
`otaPanelOfDevice(screenCode:)` 换算（`3.7寸=3D7`、`5.89寸=5D89`），判不出返回 0 自动跳过，不误伤。
mock 干跑包不带真实头信息，跳过预检。

## 五、FW_SIZE 范围改回规格书原文

`_minFwSize` 由 `0x30000` 改回 **`0x3000`**（§6.3.3 START 请求表原文，PDF 与文档截图两处一致）。
端上此前自作主张"更正"过下限，而现场固件 bin payload ≈164KB —— 落在原文范围内却被判成
"超出建议范围"，每次升级白打一条误导告警。越界一律只告警不拦，真超限由设备回 `0x08`。

## 六、升级页「未连接就点不动」（页面层，补上游 08-11 第二节）

上游当天修的「点了没反应」App 侧同款存在：`_canUpgrade` 含 `_connected`，按钮画着却点不动，
用户只能自己退回详情页连一次。三处改：

- `_canUpgrade` 不再含 `_connected`，只表示「有升级包、可以按」；
- 未连接时主按钮文案改「**连接并升级**」（新增 l10n `otaConnectAndUpgrade` / `otaConnectFailedRetry`，中英日三语）；
- `_runUpgrade` 未连接不再直接 return，而是就地 `PermissionGate` + `state.connectDevice` 自动扫连，
  连不上才回到可重试状态并如实展示原因；`autoStart` 也不再要求已连接（入口那次连接可能在路上掉了）。

## 故障归属速查（两端一致）

| 设备回什么 | 结论 |
| --- | --- |
| `0x0A`/`0x0B`/`0x0C`/`0x0D`/`0x0E` | **升级包**的问题 |
| END 阶段 `0x09` | 数据没收全 / CRC32 对不上 |
| `0x05`，或干脆不应答 | **设备状态**的问题（断电重启；持续出现找固件方） |
| 本地预检直接拒绝 | 文件本身不对（传错/截断/面板不符） |

## 一、「我的」页两张卡片的数字都取用户信息接口

### 口径

两个数字都由 `GET /Client/User/getUserInfo` 直接下发，端上不再自己算：

| 卡片 | 取值 |
| --- | --- |
| 我的设备 | `productCount` |
| 我的上传 | `imgCount` |

### 改法

| 位置 | 改动 |
| --- | --- |
| `state.dart minePhotoCount` | `_mineCastSuccessCount` → `_currentUser.imgCount` |
| `state.dart mineDeviceCount` | `productCount > 0 ? productCount : _devices.length` → 纯 `productCount` |
| `state.dart mineCastSuccessCount`（新增 getter） | 保住 `_mineCastSuccessCount` 的读取口，标注「保留备用、当前无调用方」 |
| `mine_page.dart _reload()` | 三个并发请求收成一个：只留 `refreshCurrentUser()`（去掉 `refreshDevices()` 与 `refreshMineCastSuccessCount()`） |
| `mine_page.dart` 两张卡的 subtitle | `loaded` 参数统一改成 `state.userLoaded`（原先分别是 `userLoaded \|\| devicesLoaded` 和 `mineCastSuccessLoaded`） |

`didPopNext`（被覆盖的页 pop 回来时重拉）照旧 —— 这两个字段只有 `getUserInfo` 会更新，
不重打就永远是旧值；投屏成功后 `casting_progress_page` 已经在 `refreshCurrentUser()`，正好覆盖
「刚上传完回我的，数字要变」。

### 为什么这是对 2026-08-05 的有意回退

2026-08-05 把张数从 `imgCount` 换成投屏成功记录条数，是因为当时卡片叫「我的相册」、点进去看到的是
投屏成功记录，而 `imgCount` 把投屏失败的、已从设备删掉的也算在内，两个数对不上。现在卡片文案是
「我的上传」，口径本来就是「上传过多少张」，不必再与相册列表对齐。**别再为了对齐列表改回去。**

### 卡片标题一并改成「我的上传」

小程序「我的」页那张卡的标题早已是「我的上传」，App 还写着「我的相册」——本轮按「直接按小程序的改」
一并追平：`AppL10n.mineMyGallery` 改名为 `mineMyUploads`，文案
「我的上传 / My Uploads / マイアップロード」（繁中走 `toTraditionalChinese` 自动转成「我的上傳」），
旧 key 全项目只有「我的」页这一个消费方，改完无残留。

与首页宫格的 `homeEntryUploadsTitle` 文案相同、**故意各留一份**：两处是不同的产品件，
以后只改一处时不该互相牵连（同 `mineMyDevices` 与首页那格的既有做法）。
⚠️ **目的地没变**，仍是 `AppRoutes.figmaGallery`（「我的相册」页 = 投屏成功记录列表）——
标题说「上传」、点进去是成功记录，这正是 08-05 那条口径被回退的原因：
卡上的数字是账号级上传数，与列表条数本就不是一个数。
顺带清理：`docs/l10n-review.html`（2026-08-05 那次文案审阅的一次性生成物，701 KB，仓库里没有
生成脚本）本轮按产品确认**已删除**——它里面还留着旧的「我的相册」，留着只会与代码打架。

## 二、「我的相册」删除：捕捉到设备繁忙(0x0B)整批中止，不删任何数据

### 口径

只要撞上设备繁忙 `0x0B`：提示「当前电子纸设备繁忙，请稍后重试」，**设备侧没删、后端投屏记录一条不删、
列表不刷新、选中态保留**，用户稍后原样再点一次即可。

两个捕捉点（删除链路里所有会撞上忙窗口的设备交互）：

| 位置 | 原行为 | 现行为 |
| --- | --- | --- |
| `0x01` 回读 IMG_MASK | 任何失败都只 `debugPrint`，按选中槽位原样下发 | 繁忙 → 中止（连 `0x12` 都不发）；其它失败照旧原样下发 |
| `0x12` 删除应答 | 繁忙记进 `deviceError`，**继续删记录** | 繁忙 → 中止（`deleteCastRecords` 一次都不调） |

### 改法

- `device_ble.dart` 新增 `FrameBleException.isBusy(Object?)`：与既有 `isSkippableDelete` 同一套写法，
  优先认 `resultCode == 0x0B`，拿不到退回 `FrameProtocol.isBusyMessage` 文案匹配
  （对齐小程序新增的 `protocol.isBusyError`）。
  ⚠️ **刻意不看 `kind`**：`FrameBleErrorKind.busy` 还被端上自己的图传门闩（「已有图传进行中」）复用，
  那不是设备回的 `0x0B`。
- `state.dart deleteDevicePhotoSlots`：两处 `catch` 各加一个前置分支，繁忙即
  `return DevicePhotoDeleteOutcome(blockedMessage: 繁忙提示)`。繁忙分支**排在**
  `isSkippableDelete`（`0x05`/`0x07` 良性放行）与真失败分支之前。
  原来 `0x12` 那处的「繁忙 → 单独文案记进 `deviceError`」分支被这条取代。
- 复用既有的 `blocked` 语义（原本只表示「前置条件不满足」）：调用方
  `gallery_page._confirmDelete` 对 `blocked` 本来就是「toast 原因后直接 return」——
  `deleteCastRecords` 不调、`_selectedIds` 不清、`_reloadRecordsForFilter()` 不跑，
  正是要的「什么都不删、选中态保留」。两处文档注释同步写清多出来的这个来源。

### 为什么繁忙要和别的失败区别对待

繁忙是设备**回帧主动拒绝**、指令根本没执行（规格书 v1.5 §6.6.1，固件刷墨水屏/写 Flash 的忙窗口
约几秒，见 2026-08-20 那份对真机 `刷屏失败：设备繁忙(0x0B)` 的定性），不存在「删了一半」的中间态，
天然可重试；先把后端记录删掉只会白留一张「相册里看不到、端上也没有 `imgIndex`」的幽灵图。
而 `0x04` Flash 写入失败 / `0x09` 传输中断 / 断连超时确实可能已删掉一部分，仍走 2026-08-20 的
「两半互不阻断」，否则用户会卡在「怎么点都报错」。

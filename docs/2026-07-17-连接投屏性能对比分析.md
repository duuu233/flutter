# 连接 / 上传 / 图传 性能对比分析（App vs 小程序）

> 触发：用户反馈「小程序在**连接蓝牙、连接设备、图片上传、图片传输**四个环节都明显比 App 顺畅」。
> 本文档是**只读审查**结论，不含任何代码改动——每一项都给出「现状证据 / 小程序做法 / 影响 / 建议方案 / 风险」，由用户决定是否实施。
>
> 参照物：小程序 `/home/pg/dh/photo-album`（同后端 `api.boltfox.cn`，逐行精读过 `utils/device-ble.js`、`utils/active-device.js`、`subpackages/projection/result/result.js`、`utils/request.js` 的当前代码）。
> 原则：**功能/数据格式对齐小程序，实现取原生最优解**（见 memory `app-vs-miniprogram-principle`）。

---

## 结论速览

先说三个反直觉的事实，避免走错方向：

1. **BLE 图传的「热路径」App 与小程序逐字节一致**——236 分包 / 窗口 10 / pace 3ms 探到 0 / 连接间隔 7.5(安)·15(iOS)ms / 600ms 累计 ACK / 预组帧 / 查表 CRC。所以「纯图传那一段」两端速度本应相同，**图传慢≠图传算法差**，多半是上传拖累了整条链或 BLE 栈没真正跑在优化参数上（见 F3）。
2. **真正拉开差距的是「上传的原图体积」**：小程序已于 2026-07-16 改成「压到设备长边 **1 倍**、q90」；App 还在传「设备长边 **2 倍**、q80」，即**每张原图大约是小程序的 3.5~4 倍字节**。这一条几乎可以单独解释「上传慢 + 后端转码慢」。⚠️ App 里现存的 memory/注释是照着小程序**旧逻辑**（>400KB、2×、q80）写的，小程序早改了，App 没跟。
3. **连接体验的差距在「重试」而非「速度」**：小程序的连接、服务发现、特征发现**都带重试循环**，App 全是**单次**。安卓 GATT 首次连接/发现本来就易抖动，单次失败就直接报错让用户手动再点一次——这会被体感成「小程序一次就连上、App 常要点两次」。

| 环节 | App 现状 | 小程序 | 差距定性 | 优先级 |
|---|---|---|---|---|
| 图片上传体积 | ~~设备长边 2×、q80~~ → **已改为设备长边 1×、q90** | 设备长边 **1×**、q90、原生 `wx.compressImage` | ~~原图约 3.5~4× 大~~ → **已对齐** | **P0 ✅已改** |
| 连接设备可靠性 | ~~`connect` 单次、`discoverServices` 单次~~ → **已加连接 ×2 + 发现轮询 5×/250ms** | 连接 ×2 重试(400ms)、主服务 6×/250ms、特征 4×/200ms | ~~安卓首次抖动即失败~~ → **已对齐** | **P0 ✅已改** |
| BLE 图传实际吞吐 | ~~参数与小程序一致，但**未在真机验证**~~ → **已把测量搬进 App（正式包可测）+ 修了 iOS 的 MTU 读取时机** | 真机实测过 | 可能优化没生效（0x13 被拒/MTU 协商偏低/FBP 写吞吐） | **P1 ✅已可自测（2026-07-22）** |
| 首张流水线重叠 | 首张上传要等 0x01 读完才起步 | **F1**：首张上传用设备记录尺寸，与连接/0x01 并行 | 每次投屏多串行 ~1 个往返+300ms | P2 |

## 一、按影响排序的缺陷与优化项

### 【P0-1】上传原图体积是小程序的 ~4 倍（上传慢 + 转码慢的主因）

**现状与证据**
- 选图层：`cast_photo_picker.dart:39` `_maxLongEdge = 1920`（= 最大机型 5.89 寸 960 的 **2 倍**），`:42` `_quality = 90`，走 `image_picker` 原生降采样。
- 投屏前二次兜底：`projection_service.dart:769 _prepareUploadSource` → 触发阈值 `>400KB`（`:848 _uploadCompressTriggerBytes`），目标长边 = **设备长边 × 2**（`:787-789` + `:849 _uploadLongEdgeScale = 2`），质量 **80**（`:850`）。
- 这一步用 **纯 Dart 的 `image` 包**做「解码 → `copyResize` → `encodeJpg`」（`:864-887 _compressUploadSource`）。

**小程序做法（当前代码，2026-07-16 改）**
- `result.js:807 compressForUpload`：`wx.getImageInfo` 拿长边，**长边 > 设备长边(1×) 才压**，`wx.compressImage(quality:90, compressedWidth/Height = 按比例缩到设备长边)`——原生实现，目标就是**设备长边 1 倍**。
- 即：3.7 寸设备上传 720 长边、5.89 寸上传 960 长边；App 对应上传 1440 / 1920。**App 线性 2×、面积/字节约 4×**（再算上 q80 vs q90，净体积 ≈ 小程序的 3.5~4 倍）。

**为什么这条最关键**
- memory 已确认「投屏耗时构成：①原图上传 + 后端转码 ≫ ②BLE 图传」。上传字节 4× 直接放大这个「大头」，弱网尤甚；后端还要 decode + downscale + 抖动一张 4× 大的图，转码也更慢。
- 后端最终只吐设备分辨率的六色 4bpp 帧（480×720 / 680×960），上传 1× 还是 2× 长边，**下发给设备的帧完全一样大**——多传的字节是纯浪费。小程序团队正是基于这个判断在 2026-07-16 把 2× 降到 1×。
- 附带：App 那步是「q90 原生图 → q80 纯 Dart 重编码」，既**二次有损**又**慢**（纯 Dart 解码一张 1920px JPEG 常 300ms~1s）。

**建议方案（三选一，均由你定夺）**
- **A（对齐小程序，最省事、收益最大）**：把 `_uploadLongEdgeScale` 从 2 改回 1（对齐 `compressForUpload` 的设备长边 1×）。上传字节直接降到 ~1/4。质量担忧：后端本就缩到设备分辨率再抖动，1× 已等于设备分辨率，肉眼无损（小程序线上已这么跑）。
- **B（保留一点过采样但换原生编解码）**：长边取 1.25~1.5×，并把 `_prepareUploadSource` 的纯 Dart `image` 换成原生插件 `flutter_image_compress`（见第三章），避免慢速纯 Dart 编解码。
- **C（最彻底）**：投屏时已知设备尺寸，直接在**选图阶段**就把 `image_picker` 的 `maxWidth/maxHeight` 设成当前设备长边（原生降采样，一步到位，砍掉整个 `_prepareUploadSource` 二次压缩）。难点：选图时可能还没确定投给哪台设备（首页多设备），需把「选图 → 预览页确认设备 → 再按设备尺寸压」串起来。

**风险**：方案 A/C 会让「已裁剪/旋转过的编辑产物」也被压到设备长边——需确认预览页裁剪导出（`cast_image_editor.dart` q92 / 2000px）与这步的先后不冲突（当前 `_prepareUploadSource` 在最后兜底，改小 scale 不改变时序，风险低）。

> **✅ 已实施（2026-07-17，方案 A）**：`projection_service.dart`
> - `_uploadLongEdgeScale` `2 → 1`（目标长边 = 当前设备长边 = 设备分辨率）；
> - `_uploadCompressQuality` `80 → 90`（对齐小程序 `UPLOAD_COMPRESS_QUALITY`）；
> - 同步更新 `_prepareUploadSource` 与 `cast_photo_picker.dart` 的注释（原写的是小程序旧逻辑 2×/q80）。
> - **未做**（留作后续，需加依赖 + 开发机 pub get）：把 `_compressUploadSource` 的纯 Dart `image` 包换成原生 `flutter_image_compress`；把选图层 `_maxLongEdge` 从 1920 降到 960（= 最大设备长边×1），让纯 Dart 解码更快。本次只改上传目标体积，不动选图/裁剪链路。

### 【P0-2】连接/服务发现无重试——安卓首次抖动即失败（连接体感差的主因）

**现状与证据**
- `device_ble.dart:257 connect()`：`:269 device.connect(timeout: 12s)` **单次**；`:294 discoverServices()` **单次**；发现不到 FF00/FF01/FF02 直接抛错（`:302`、`:313`）。
- `ble_controller.dart:364 connect()` 无重试；`connectBoundDevice` 也是扫到即连一次。

**小程序做法**
- `device-ble.js:307 createConnectionWithRetry(attempts=2)`：失败先 `closeBLEConnection` 再 `sleep(400)` 重试，「already connected」按成功处理。
- `device-ble.js:252 discoverMainService(attempts=6, interval=250)`、`:277 discoverCharacteristics(attempts=4, interval=200)`：安卓 `getBLEDeviceServices` 首次常返回不全，靠轮询补齐。

**影响**
- 安卓 BLE 的 GATT 连接与服务发现**首次失败/返回不全**是常态（厂商栈差异大）。小程序靠重试兜住，用户几乎无感；App 单次失败就弹「连接失败/未找到服务」，用户手动再点——**主观上就是「小程序一次连上、App 老要点两次」**。这正是四项抱怨里「连接蓝牙 / 连接设备」的直接来源，且与图传算法无关。

**建议方案**
- 给 `_client.connect` 包一层「连接 ×2（失败先 disconnect + 400ms 再试）」+「discoverServices 轮询到齐（如 4~6 次 / 250ms）」，语义照搬小程序 `createConnectionWithRetry` / `discoverMainService`。
- 注意与既有的 S2「失败必 disconnect 回收」、S12「connecting 重入护栏」保持一致：重试要在同一个 `connecting=true` 区间内，别触发重入拒绝。

**风险**：低。纯增强可靠性，不改协议。唯一要注意别把「用户主动取消」也重试。

> **✅ 已实施（2026-07-17）**：`device_ble.dart`
> - 新增 `_connectWithRetry(device, attempts:2)`：`device.connect` 失败先 `disconnect()` 再 `sleep(400)` 重试，最多 2 次（对齐 `createConnectionWithRetry`）；
> - 新增 `_discoverFrameChars(device, attempts:5)`：轮询 `discoverServices` 直到 FF00 下 FF01/FF02 齐了才返回 `[write, notify]`，最多 5 次 / 每次 250ms（对齐 `discoverMainService`/`discoverCharacteristics`）；
> - `connect()` 改调这两个helper，替换原来的单次 connect + 单次 discoverServices。
> - 与既有会话卫生一致：仍在同一 `connecting=true`（S12 重入护栏）内、失败仍走 `catch → disconnect()`（S2）、`_linkAlive`/notify 订阅时序不变（S2/S3）。
> - **副作用（预期，非 bug）**：设备真的不在时最坏连接耗时 ~24s（2×12s + 400ms），比原来 12s 长——只发生在两次都超时的真失败场景（连接前已扫到设备，通常一次即成）。

### 【P1-3】图传优化是否真在真机生效——未验证（可能是「传输慢」的隐藏元凶）

**现状**
- App 的图传参数（`device_ble.dart:102-106`）与小程序**逐字节相同**。所以**若图传仍慢，问题不在参数，而在**：
  1. **0x13 是否被固件接受**：`optimizeConnectionIntervalForTransfer`（`:462`）无条件下发 0x13 并回读 0x05 校验，但校验结果只在 `kDebugMode` 打印（`:471-476`），release 无从得知。老固件不认 0x13 → 整场跑在手机默认 30/45ms 间隔，慢一倍。
  2. **MTU 实际协商值**：`:284 requestMtu(512)`，但真机返回可能远低于 512；虽然分包恒被夹到 236（`dataChunk`），MTU 过小仍会让单包放不下 244 帧而**静默丢包卡传**。
  3. **`flutter_blue_plus` 的 write-without-response 吞吐**：窗口 10 的流水线，前提是底层「无应答写」真的能连发不等回调。部分 FBP 版本/机型会串行化每次写（等 `onCharacteristicWrite`），那样窗口 10 名存实亡，吞吐退回「一包一等」。这是**两端最可能的真实差异**（小程序走微信原生 BLE 栈，App 走 FBP）。

**建议方案（先测再改）**
- App 已内建 `DeviceInteractionTrace`，但只在 debug 打印。**做一次真机 trace**：debug 包连一次、投一批，`adb logcat | grep DeviceInteraction`，看：
  - `set-fast-connection-interval` 后的「请求 7.5ms / 回读 Xms（已生效/未生效）」；
  - 每张 `ble-transfer-image-N` 的实际毫秒 / 换算 KB/s，与小程序真机实测（5.89 寸约 17.6KB/s）对比。
- 若回读显示 0x13 未生效 → 是固件版本问题，记差异台账，别再调发送侧。
- 若 0x13 生效但吞吐仍明显低于小程序 → 高度怀疑 FBP 写吞吐，方案见第三章（FBP 写法调优 / 平台通道）。

**风险**：纯测量，无风险。**这一步应先于任何图传侧改动**——否则容易在「参数已对齐」的地方反复空转。

> **✅ 已实施（2026-07-22）**：详见 `docs/2026-07-22-iOS投屏性能优化.md`。要点：
> - 原方案要 Mac + `adb logcat` / Xcode，iOS 侧根本走不通（无应用内日志、release 不打印、
>   CoreBluetooth 读不到连接间隔）。改为**把测量搬进 App**：`BlePerfLog`（release 也记录）
>   + 隐藏的「投屏性能自检」页（设置 → 更新 BoltStar → 连点版本号 7 次）。
> - 上文列的三个怀疑点现在都能在正式包里单独证伪：
>   **① 0x13 是否生效** → RTT 探针（100ms 档 vs 图传档比最小往返时间，≥2.5 倍即生效）；
>   **② MTU 实际协商值** → 自检页第①块直接显示，并且**已修**：iOS 的 `mtuNow` 原来读得太早，
>   会拿到初值 23 → 每包 12 字节 → 包数暴涨十几倍（这极可能就是「iOS 特别慢」的真凶）；
>   **③ FBP 写吞吐/背压** → 旋钮把数据包切成「有应答写」重测，看 `retries` 是否归零。
> - 另修：release 关掉 flutter_blue_plus 的逐包日志（iOS 的 os_log 开销落在传输热路径上）。

### 【P2-4】首张上传没有与连接/读信息重叠（每次投屏白串一个往返）

**现状与证据**
- `projection_service.dart:175` 先 `await readTransferInfo`（0x01）拿宽高，`:220 startPrefetch(0)` 才起首张上传，`:226 beginTransferSession`（0x13 + 300ms 回读）。首张上传的网络时间**没有**盖住 0x01 读这一个往返。
- 且 `ble_controller.connect()` 在连接时已读过一次 0x01（`:386`），投屏又读一次（`:175`）——**0x01 读了两遍**（第二遍是为拿最新 imgMask，有合理性，但宽高/屏型可复用）。

**小程序做法**
- `result.js:348-356 F1`：首张 `convertOnServer` 直接用**设备记录里的 guessedSize** 起步，与 `ensureConnection + readTransferInfo(0x01)` 并行；0x13+回读也并行在首张上传里（`:422-441`）。

**建议方案**
- 用连接时已缓存的 `BleController.info`（含 width/height/screenType）**先把首张上传发出去**，`readTransferInfo`（拿最新 imgMask 用于选槽位）与之并行；帧长度仍按 0x01 实读值校验（`:248 expected4bpp`）作兜底，尺寸不符再回退。
- 收益：每次投屏省掉「0x01 一个往返 + 部分 0x13/300ms」的串行等待（约几百 ms~1s，取决于链路）。

**风险**：中。若设备记录尺寸与真机 0x01 不一致会白传一张（memory `app-vs-miniprogram-principle` 已记此风险）。可只在「记录尺寸 == 上次连接实读尺寸」时启用。

### 【P2-5】多张投屏可「反超」小程序：预取深度自适应加深

**现状**：`projection_service.dart:199,245` 预取深度固定 1 张。小程序也是 1 张——**App 不落后，但也没利用原生优势反超**。

**为什么有空间**：既然「上传+转码 ≫ BLE 图传」，那 BLE 在传第 i 张时，后台其实**可以同时**转码第 i+1、i+2…（后端转码是纯网络/后端算力，不占 BLE、不占本机 CPU）。深度 1 时 BLE 传完第 i 张往往还要干等第 i+1 张转码。加深到 2~3 张并行上传，多张投屏的总耗时可从「Σ 上传」压到「max(上传, 图传) 叠加」，弱网多图收益明显。

**建议方案**：把预取改成「最多 K 张在途」（K=2~3，或按已测得的 上传/图传 时间比自适应）。这是「取原生最优解、超过小程序天花板」的正解（符合 App 差异化原则）。

**风险**：中。①后端对同账号并发上传是否限流需确认；②中断/失败时浪费的在途上传更多（K 张）；③本机内存/连接数上升（可控，K 小）。建议先做 P0/P1，再评估这条。

### 【P3-6】连接后同步等 0x13 空闲间隔（老固件最坏卡 2s）

**现状**：`device_ble.dart:332` 在 `connect()` 内 `await applyIdleConnectionInterval()`（发 0x13→100ms，`setConnectionIntervalMs` 内 2s 超时 `:448`）。老固件不认 0x13 时，**每次连接都在这白等最多 2s** 才算「连接完成」。

**小程序**：同样在连接后发空闲间隔（`device-ble.js:454`，2s 短超时、吞错），但这一步不该挡在「连接可用」之前。

**建议方案**：把这步改成 `unawaited(...)`（后台发），连接建立（notify 就绪）即返回可用。省电目的不需要阻塞连接完成。

**风险**：极低。best-effort、失败本就不影响使用。

> **✅ 已实施（2026-07-22）**：`connect()` 改为 `unawaited(applyIdleConnectionInterval())`。
> 同时堵死改后引入的竞态——「连接后立刻投屏」时空闲档(100ms) 与图传档(15ms) 两条 0x13 会同时在飞，
> 若空闲档后到，**整场图传跑在 100ms 上，比不做优化还慢 6 倍**且极难复现。两道保险：
> `_queueConnInterval()` 串行链 + `applyIdleConnectionInterval()` 遇 `_transferSessionDepth > 0` 跳过；
> 配套把 `endTransferSession()` 改成**先降会话深度再回落**（否则这次回落会被自己跳掉）。

| **上传压缩提速**（P0-1 的实现手段） | **`flutter_image_compress`** | 原生编解码（Android CameraX/`Bitmap`、iOS `CoreGraphics`），替换 `projection_service._compressUploadSource` 里的纯 Dart `image` 包。快、省内存、可直接控 `minWidth/minHeight/quality/format`，与 `wx.compressImage` 对等。`image` 包仅保留裁剪/旋转的非交互用途即可。 |

| **保持不动** | `image_picker` 的原生降采样、`cached_network_image`、`flutter_blue_plus` 本体 | 现状合理，别顺手替换。 |

## 三、建议的推进顺序（先低风险高收益，且先测量）

1. **P1-3 先做一次真机 trace**（零风险）——它决定「传输慢」到底是上传拖累、还是 0x13 没生效、还是 FBP 写吞吐。避免在已对齐的参数上空转。
2. **P0-1 上传体积对齐 1×**（改一个常数 `_uploadLongEdgeScale: 2→1`，最大单点收益）——直接砍掉 ~3/4 上传字节。
3. **P0-2 连接/发现加重试**（低风险、直接改善「连接」体感）。
4. 视 trace 结果决定 P1-3 的图传侧改动（FBP 写法 / 平台通道）。
5. **P3-6 空闲间隔改后台发**（顺手）。
6. 有余力再上 **P2-4 首张重叠**、**P2-5 预取加深**（反超小程序）。

## 四、维持现状（勿「顺手优化」，已确认质量高于平均）

- BLE 图传协议核心：分包/窗口/AIMD pace/连接间隔/查表 CRC/预组帧/零拷贝 `sublistView`——与小程序逐字节一致且工程质量高（见 `2026-07-17-optimization-audit.md` 第四节）。
- 断链/重连会话卫生（S2/S3/S11/S12）、网络层纪律（超时/重试/脱敏）、错误分类枚举化（M2）——都不在本次性能范畴，别动。
- 图传发送侧的 pace/window 微调：在 P1-3 真机数据出来前**不要盲调**（memory 已多次记「连接间隔是第一杠杆，远大于发送侧微调」）。

# 2026-07-22 iOS 投屏性能优化（可在正式包内自证）

> 触发：用户反馈「**iOS 上传输给设备的速度明显慢于安卓端和小程序端**」，且现场条件是
> **不能用 Xcode 打印日志、只能改代码、最终在打好的 iOS 包里体验**。
>
> 于是本轮同时做两件事：
> 1. **把诊断能力搬进 App**——正式包里能自己回答「15ms 连接间隔到底生没生效」；
> 2. **落地几项确定的 iOS 侧优化**（不需要等测量结果就能确定是对的）。
>
> ⚠️ 本机无 Flutter 工具链（见 memory `no-toolchain-on-linux-box`），**以下改动均未编译**，
> 需在开发机 `flutter analyze` + `flutter test` + 真机回归。

---

## 一、为什么原来的排查路子在这个场景下走不通

`docs/iOS-投屏性能测试指南.md` 给的方案全部依赖 Mac：`flutter run --profile` 看 `[BLEPerf]`、
Console.app 挂 iPhone、PacketLogger 抓 HCI。而现在的约束是「只能改代码 + 只在正式包里体验」，
这三条全废。更糟的是 iOS 侧的先天缺口：

| 缺口 | 后果 |
|---|---|
| CoreBluetooth **没有任何读连接间隔的 API** | App 无法自证 15ms 是否生效 |
| 0x05 回读可能只是**固件保存的配置值** | 回读 15 不等于链路跑在 15 |
| `CrashLogger` 只有 Android 实现 | iOS 没有任何应用内日志文件 |
| release 下 `debugPrint` 不输出 | 正式包里 `[BLEPerf]` 一条都看不到 |

结论：**必须在 App 内造一个不依赖任何私有 API 的判据**，否则 iOS 端永远是黑箱。

## 二、核心新增：应用内「投屏性能自检」页

入口（隐藏）：**设置 → 更新 BoltStar → 连点版本号 7 次**（3 秒内）。
版本号是全 App 唯一「点了本来没反应」的控件，用户不会误触；路由 `AppRoutes.blePerf`
**刻意不按 `kDebugMode` 屏蔽**——这页存在的全部意义就是在正式包里看数字。

页面五块：

### ① 链路事实
MTU / 每包字节 / 「172KB 一帧约多少包」/ 写方式 / 本次图传档请求值。
`每包字节 < 100` 时整行标红并给出警告——见第三章 A。

### ② 连接间隔自检（RTT 探针）—— **本轮最关键的一件事**

原理：**一问一答的最小往返时间被连接间隔量化**。
一条指令要在某个连接事件里发出、设备在之后的连接事件里回 ACK，所以

```
RTT ≈ k×连接间隔 + 固件处理时间 + 排队抖动   (k ≥ 1)
```

取一组样本的**最小值**能把抖动挤掉，剩下的由连接间隔主导：

| 链路间隔 | 最小 RTT 量级 |
|---|---|
| 15ms | 30~60ms |
| 30ms | 60~120ms |
| 100ms（空闲档） | 200~300ms |

自检流程：把连接间隔设到 **100ms** 采 16 次 0x04 往返 → 设到**图传档**再采 16 次 → 比最小值。

- 比值 **≥2.5** → ✅ 0x13 确实改变了链路，15ms 生效；
- 比值 **≤1.3** → ❌ 0x13 对链路无作用（固件没真发参数更新请求，或参数违反 Apple 规范被 iOS 拒绝）——**App 侧再怎么调都没用，问题在固件**；
- 之间 → ⚠️ 不确定，贴近设备、避开其它蓝牙设备重测。

> 为什么用 100ms 而不是原文档第 6 节的 30ms 当对照：100 vs 15 是 6~7 倍差，
> 一眼可判；30 vs 15 只有 2 倍，一次偶发重传就糊掉了。这也是**不必再出三个包**跑 A/B/C 的原因。

实现：`FrameBleClient.probeCommandRtt()` + `BleRttStats`（只看 `minMs`，中位数/均值会被单次重传抬高）。

### ③ 纯 BLE 吞吐测速
本地生成彩条测试帧直传设备：**不联网、不经后端转码**，把「原图上传 + 后端转码」这个大头
整个排除掉，测出来的 KB/s 就是链路本身。判读基线沿用测试指南第 7 节
（Android ≈30~40KB/s；iOS 生效 ≈30~35，未生效 ≈15~18）。测完默认自动删掉那张测试图。

### ④ 调优旋钮（改完立即生效、跨启动保留）
`BleTuning`（新文件 `lib/src/device/ble/ble_tuning.dart`，落 SharedPreferences）：

| 旋钮 | 取值 | 用途 |
|---|---|---|
| 图传连接间隔 | 平台默认 / 15 / 30 / 100 / **不下发** | 一个包跑完测试指南第 6 节的 A/B/C 三组 |
| 发送地板 pace | 0（默认）/ 1 / 2ms | 验证 iOS 无应答写是否缺背压在丢包 |
| 滑窗大小 | 10（默认）/ 6 / 3 / 1 | 链路吃不消时的对照 |
| 数据包写方式 | 无应答（默认）/ **有应答** | **证伪用**：切成有应答写后 `retries` 归零 = 无应答写在丢包 |

这些值**正常投屏也会用**——调完可以直接回去投一批真图体验，这正是「在最终包里体验」的诉求。
「恢复默认」一键回到与小程序逐字节对齐的那组参数。

### ⑤ 埋点记录 + 一键复制
`BlePerfLog`（内存环形缓冲，最近 300 条，**release 也记录**、不落盘）。
`connected` / `connInterval` / `upload` / `rtt` / `warn` 五类，可全量复制到剪贴板回传。

## 三、本轮落地的 iOS 侧优化（不依赖测量结果，确定是对的）

### A.【最可能是真凶】MTU 读取时机——挪到服务发现之后 + iOS 轮询等真值

**问题**：`connect()` 里原来是「连上 → 立刻读 MTU → 再发现服务」。
iOS 没有 `requestMtu`，只能读 `device.mtuNow`，而它是 flutter_blue_plus **原生侧推上来的缓存值**，
`connect()` 返回时这条消息可能还没到，读到的就是初值 **23**：

```
mtu=23 → dataChunk=12 字节/包 → 172KB 一帧从 ≈994 包暴涨到 ≈14400 包
```

**慢十几倍，且与连接间隔毫无关系**——但现象一模一样（都表现为「投屏很慢」），
不先排掉它，调连接间隔就是空转。

**改法**：
1. MTU 协商挪到 `_discoverFrameChars()` **之后**（服务发现本身要几百毫秒，届时交换早已完成）；
2. 新增 `_negotiateMtu()`：iOS 侧轮询 `mtuNow` 直到 >23，最多 20×50ms；
3. 轮询用尽仍是 23 就**保持 23**——宁可慢，也不臆造更大的 MTU：真按 185 分包而链路只有 23，
   数据包会被静默丢弃，表现为图传停在某一包不再前进（比慢更糟）；
4. `dataChunk < 100` 时额外记一条 `warn`，自检页第①块标红提示「先查 MTU，别调连接间隔」。

### B. flutter_blue_plus 的日志级别——release 关掉

FBP 默认把**每一次特征读写**都打日志。图传一张图 ~1000 个数据包，每包都产生日志；
iOS 上 `print` 走 os_log，单条几十~上百微秒，整张图白白多花几十到几百毫秒，
而且这份开销**只落在传输热路径上**。安卓的 logcat 便宜得多，同样的日志量代价小很多——
**这本身就是一处 iOS 独有的相对劣势**。

`main()` 里调 `FrameBleClient.applyPluginLogLevel()`：release → `LogLevel.none`，
debug/profile → `LogLevel.warning`（出问题还能看到底层告警）。

### C. 连接后的空闲档下发不再阻塞连接（P1 文档里的 P3-6）

`connect()` 里原来 `await applyIdleConnectionInterval()`：老固件不认 0x13 时，
**每次连接都要白等满 2s** 才算「连接完成」。省电目的根本不需要阻塞连接建立，改成后台发。

**但这引入一个必须堵死的竞态**：连接后立刻投屏时，空闲档(100ms) 与 图传档(15ms) 两条 0x13
可能同时在飞，谁后到谁生效——若空闲档后到，**整场图传跑在 100ms 间隔上，比不做优化还慢 6 倍**，
且随时序抖动、极难复现。两道保险：

1. `_queueConnInterval()`：所有 0x13 走一条串行链，顺序确定；
2. `applyIdleConnectionInterval()` 执行时若 `_transferSessionDepth > 0` 直接跳过。

配套：`endTransferSession()` 改为**先降会话深度再回落**——否则这次回落会被上面第 2 条自己跳掉，
链路永远留在费电的极速间隔上。

### D. `ios/Runner/Info.plist` 补 `UIBackgroundModes: bluetooth-central`

原来只有权限描述、没有后台模式。投屏中切后台/锁屏，iOS 会挂起 CoreBluetooth，整批必断
（Android 侧对应的是 `BleConnectionService` 前台服务，iOS 一直是缺的）。

⚠️ 上架审核会问用途，如实答「与蓝牙相框保持连接以完成正在进行的照片传输」。
若产品最终不要求「投屏中可锁屏」，删掉这一项不影响前台投屏。

## 四、明确**没有**改的（以及为什么）

| 项 | 为什么不动 |
|---|---|
| 分包上限 236 字节 | 来自**固件**（PRD 6.8.2），不是 MTU 限制；iOS 协商到 527 也吃不满 |
| iOS 请求更大 MTU | CoreBluetooth **没有这个 API**，系统自协商，改不了 |
| iOS 请求 <15ms 连接间隔 | Apple 硬约束，请求 7.5ms 会被直接忽略、链路反而停在 30/45ms |
| 滑窗 10 → 30+ | 卡在**固件收包缓冲**。这是「不动连接间隔就能拿到的最大一块 iOS 收益」，但只能固件改 |
| 0x13 的 min/max 组装 | App 只下发单值，min/max 由固件组装。若固件发 min=max=15ms 违反 Apple 规范（要求 IntervalMax ≥ IntervalMin + 15ms）会被 iOS 直接拒绝 → 又是一个 2x。**请固件确认发的是 min=15 / max=30** |
| 图传协议热路径（AIMD/预组帧/查表 CRC/零拷贝） | 与小程序逐字节一致且质量高于平均，别顺手动 |

## 五、拿到包之后建议的操作顺序

1. 进自检页看**第①块**：`每包字节` 是不是 174（iOS 正常值）。
   **是 12 → 到此为止，问题就是 MTU**，本轮 A 项应已修好；若仍为 12 请回报。
2. 跑**第②块**连接间隔自检，跑 2~3 次取一致结果。
   - ❌ → 结论明确：**问题在固件**（0x13 没真发参数更新 / 参数被 iOS 拒绝），把第四章最后两行给固件。
   - ✅ → 继续第 3 步。
3. 跑**第③块**吞吐测速，与基线比。若 ≈30KB/s 却仍觉得投屏慢，
   说明瓶颈**不在 BLE**，而在「原图上传 + 后端转码」（memory 已确认这才是耗时大头）。
4. 想进一步定位无应答写丢包：第④块把「数据包写方式」切成**有应答**再测一次，
   看埋点里的 `retries` 是否从一堆变成 0。
5. 全部测完记得点「恢复默认」。
